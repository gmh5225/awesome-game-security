## 二、这台机器最大的三个坑（精华）

### 坑 1：华为锁死了 SELinux 策略写接口 → frida-server 用不了

```
frida-server -v
→ Unable to save SELinux policy to the kernel: Out of memory

# 换成 Magisk 自己的工具，同样失败（证明不是 frida 的问题）
magiskpolicy --live "allow magisk magisk_file file read"
→ write failed with 12: Out of memory

setenforce 0
→ setenforce: Couldn't set enforcing status to '0': Invalid argument
```

**结论**：任何需要在运行期改 SELinux 策略的工具在华为上全部失效。
**解法**：改用 **Frida Gadget**（把 `libfrida-gadget.so` 打进 APK，不需要改 SELinux）。
参考 [frida#1039](https://github.com/frida/frida/issues/1039)。

### 坑 2：华为上 `pm` / `am` 不能用 root 跑

```bash
adb shell su -c 'pm list packages'
→ cmd: Failure calling service package: Failed transaction (2147483646)
```

**解法**：`pm` / `am` 一律用 **shell 身份**（直接 `adb shell pm ...`，不要 `su -c`）。
这个坑会让"黑域"这类靠 `pm disable` 的工具失效。

### 坑 3：`magisk --sqlite` 带子查询会把 magiskd 搞崩

```bash
adb shell su -c 'magisk --sqlite "REPLACE INTO policies (...) VALUES (...,(select ...))"'
→ read (4 != 0) failed with 0: Success
# 之后 magiskd 死亡，root 全部失效（重启后恢复）
```

**解法**：加 su 授权走 Magisk Manager 界面，别手搓 SQL。

## 四、快速开始

### 4.1 电脑端环境

```powershell
cd 'G:\DeepSeek Harness\Root'
. .\scripts\env.ps1            # 把 adb / JDK / apktool / frida 加进 PATH
.\scripts\phone.ps1 status      # 看手机现在什么状态
```

需要预装（脚本会自动探测路径，也可用环境变量覆盖）：
- **adb**（Android SDK platform-tools）
- **JDK 17**（apktool / objection 需要）
- **Python 3.11** + `pip install frida frida-tools objection`
- **apktool**（`objection patchapk` 需要）

### 4.2 抓一个 App 的 HTTPS 明文

```powershell
# ① 让手机信任你的抓包证书（把 CA 放进 cacerts 模块，重启）
#    详见 docs/07-抓包能力配置与验证.md

# ② 开代理（手机和电脑不同网段也能用）
.\scripts\proxy.ps1 on 8080
#    另开一个窗口：mitmweb --listen-port 8080

# ③ 如果 App 有 SSL Pinning，用 Frida Gadget 解掉
.\scripts\frida-patch.ps1 -Package com.target.app -Install
#    手机上启动 App 后：objection -g com.target.app explore
#    进去敲：android sslpinning disable

# ④ 手机上操作 App，mitmweb 里就能看到明文
```

### 4.3 抓不走代理的流量

```powershell
.\scripts\capture.ps1 start
# ...操作 App...
.\scripts\capture.ps1 stop        # 自动拉回 capture\cap.pcap，用 Wireshark 打开
```

## 六、关键技术备忘

### 分区布局（本机没有 `boot`，ramdisk 在 `recovery_ramdisk`）

```
kernel           -> /dev/block/sdd38
recovery_ramdisk -> /dev/block/sdd40    ← Magisk 装在这里
fastboot         -> /dev/block/sdd28
oeminfo          -> /dev/block/sdd6     ← 解锁状态存这里
nvme             -> /dev/block/sdd4
vbmeta           -> /dev/block/sdd49
userdata         -> /dev/block/sdd64
```

### Magisk 20.1 的安装模块姿势

20.1 **没有** `magisk --install-module`，必须手动跑模块 zip 里的 `update-binary`：

```sh
export BOOTMODE=true MAGISK_VER=20.1 MAGISK_VER_CODE=20100
export ARCH=arm64 IS64BIT=true API=28
export TMPDIR=/dev/tmp MAGISKTMP=/sbin/.magisk NVBASE=/data/adb
sh META-INF/com/google/android/update-binary 3 1 "$ZIP"
```

已封装成 [scripts/install-module.sh](scripts/install-module.sh)。

### 常用 adb 命令

```bash
# 查询（不要用 su！）
adb shell pm list packages -3          # 第三方应用
adb shell pm list packages -d          # 已冻结
adb shell settings get global http_proxy

# root 操作
adb shell su -c 'ls /data/adb/modules'
adb shell su -c 'magisk -v'

# 端口转发
adb forward tcp:8022 tcp:8022          # 电脑 → 手机（SSH）
adb reverse tcp:8080 tcp:8080          # 手机 → 电脑（代理抓包）
```

.\scripts\phone.ps1 su "id"
.\scripts\phone.ps1 su "ls /data/adb/modules"
```

| Load Average | **41.40 / 31.69 / 15.14**（8 核） | ⚠️ 严重超载（正常应 < 8） |
| kswapd0 / f2fs_gc | 持续占用 CPU | ⚠️ 内存回收 + 闪存垃圾回收互相抢 I/O |
| ZRAM 交换 | 852 MB 已换出 | ⚠️ 内存压力大 |
| 主要 I/O | system_server 404 major faults，com.huawei.hidisk 6.8% CPU | ⚠️ I/O 阻塞 |
| DropBox 异常 | system_server_wtf: No service published for: connectivity (HwWifiStateMachine) | ⚠️ 系统服务启动异常 |
| 第三方应用 | 42 个 | 常驻后台多 |

**结论（初步）**：卡死不是单一原因，而是 **存储接近写满 + 老化的 UFS + 内存压缩交换 + 大量后台应用** 共同造成的 I/O 雪崩。EMUI 9.1 在 /data 剩余空间低于 10% 时，f2fs 的 GC 会与正常读写严重争抢，典型表现就是“随机卡死几十秒”。

**这意味着：修复卡死其实不需要 Root** —— 清理存储 / 恢复出厂 / 重刷固件就能解决绝大部分问题。Root 是“废物利用”的额外目标。

## 第三部分：Root / 解锁方案调研

### 3.0 前提事实

1. **华为官方解锁码通道已于 2018-07-25 永久关闭**，官方渠道无解。
2. 本机 Bootloader = **locked**，fastboot 绝大部分命令返回 Command not allowed，**必须先解锁 BL 才能 Root**。
3. 麒麟 970 无法用老牌工具 PotatoNV 解锁（PotatoNV 仅支持 Kirin 620/65x/925/935/950/955/960）。

   - **硬件测试点**：拆机后用镊子把主板测试点短接到地。

### 3.6 解锁之后的 Root 路线（华为特有，重点）

因为 **华为 EMUI 9 没有 boot / ramdisk 分区**，所以不能照搬“修补 boot.img”的通用做法。

**路线 R1：Magisk 修补 recovery_ramdisk（推荐，无需第三方 Recovery）**
1. 从官方固件 update.app 中提取原厂 recovery_ramdisk.img（用 HuaweiUpdateExtractor）
2. 装 Magisk App → 设置里**打开 Recovery Mode**（因为检测到 Ramdisk = No）→ 修补 recovery_ramdisk.img → 得到 magisk_patched-xxxxx.img
3. fastboot flash recovery_ramdisk magisk_patched-xxxxx.img
4. **每次开机按住 音量+ + 电源** 进 recovery → Magisk 引导系统 → 获得 Root
5. 代价：正常开机无 Root，必须走 recovery 组合键；可装 Magisk 模块（Zygisk + Shamiko 隐藏 Root）

**路线 R2：刷第三方 TWRP + Magisk**
- 荣耀 V10 有适配 EMUI 8/9 的 TWRP 3.2.x，刷入 recovery_ramdisk 后卡刷 Magisk.zip
- 优点：可备份/刷机更方便；缺点：TWRP 与 EMUI 9.1 兼容性参差

**Magisk 版本建议**：EMUI 9 上 **v23.0** 兼容性最好（v24+ 对 legacy recovery 模式支持有变化，v26+ 基本移除），也有教程用 v20.4。

**必要收尾**：解锁后需处理 dm-verity / AVB（Kirin-Tool 解锁流程通常已处理，或 fastboot flashing unlock / 刷入已去除 verity 的 vbmeta）。

| **1** | **修复卡死**：清理 /data 至剩余 > 20%，或直接恢复出厂设置 | 低（会清数据，已备份） | 否 | 30 分钟 |
| **2** | **解锁 Bootloader**：Kirin-Tool + SWTP（失败则转硬件测试点） | **中高**（变砖/状态不可逆/清数据） | 否 | 1-3 小时 |

### ⚠️ 必须先确认的风险点

1. **数据大概率全清**：解锁命令本身是否强制擦除没有 100% 保证，但三条证据都指向“会清”：(a) XDA 指南明确要求解锁后 `format userdata`；(b) 本机是 FBE 加密，密钥由 Keymaster 封装且与引导状态绑定，green → orange 后大概率拒绝解密，系统会强制恢复出厂；(c) dm-verity 处于 enforcing。**按“一定会清空”准备，先备份。**
2. **解锁状态不可逆 —— 更正上次的说法**：“硬件熔断 eFuse”这个说法我上次讲过头了。公开资料（bootloader-unlock-wall-of-shame 等）显示华为的锁状态存放在 OEMINFO/NVME 安全区 + 安全引擎（hisee/hhee/teeos）里，走的是分区 + RSA 签名（RDLOCK）路线，**没有证据**表明麒麟 970 解锁会烧断硅片熔丝（那是三星 KNOX 的机制）。但“不可逆”是真的：回锁也恢复不成“从未解锁”，`fastboot oem check-rootinfo` 会留下带时间戳的永久 RISK 记录。另外本机是 2017 年机型，**保修早已过期**，这条风险对你无实际影响。
3. **变砖风险**：Kirin 970 解锁存在“能解锁但系统异常”的报告（如托盘无法下拉），需要补刷 kernel 甚至重刷全量固件。**本机是唯一一台机器的话，请谨慎**。
4. **需要拆机**：如果 SWTP 失败，就必须拆后盖短接测试点（后盖为玻璃，有碎裂风险）。
5. **固件获取**：SWTP 需要与机型/版本匹配的官方 update.app，如果找不到 ≥ 9.1.0.337 的 C00 固件，SWTP 走不通，只能拆机。

### 建议

- **如果首要目标是“让手机不卡”**：先做阶段 0 + 1，大概率就好了，不需要冒险解锁。
- **如果确定要“废物利用”**（刷模块、当服务器、跑脚本）：再走阶段 2 + 3，推荐 **方案 A（Kirin-Tool，免费）**，付费方案 C（HCU + DC Phoenix $19）作为保底。

## 三、技术攻关过程

### 3.1 核心难点
华为 EMUI 9 的 USB 更新模式（DLOAD）有**版本检查**，拒绝低于设备版本的固件包。

### 3.2 关键突破

**① 逆向出完整 CRC 机制**
- 算法：**CRC-16/X-25**，按原始数据逐 **32K 块**计算（最后一块不补齐）
- `CRC.img` 结构：uint16 LE 数组，每 32K 块一项
  ```
  idx0 = CURVER
  idx1 = VERLIST
  idx2 = PACKAGE_TYPE
  idx3.. = HISIUFS_GPT 及其后所有镜像
  ```
- **`CRC.img` 自身不在表内，但有 SHA256RSA 签名保护 → 不可修改**

**② 挖出设备端版本检查逻辑**（反编译 update-binary）
```
check_emui_version
the current emui version does not exist in the list, not allow to update.
line length of list greater than emui version length, not allow to update.
This is not a downgrade package, don't need to check emui version.
version list not be checked, maybe there is no versionlist or checked fail!
```

**③ 实现真实 CRC 碰撞**
用 GF(2) 线性代数求解，构造出**内容全改但 CRC 值不变**的 VERLIST：
- 目标 CRC：`0xad14`（原值）
- 方法：在末尾留 16 字节"牺牲区"，用高斯消元求解使 CRC 命中目标
- **结果：CRC.img 无需修改，签名保护绕过**

**④ 发现版本标识真相**
对比 9.1.0.337 与 8.0.0.199 的 VERLIST：
```
9.1.0.337 包:  BKL-EMUI90          ← 设备实际比对的「EMUI 版本标识」
              BKL-EMUI9.0.0.150_Xloader
              BKLL00B000
              BKLC00B000
              BKL-AL00 8.0.0.106(C00)
              ...
8.0.0.199 包:  （无 BKL-EMUI90 这两行）→ 版本检查失败
```

## 七、Magisk 环境修复详解（本次独有）

### 问题
格式化数据分区后 `/data/adb/magisk/` 被清空，导致：
```
E Magisk : * Magisk environment setup incomplete, abort
```
Magisk Manager 反复提示"需要修复运行环境"，但它的修复流程（下载+打补丁+刷机）在这台华为上无效，形成死循环。

### 根因
Magisk Manager 7.5.1 的 APK **不打包 Magisk 二进制**（只有 2 MB 界面资源），需要联网下载 `Magisk-vXX.zip`。而修复流程走的是"打补丁刷 boot 分区"，这台设备**没有 boot 分区**，所以永远失败。

### 解决
从官方 `Magisk-v20.1.zip` 手工组装 `/data/adb/magisk/`：

| 文件 | 来源 | 大小 |
|---|---|---|
| `magisk` | `magiskinit64 -x magisk magisk` 提取 | 149848 |
| `magiskboot` | `arm/magiskboot` | 303088 |
| `magiskinit` | `arm/magiskinit` | 365892 |
| `magiskinit64` | `arm/magiskinit64` | 345412 |
| `busybox` | 从 `update-binary` 偏移 1604608 处 dd 出（ARM 版） | 1070668 |
| `util_functions.sh` / `boot_patch.sh` / `addon.d.sh` / `magisk.apk` | `common/` | — |
| `chromeos/` | `chromeos/` | — |

**关键发现**：`update-binary` 是自解压脚本，脚本占前 1024 字节，后面追加多个 busybox：
- 偏移 1024，长度 1603584 → **x86 版**
- 偏移 1604608，长度 1070668 → **ARM 版** ← 我们要的

## 1. 问题一：rootinfo 安全账本到底能不能变更？

### 1.1 先看实测结构（你手机的真实输出）

```
fastboot oem check-rootinfo
  status        : SAFE
  version       : v2.0
  current status: SAFE
  old status    : SAFE
  change_time   : 0

  item:usb-debug,     category:potential, credible:Y, status:RISK, old status:RISK, time:1792604984
  item:pha,           category:potential, credible:Y, status:RISK, old status:RISK, time:1760812336
  item:verifyboot,    category:integrity, credible:N, status:SAFE, old status:SAFE, time:0
  item:verity-enable, category:integrity, credible:Y, status:SAFE, old status:SAFE, time:0
  item:key-files,     category:integrity, credible:Y, status:SAFE, old status:SAFE, time:0
```

### 1.2 三个关键解读

**① 项目分两类，性质完全不同**

| 类别 | 项目 | 含义 | 当前值 |
|---|---|---|---|
| `potential`（潜在风险） | usb-debug、pha | 行为类风险，**不影响总状态** | 已 RISK |
| `integrity`（完整性） | verifyboot、verity-enable、key-files | 设备完整性，**决定总状态** | 全 SAFE |

注意：你现在 USB 调试开着，`usb-debug` 已经是 RISK 了（时间戳 1792604984 ≈ 2026-10-21，就是你开调试那天），但总状态仍是 SAFE。**说明 potential 类不参与总判定。**

**② integrity 类不是日志，是「开机实时测量」**

这三项的名字已经说明了它们的来源：
- `verifyboot` = 验证启动状态（对应 ro.boot.verifiedbootstate）
- `verity-enable` = dm-verity 是否开启（对应 ro.boot.veritymode）
- `key-files` = 关键文件签名校验

这些值由 **bootloader 在每次启动时从设备实际状态重新测量**，而不是从一份历史记录里读。

**推论：解锁后 verifiedbootstate 从 green 变 orange，这三项必然翻成 RISK。即使你有办法把记录擦掉，下次开机立刻重新测出来、重新记上。**

**③ 数据由引导器持有，不在 Android 层**

`check-rootinfo` 是 fastboot 命令 —— 回答你的是引导器，不是 Android。数据住在引导器能访问的安全存储里（结合社区资料，位置是 OEMINFO/NVME 分区 + 安全引擎 hisee/hhee/teeos）。

### 1.3 全网检索到的证据

| 来源 | 内容 | 可信度 |
|---|---|---|
| bootloader-unlock-wall-of-shame（GitHub 社区权威汇总） | 华为锁状态存于 **OEMINFO/NVME 分区**；麒麟 970 的解锁码是 **RSA 签名（RDLOCK）**，非明文；HCU-client 因持有 RSA 私钥而收费 | 高 |
| PotatoNV 官方手册 | FBLOCK 存于 **NVME 分区**，可用 nve 命令改写（仅限麒麟 960 及以下） | 高 |
| HalabTech 华为 fastboot 命令集 | `fastboot oem check-rootinfo` 在旧机型返回 `old_stat / now_stat / change_time`；`fastboot oem relock` 返回 `remote: stat not match`（**回锁经常直接失败**） | 高 |
| CSDN 问答（社区回答） | 「华为已明确停止支持重新锁 BL……一旦解锁，BootROM 会永久标记设备为已解锁状态，无法通过任何公开工具、命令或华为官方服务恢复」 | 中（社区回答，可能含 AI 生成内容） |
| 华为官方社区公告 | 2018-07-25 停止发放解锁码；官方措辞为解锁后不可恢复 | 高（但页面为 JS 渲染，未能抓到全文） |
| leadroyal.cn 同机型实测 | 「解锁状态不会轻易丢失，**当且仅当使用 HiSuite 升级降级时，码会被刷新掉**」 | 高（同机型同版本实测） |

**检索结论：全网没有任何一个工具、教程或成功案例声称能把 rootinfo 重置回 SAFE。**

### 1.4 分层结论（这是我能给你的最诚实的答案）

| 命题 | 判定 |
|---|---|
| integrity 三项会被开机实时重测，擦记录也没用 | ✅ **确定**（由机制推导） |
| 解锁后 integrity 三项会翻成 RISK、总状态变 RISK | ✅ **几乎确定** |
| `fastboot oem relock` 在华为上大概率失败或无法恢复原状 | ✅ **确定**（多个来源一致） |
| 回锁 + 刷回全官方固件后，历史记录会被清零 | ⚠️ **高度可能不会**，但无公开案例可证 |
| 「物理上 100% 绝对不可能变更」 | ❌ **我不能替华为保证**。理论上 HCU/ChimeraTool 能写 oeminfo，也许能改记录；但（a）没有任何公开工具提供此功能，（b）改完开机又被重测覆盖，（c）改它本身就得先解锁 |

**给你的实操建议：把 rootinfo 当作「一次性、不可逆」来对待。** 不是因为它 100% 物理不可逆，而是因为**没有任何已知的可行路径让它恢复**，赌它可逆没有任何收益。

#### 2.3 SWTP 进入 COM 1.0（不拆机）

1. 装 HiSuite（拿 USB 更新模式驱动）
2. 解压固件包，找到并解压 `update_sd_base`，取出里面的 `update.app`
3. 打开 Kirin-Tool → CPU model 选 **970** → VCOM operations 标签 → 勾选 `software testpoint`
4. 在 `Base UPDATE.APP` 输入框右侧点浏览，选中上一步的 `update.app`
5. **手机关机** → 同时按住 **音量加 + 音量减** → 插 USB → 等它进 recovery
6. 手机上选 `Update mode` → `USB update mode`
7. Kirin-Tool 点 `Enter`
8. **成功标志**：手机显示 `update success` 后黑屏 → 已进入 COM 1.0
9. **失败标志**：显示 `update failed` → 说明安全补丁太新或固件不对 → 转 2.4

#### 2.4 硬件测试点（SWTP 失败时的兜底）

参考资源：
- onfix.cn/course/7444 —— 荣耀V10 拆机短接图示
- donghairom.com/thread-5243-1-1.html —— BKL-AL00/AL20/TL10 进 USB1.0 精准点位图
- YouTube: Honor V10 (BKL-AL20) Test Point | Dead Boot Repair | EDL 9008

操作要点：
1. 关机；热风枪/吹风机均匀加热后盖 2-3 分钟
2. 塑料卡片沿边划开玻璃后盖（**碎裂风险真实存在**）
3. **断开电池排线**（测试点手册强制要求）
4. 按点位图找到测试点，用**导电镊子**短接到地（金属屏蔽罩）
5. **保持短接**的同时插 USB，保持约 3 秒
6. 设备管理器出现 `USB SER` 或 `HUAWEI USB COM 1.0` 即成功
7. 若显示 `USB SER`，用 COM 1 DRIVER 里的 `hw_quser.inf` 手动装驱动

#### 2.5 执行解锁

1. Kirin-Tool → CPU = 970 → `VCOM operations` → 点 **Unlock**（K980 才会弹窗，970 直接过）
2. 切到 `Security tools` 标签 → 点 **Unlock** → 提示时**按一下手机电源键**
3. 完成后验证：

```
fastboot oem get-bootinfo        → 应显示 unlocked
fastboot oem check-rootinfo      → 观察 integrity 三项是否翻 RISK
fastboot oem get-product-model   → 确认 BKL-AL20
```

4. **解锁后立刻格式化 userdata**（`fastboot erase userdata` 或让系统自行恢复出厂）

#### 2.6 阶段 2 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 数据全清 | 高 | 阶段 0 已备份 |
| SWTP 失败 | 中 | 转 2.4 硬件测试点 |
| 拆机碎屏 | 中 | 找有经验的人；备好替换后盖 |
| 解锁后系统异常（如托盘下拉打不开） | 中 | 按 PotatoNV 讨论 #155：补刷 kernel；或重刷全量固件 |
| 变砖 | 低-中 | 见 3.8 救砖预案 |
| rootinfo 永久变 RISK | 几乎必然 | 已接受（见第 1 章） |

### 3.6 阶段 3：Root（Magisk 修补 recovery_ramdisk）

**依据**：leadroyal 同机型同版本实测路径 + CSDN 荣耀 V9 免 TWRP 教程交叉验证。

1. 用 HuaweiUpdateExtractor 从 `update.app` 提取 **`recovery_ramdisk.img`**（原厂镜像）
2. 手机装 Magisk App（建议 **v23.0**，EMUI 9 兼容性最好；v24+ 对 legacy recovery 模式支持有变化）
3. Magisk 设置里**打开 Recovery Mode**（因为本机检测为 Ramdisk = No）
4. 选择「安装 → 修补一个文件」→ 选 `recovery_ramdisk.img` → 得到 `magisk_patched-xxxxx.img`
5. 把修补后的镜像拷到电脑：

```
fastboot flash recovery_ramdisk magisk_patched-xxxxx.img
```

6. **开机方式（关键）**：

| 按键组合 | 进入 | 有无 Root |
|---|---|---|
| 电源键 | 正常系统 | ❌ 无 Root |
| **音量加 + 电源键** | **recovery（Magisk 系统）** | ✅ **有 Root** |
| 音量减 + 电源键 | fastboot | — |
| 电源键 + 音量加（3 秒） | eRecovery（救砖） | — |
| 音量加 + 音量减 + 电源键 | 三键强刷 | — |

7. 验证：进 Magisk App 看是否显示已安装版本；`adb shell su -c id` 应返回 uid=0

**期望值管理（来自同机型实测）**：
- ❌ EdXposed 会导致启动卡死，**不要装**
- ❌ frida 不可用（疑似 SELinux 问题）
- ⚠️ 部分 Magisk 模块会报「需要 Magisk 20+」而装不上
- ⚠️ TWRP 无法解密 data，只能用来删模块文件
- ✅ 太极（Magisk 版）实测正常

### 3.9 决策门（Go / No-Go）

**决策门 A（阶段 1 之后）**：手机还卡吗？

**决策门 C（阶段 3 之后）**：

## 3.11 【2026-10-22 04:22 更新】rootinfo 完整结构实测（重要更正）

之前只抓了前 20 行，实际完整输出有 **3 个类别、19 个项目**：

| 类别 | 项目 | 当前状态 |
|---|---|---|
| `potential` | usb-debug ⚠️RISK (2026-10-21)、pha ⚠️RISK (2025-10-18) | 不影响总状态 |
| `integrity` | verifyboot、verity-enable、key-files、verified-state、eima | 全 SAFE |
| `root` | root-prop、**fblock**、**userlock**、check-su、sysrw、setids、kcode、kcode-syscall、se-enforcing、se-hook、**root-procs ⚠️RISK (2024-12-06)** | 其余全 SAFE |

**三个关键结论：**

1. **`userlock` 就是 bootloader 用户锁状态项。** 现在 SAFE（=锁定）。**解锁后它必然变 RISK，并写入时间戳，`old status: SAFE` 作为历史永久保留。** 这是"不可逆"最直接的证据。
2. **`root-procs` 已经是 RISK，时间戳 1733499038 ≈ 2024-12-06** —— 这台手机在 2024 年 12 月就已经被引导器记录过"检测到 root 进程"。**它本来就不是"完全干净"的状态了。**
3. **总状态只由 `integrity` 类决定**：即使 potential 和 root 类里已有 3 项 RISK，`current status` 仍是 SAFE。

基线快照已存：`phone_backup/baseline_before_unlock.txt`（解锁后可对比，看哪些项翻转）。

# 第一部分 · 原理篇

## 1.1 Magisk 到底是什么

Magisk 不是"一个 App"，而是**一套系统级改造框架**，由 4 个部分组成：

| 组件 | 位置 | 作用 |
|---|---|---|
| **magiskinit** | 打包进 recovery_ramdisk，启动时替换 \`/init\` | 最早期接管启动，挂载 magisk 分区 |
| **magiskd** | 常驻守护进程（root 身份） | 管理 root 授权、模块、Hide |
| **magisk** | 命令行工具 | 你敲的 \`magisk\` 命令 |
| **Magisk Manager** | 普通 App | 图形界面，操作上面三个 |

## 1.2 核心思想：Systemless（无系统修改）

**传统 Root（SuperSU 时代）的问题**：
\`\`\`
直接往 /system 里塞 su 二进制 → 系统分区被改 → OTA 更新失败 → 变砖
\`\`\`

**Magisk 的解法**：
\`\`\`
/system 分区一个字节都不动
    ↓
启动时用 overlayfs / bind mount 把模块文件"叠"到 /system 上
    ↓
系统以为自己看到了修改后的文件，实际磁盘上什么都没变
\`\`\`

**好处**：
- ✅ 随时可以完全卸载，系统恢复原样
- ✅ OTA 更新不会因为系统被改而失败
- ✅ 出问题拔掉模块就好，不用重刷系统

## 1.3 Magisk 启动流程（你这台机器的真实日志）

\`\`\`
① BootROM
     ↓  加载 XLOADER（我们恢复过的那个）
② XLOADER
     ↓  加载 FASTBOOT / UCE
③ fastboot → 引导内核
     ↓  读 recovery_ramdisk 里的 magiskinit（替换了原厂 /init）
④ magiskinit
     ↓  解析内核 cmdline，判断是正常启动还是 recovery
     ↓  挂载 /data，读取 /data/adb/magisk/
⑤ magiskd 启动
     ↓
   ┌─ post-fs-data 阶段（阻塞式，其他进程会等）
   │   * Initializing Magisk environment
   │   * Mounting mirrors          ← 挂载 /system /vendor /product 镜像
   │   * Setting up internal busybox
   │   * Running post-fs-data.d scripts
   │   * Running module post-fs-data scripts
   │   * Loading modules            ← 把模块文件 overlay 到系统
   │   * Starting MagiskHide        ← 启动隐藏守护
   └─
     ↓

   │   * Running service.d scripts
   │   * Running module service scripts
   └─
     ↓

## 1.4 华为 EMUI 的特殊之处（非常重要）

### 普通安卓 vs 华为

| | 普通安卓 | 华为 EMUI 9 |
|---|---|---|
| boot 分区 | 有（kernel + ramdisk） | **没有** |
| recovery 分区 | 有 | **没有独立 recovery 分区** |
| ramdisk 在哪 | boot 分区里 | **recovery_ramdisk 分区** |
| Magisk 刷哪 | boot | **recovery_ramdisk** |

### 这意味着什么

\`\`\`
普通安卓:  电源键 → boot 分区 → 系统（带 Magisk）
           音量+ + 电源 → recovery 分区 → recovery

华为EMUI9: 电源键 → kernel + recovery_ramdisk → 系统（带 Magisk）
           音量+ + 电源 → kernel + recovery_ramdisk → recovery 模式
\`\`\`

**你的实测结果：正常开机（电源键）就带 Root** ✅ —— 所以不用担心"要不要按音量+"的问题。

### 华为的「双锁」机制

华为 Bootloader 有**两层锁**（这是它比其他厂商难解的原因）：

| 锁 | 存储位置 | 作用 | 解锁后 |
|---|---|---|---|
| **FBlock** | rdmode NV 项 | 控制能否刷写分区 | \`unlocked\` |
| **USER Lock** | oeminfo bootinfo NV 项 | 控制能否启动非签名镜像 | \`unlocked\` |

**你现在的状态**（\`fastboot oem check-rootinfo\`）：
\`\`\`
item: fblock,   status: unlocked, credible: Y
item: userlock, status: unlocked, credible: Y
status: RISK
\`\`\`

### 模块目录结构
\`\`\`

  post-fs-data.sh     早期启动脚本
  service.sh          后期启动脚本

## 3.3 MagiskHide（隐藏 Root）

### 为什么需要
银行 App、支付宝、微信支付、游戏反作弊会检测 root，检测到就拒绝运行。

### 原理
\`\`\`
MagiskHide 会对勾选的 App 做三件事：
① 卸载 /sbin 下的 magisk 相关挂载点（该 App 看不到）
② 修改该进程的 SELinux 上下文（伪装成普通 App）
③ 隐藏敏感系统属性（ro.debuggable、ro.secure 等）
\`\`\`

### 配置步骤
\`\`\`
① Magisk Manager → 设置 → 打开 MagiskHide 开关
② 侧边栏 → MagiskHide
③ 勾选需要隐藏的 App
④ 重启手机
\`\`\`

### 验证是否生效
\`\`\`bash
# 查看当前 hide 列表
adb shell su -c 'magiskhide ls'

# 测试某个 App
adb shell su -c 'magiskhide test com.example.app'
\`\`\`

### 推荐的隐藏对象
\`\`\`
支付宝          com.eg.android.AlipayGphone
微信            com.tencent.mm
云闪付          com.unionpay
各大银行 App
三国志战略版    com.aligames.sgzzlb.huawei    ← 你装的那个游戏
Google Play 服务 com.google.android.gms
\`\`\`

## 3.4 系统级 hosts（去广告基础）

### 原理
\`\`\`
Android 的 DNS 解析会先查 /etc/hosts
把广告域名的 IP 改成 0.0.0.0 → 广告加载失败
但 /system 是只读的 → Magisk 用 bind mount 把可写的 hosts 叠上去
\`\`\`

### 开启步骤
\`\`\`
Magisk Manager → 设置 → 打开「系统级 hosts」
\`\`\`

### 验证
\`\`\`bash
adb shell su -c 'mount | grep hosts'
# 应该看到 /data/adb/modules/hosts/system/etc/hosts 挂载到 /system/etc/hosts
\`\`\`

见第五部分第 21 项。

## 3.7 「保持 AVB 2.0 / 保持强制加密」到底要不要开

| 设置 | 开 | 关 |
|---|---|---|
| **保持 AVB 2.0/dm-verity** | 系统分区保持完整性校验 | 关闭校验（某些模块需要） |
| **保持强制加密** | /data 保持加密 | 关闭加密（性能略好，但安全性下降） |

**你的建议**：**两个都保持开启**。
- 你是日常使用，安全性更重要
- 关闭加密后如果忘记密码，数据完全暴露
- 而且你的卡死问题已经通过清理存储解决了，不需要靠关加密提升性能

## 4.2 magiskboot（镜像工具）

\`\`\`bash

# 附录 C · 三个高价值实操（带完整命令）

## C.1 安装系统级 CA 证书（抓包必备）

Android 7 以后，App 默认**不信任用户安装的证书**，所以抓 HTTPS 必须把证书装到系统区。

\`\`\`bash
# 1. 准备证书（从 NetCapture/Charles/Fiddler 导出 .pem 格式）
#    文件名必须是 <证书哈希>.0 的格式

# 2. 计算哈希（在电脑上，需要 openssl）
#    openssl x509 -inform PEM -subject_hash_old -in ca.pem | head -1
#    假设得到 9a5ba575

# 3. 改名并推送
#    mv ca.pem 9a5ba575.0
adb push 9a5ba575.0 /sdcard/

# 4. 挂载 /system 为可写并复制
adb shell su -c 'mount -o rw,remount /system'
adb shell su -c 'cp /sdcard/9a5ba575.0 /system/etc/security/cacerts/'
adb shell su -c 'chmod 644 /system/etc/security/cacerts/9a5ba575.0'
adb shell su -c 'chown root:root /system/etc/security/cacerts/9a5ba575.0'

# 5. 重启
adb reboot

# 6. 验证
adb shell su -c 'ls -la /system/etc/security/cacerts/ | grep 9a5ba575'
\`\`\`

**注意**：这是唯一需要**真的写 /system** 的操作（不能 systemless，因为证书要在系统启动早期可用）。改完记得备份。

## 七、踩到的坑（记录备用）

1. **华为 EMUI 上 `pm` 不能用 root 跑**：`su -c 'pm list packages'` 会报
   `cmd: Failure calling service package: Failed transaction (2147483646)`。
   必须以 **shell（uid 2000）** 身份执行 `pm`。这是本机最容易踩的坑。
2. **toybox 的 `dd` 不认 `bs=1M`**，必须写 `bs=1048576`。
3. **Magisk 20.1 没有 `magisk --install-module`**，装模块只能手动跑 zip 里的
   `META-INF/com/google/android/update-binary`，并设好
   `BOOTMODE=true / MAGISK_VER=20.1 / MAGISK_VER_CODE=20100 / ARCH=arm64 / IS64BIT=true / API=28`。
4. **USB 会间歇性掉线**，`adb install` 用流式写入容易失败；改用
   `adb push` + `pm install` 更稳。
5. **不要用 Magisk Manager 的「安装/修复运行环境」**——本机没有独立 boot 分区，
   会把 recovery_ramdisk 搞坏。

## 3. 拼图二：代理抓包（跨网段也能用）

### 3.1 关键技巧：`adb reverse`

你这台电脑在 `192.168.9.x`，手机在 `192.168.5.x`，**不在同一个局域网**，手机直连不到电脑的代理端口。

**解决办法：用 `adb reverse` 把电脑的端口"反向"映射到手机的 127.0.0.1。**

```powershell
# 电脑上执行：把电脑的 8080 映射成手机上的 127.0.0.1:8080
adb reverse tcp:8080 tcp:8080
adb reverse --list        # 确认：(reverse) tcp:8080 tcp:8080

# 让手机全局走这个代理
adb shell settings put global http_proxy 127.0.0.1:8080
```

取消代理：
```powershell
adb shell settings put global http_proxy :0
adb reverse --remove-all
```

### 3.2 用 mitmproxy（命令行，最方便）

```powershell
# 电脑上
pip install mitmproxy          # 或者用 py -m pip install mitmproxy
mitmweb --listen-port 8080     # 会打开浏览器界面 http://127.0.0.1:8081
```

### 3.3 用 Charles / Fiddler

1. 电脑上设置监听端口 **8080**，勾选 "Allow remote clients"
2. 按 3.1 建立 `adb reverse` 并设置手机代理
3. 证书用第 2 节的方法装进系统区
4. 手机上打开目标 App，电脑上就能看到明文 HTTPS

### 4.2 完整流程

```powershell

    // 1. 干掉 OkHttp 的 CertificatePinner
    try {
        var CertificatePinner = Java.use('okhttp3.CertificatePinner');
        CertificatePinner.check.overload('java.lang.String', 'java.util.List').implementation = function (a, b) {
            console.log('[+] OkHttp pinning bypassed: ' + a);
            return;
        };
    } catch (e) { console.log('[-] no OkHttp'); }

    // 2. 干掉 X509TrustManager 的所有校验
    try {
        var X509TrustManager = Java.use('javax.net.ssl.X509TrustManager');
        var SSLContext = Java.use('javax.net.ssl.SSLContext');
        var TrustManager = Java.registerClass({
            name: 'com.dsh.TrustAll',
            implements: [X509TrustManager],
            methods: {
                checkClientTrusted: function (chain, authType) {},
                checkServerTrusted: function (chain, authType) {},
                getAcceptedIssuers: function () { return []; }
            }
        });
        var TrustManagers = [TrustManager.$new()];
        var SSLContext_init = SSLContext.init.overload(
            '[Ljavax.net.ssl.KeyManager;', '[Ljavax.net.ssl.TrustManager;', 'java.security.SecureRandom');
        SSLContext_init.implementation = function (km, tm, sr) {
            console.log('[+] SSLContext.init hooked');
            SSLContext_init.call(this, km, TrustManagers, sr);
        };
    } catch (e) { console.log('[-] TrustManager hook failed: ' + e); }

    // 3. 打印所有网络请求（可选）
    try {
        var URL = Java.use('java.net.URL');
        URL.openConnection.overload().implementation = function () {
            console.log('[URL] ' + this.toString());
            return this.openConnection();
        };
    } catch (e) {}
});
```

## 6. 拼图五：EdXposed（不重打包就能 Hook）

**优点**：不用改 APK、不用重装，装上模块勾选目标 App 重启即可。
**缺点**：只能用在已 Root 且有 Xposed 框架的机器上（本机已就绪）。

### 6.1 装模块

## 7. 拼图六：tcpdump 被动抓包（抓不走代理的流量）

代理抓包有个盲区：**不遵守系统代理的 App**（很多 App 会绕过）。这时候用 tcpdump 在网卡层抓。

### 7.1 抓包

```powershell
# 电脑上执行，抓包存到手机 /sdcard
adb shell su -c 'LD_LIBRARY_PATH=/data/data/com.termux/files/usr/lib /data/data/com.termux/files/usr/bin/tcpdump -i any -s 0 -w /sdcard/cap.pcap'

# 抓到够了按 Ctrl+C，然后拉回电脑
adb pull /sdcard/cap.pcap
# 用 Wireshark 打开
```

### 7.2 常用参数

| 参数 | 含义 |
|---|---|
| `-i any` | 所有网卡（WiFi + 移动网络 + 回环） |
| `-s 0` | 抓完整包（不截断） |
| `-c 100` | 抓 100 个包就停 |
| `-w file.pcap` | 写入文件 |
| `-r file.pcap` | 读取文件 |
| `-nn` | 不解析主机名和端口名（更快） |
| `port 443` | 只抓 HTTPS |
| `host 1.2.3.4` | 只抓某个 IP |

### 7.3 在手机 Termux 里直接抓

```bash
# Termux 里（需要 su，Magisk 会弹窗，点允许）
su -c 'LD_LIBRARY_PATH=$PREFIX/lib $PREFIX/bin/tcpdump -i any -w /sdcard/cap.pcap'
```

### 7.4 更省事的替代：PCAPdroid

**PCAPdroid** 是一个 App，用 VPN 方式接管流量，**免 root**：
- 能抓到所有 App 的流量（包括不走代理的）
- 可以直接导出 pcap 给 Wireshark
- 也内置了 mitm 解密功能
- 缺点：VPN 模式和某些 App 的 VPN 检测冲突

### 场景 B：有 SSL Pinning 的 App

## 9. 常见问题

| 问题 | 解决 |
|---|---|
| `frida-ps -U` 没反应/卡住 | 本机没有可用的 frida-server。用 Gadget 路线，或先确认 Gadget 已随 App 启动 |
| `objection patchapk` 报找不到 adb / apktool | 按第 1 节把路径加进 PATH |
| 补丁版 App 装不上（签名冲突） | 先 `adb uninstall <包名>`；数据会丢，先备份 |
| 装了证书 App 还是报证书错误 | 该 App 有 SSL Pinning → 走场景 B |
| App 完全不发请求 | 它可能绕过了系统代理 → 走场景 C |
| 手机和电脑不同网段 | 用 `adb reverse`（第 3.1 节） |
| `setenforce 0` 报 Invalid argument | 华为锁死，正常现象，别折腾 |
| `pm` 命令报 `Failed transaction` | 华为限制：**不要用 `su -c` 跑 `pm`**，直接用 `adb shell pm ...` |
| Termux 里 `su` 弹窗 | 在 Magisk Manager → 超级用户里给 Termux 授权 |

## 一、重大突破：找到了完整的技术原理（不拆机路径存在！）

### 1.1 关键仓库：kasnria001/huawei-usbdload-tool

https://github.com/kasnria001/huawei-usbdload-tool

**注意：kasnria001 正是 Kirin-Tool 作者在 README 里致谢的人（提供解密 xloader）。** 这个仓库公开了完整原理：

**核心原理（原文要点）：**

1. 老华为设备有一个 **USB DLOAD MODE（也叫 5% MODE）**
2. 进入方式：**Vol+ + Vol- + Power 三键**（或在 recovery 里选）—— **不需要拆机！**
3. 这个模式可以接收 `UPDATE.APP` 包，把镜像写进指定分区
4. UPDATE.APP 的第一个镜像是 `SHA256RSA.img`（签名），第二个是 `CRC.img`（每块 CRC）
5. **关键漏洞：EMUI9 及以下，update-binary 只校验镜像块的 CRC，不校验签名 → 可以做 CRC 碰撞**
6. 以 0x8000 为一块，把 `PACKAGE_TYPE` 改成 `OFFLINE_UPDATE` 即可绕过在线校验
7. 版本检查（BASE_VER/BASE_VERLIST）绕过法：**连发两个包不重启，第一个用更高版本**
8. **EMUI 9.1 起华为给关键分区加了 hash 校验，但是——PRELOADER 和 XLOADER 是同一个物理分区，PRELOADER 不属于关键分区。只要把 XLOADER 的镜像头里的分区名改成 PRELOADER，就能继续用 CRC 碰撞。**
9. **这样就能把手机踢进 COM 1.0 模式**，之后用 BootROM/xloader 漏洞解锁

**另有 nvme_editor.py**：老华为把 FBLOCK 和解锁码（USRKEY）的 SHA256 存在 nvme 分区，**可以直接改这两个值**（需同步更新每项的 CRC）。

### 1.2 我们的机器为什么适用

| 条件 | 本机 | 是否满足 |
|---|---|---|
| EMUI 版本 | **EMUI 9.1.0.337** | ✅ 在「EMUI9 及以下」范围内 |
| XLOADER→PRELOADER 改名绕过 | 适用 EMUI 9.1 | ✅ |
| 进入 USB DLOAD MODE | 三键组合 | ✅ **不需要拆机** |

**结论：存在一条不拆机的路径。** 但必须有一份 BKL-AL20 的 `UPDATE.APP`。

# 14 · 踩坑记录（完整清单）

## 一、华为/荣耀 EMUI 专属坑（最要命）

### 1. 华为锁死了 SELinux 策略写接口 → frida-server 彻底用不了

```
frida-server -v
→ Unable to save SELinux policy to the kernel: Out of memory

# 换 Magisk 自己的工具，同样失败（证明不是 frida 的问题）
magiskpolicy --live "allow magisk magisk_file file read"
→ write failed with 12: Out of memory

→ setenforce: Couldn't set enforcing status to '0': Invalid argument
```

**根因**：`/sys/fs/selinux/load` 被锁，任何写入返回 `ENOMEM(12)`。
**影响**：frida-server、setenforce、magiskpolicy --live、以及所有"运行期改 SELinux"的工具全部失效。
**解法**：用 **Frida Gadget**（把 gadget 打进 APK，不碰 SELinux）。见 [08-Frida与抓包完全教程](08-Frida与抓包完全教程.md)。
**参考**：[frida#1039](https://github.com/frida/frida/issues/1039) · [frida#1023](https://github.com/frida/frida/issues/1023)

> 注意：**Magisk 模块的 `sepolicy.rule` 在开机早期是能生效的**（Riru/EdXposed 就靠它），
> 但运行期再写就一律失败。

### 2. `pm` / `am` 不能用 root 跑

```bash
adb shell su -c 'pm list packages'
→ cmd: Failure calling service package: Failed transaction (2147483646)

adb shell su -c 'am startservice ...'
→ cmd: Failure calling service activity: Failed transaction (2147483646)
```

**解法**：`pm` / `am` / `settings` 一律用 **shell 身份**（直接 `adb shell pm ...`）。
**连带影响**：
- 黑域（Blackhole）这类靠 `pm disable` 的工具，root 模式会失效
- Magisk 的 `service.d` 脚本以 root 运行，**不能在里面调 `am`**，所以"开机自动启动某 App"这条路走不通
- 加 su 授权别用 `magisk --sqlite`，走 Magisk Manager 界面

### 3. `magisk --sqlite` 带子查询会把 magiskd 搞崩

```bash
adb shell su -c 'magisk --sqlite "REPLACE INTO policies (uid,policy,until,logging,notification,package_name) VALUES (10123,2,0,1,1,(select package_name from policies where uid=10123))"'
→ read (4 != 0) failed with 0: Success
# 之后 magiskd 死亡，su 全部失效 → "No daemon is currently running!"
```

**恢复**：重启手机，magiskd 会自动重启（实测有效）。
**教训**：别手搓 SQL，用 Magisk Manager 界面。

### 4. 本机没有独立 `boot` 分区

分区表里只有 `kernel` + `recovery_ramdisk`，**没有 `boot`**。
所以：
- Magisk 只能装在 `recovery_ramdisk`
- **绝对不要用 Magisk Manager 的「安装 / 修复运行环境」** —— 它会去找 boot 分区，把 recovery_ramdisk 搞坏
- 升级 Magisk 到 24+ 的风险极高（刷坏就失去 root，而且本机**没有可用的 fastboot 兜底**）

### 5. eRecovery 的「下载最新版本并恢复」已失效

华为服务器不再为 EOL 机型提供服务，点了直接「获取失败」。
「恢复出厂设置」也不格式化，只是重启。

### 6. 工程菜单「存储卡升级」不工作

SD 卡里 `dload/UPDATE.APP` 放好了、手机也认得到，但点了转 1 秒就没反应。

### 7. EMUI 默认禁止第三方 App 自启动

Termux:Boot 装了也没用，必须手动放行：
**设置 → 应用 → 应用启动管理 → 找到目标 App → 关掉"自动管理" → 三个开关全开**

### 8. 系统分区是只读 erofs，`mount -o rw,remount` 没用

```
/sbin/.magisk/block/system_root on /system type erofs (ro,seclabel,...)
```
**正确做法**：用 Magisk 模块挂载（module 里放 `system/...`），不要试图 remount。
改 CA 证书、改 hosts、替换系统文件都走这条路。

## 二、Magisk 20.1 专属坑

### 9. 20.1 没有 `magisk --install-module`

`magisk --list` 只有 `su` / `resetprop` / `magiskhide` 三个 applet。
**解法**：手动跑模块 zip 里的 `update-binary`：

```sh
export BOOTMODE=true MAGISK_VER=20.1 MAGISK_VER_CODE=20100
export ARCH=arm64 IS64BIT=true API=28
export TMPDIR=/dev/tmp MAGISKTMP=/sbin/.magisk NVBASE=/data/adb
sh META-INF/com/google/android/update-binary 3 1 "$ZIP"
```

已封装：[scripts/install-module.sh](../scripts/install-module.sh)

### 10. 20.1 的 `util_functions.sh` 没有 `install_module()`

Magisk **20.4+** 的模块安装器（例如 EdXposed 的）会这样写：
```sh
. /data/adb/magisk/util_functions.sh
[ $MAGISK_VER_CODE -lt 20400 ] && require_new_magisk
install_module
```
在 20.1 上直接 abort：`Please install Magisk v20.4+!`

**解法**（本项目用的）：临时把 `/data/adb/magisk/util_functions.sh` 换成
「v20.1 内容 + 补上 20.4 的 `install_module()` / `print_modname()`」的兼容版，
装完立刻还原。

### 11. Riru v23.9 官方 zip 有拼写 bug

`customize.sh` 和 `util_functions.sh` 里把 `$BOOTMODE` 写成了 **`$BOOTMOE`**：
```sh
if $BOOTMOE; then      # → if ; then  语法错误，必装失败
```

**解法**：
1. 改成 `BOOTMODE`
2. **必须重算 sha256 写回 `.sha256sum` 文件** —— Riru 自带的 `verify.sh` 会校验，不改校验就 abort
   （格式：`.sha256sum` 文件里只放 64 位十六进制，没有文件名）

### 12. EdXposed 装完要重启两次

Magisk < 21006 时，EdXposed 的安装器会 `touch reboot_twice_flag`，需要两次重启才完全生效。

## 三、Windows / PC 端坑

### 13. Windows 自带 OpenSSH 9.5 对 OpenSSH 10.x 服务端密钥认证静默失败

```
debug1: Server accepts key: ...
debug3: sign_and_send_pubkey: using publickey-hostbound-v00@openssh.com
debug2: we did not send a packet, disable method
→ Permission denied (publickey,password,keyboard-interactive)
```

**解法**：
- 在 `~/.ssh/config` 里给该主机加 `PubkeyAuthentication no` 强制走密码
- 或者用 **plink**（`tools\plink.exe`，实测可用）
- 服务端密钥认证本身是好的（用 Termux 自己的 ssh 回环测过 `PUBKEY_AUTH_OK`）

### 14. `adb install` 流式写入容易失败

USB 间歇性掉线时，`adb install xxx.apk` 会报空错误。
**解法**：改用 `adb push` + `pm install`：
```bash
adb push app.apk /data/local/tmp/a.apk
adb shell pm install -r /data/local/tmp/a.apk
```

### 15. toybox 的 `dd` 不认 `bs=1M`

```
dd: block size '1M': illegal number
```
**解法**：写 `bs=1048576`。

### 16. `.xz` 解压：PowerShell 没有内置支持

**解法**：用 Python 的 lzma：
```python
import lzma, shutil
with lzma.open(src,'rb') as f, open(dst,'wb') as o: shutil.copyfileobj(f,o)
```

### 17. PowerShell 调原生 exe 报 StandardOutputEncoding 错

`& python.exe script.py` → `StandardOutputEncoding is only supported when standard output is redirected`

**解法**：用 **`C:\Windows\py.exe`**（Python 启动器，路径无空格）：
```powershell
& "C:\Windows\py.exe" script.py
```

### 18. `objection patchapk` 需要 adb 和 apktool 在 PATH 里

否则报：
```
Unable to find adb. Install it with: apt install adb ...
Unable to find apktool. Install it from https://apktool.org/docs/install
```
**解法**：见 [scripts/env.ps1](../scripts/env.ps1)。apktool 需要自己造一个 `apktool.bat` 包装 `java -jar apktool.jar %*`。

### 19. Windows 上 `pip install` 用清华源会 403

**解法**：`--index-url https://pypi.org/simple/`

## 四、Termux / 手机端坑

### 20. `tcpdump` 不在 Termux 主仓库

```
E: Unable to locate package tcpdump
```
**解法**：先 `pkg install root-repo`，再 `pkg install tcpdump`。

### 21. Termux 的 sshd 必须在 App 上下文里跑

从 magisk 域（`su 10123 -c sshd`）跑会失败：
```
bad addr or host: <NULL> (No address associated with hostname)
```
因为 magisk 域拿不到 netd 的 DNS。同理，从 magisk 域跑 `curl` 也解析不了域名。
**解法**：在 Termux App 里敲 `sshd`（或走 Termux:Boot）。

### 22. `~/.ssh/authorized_keys` 不能有 CRLF

Windows 下 `ssh-keygen` 生成的 `.pub` 推过去可能带 `\r`，sshd 会静默拒绝。
**解法**：推送前去掉 `\r`。

### 23. 从 magisk 域跑 Termux 的二进制，能执行但没网

`su -c "su 10123 -c 'id'"` 能跑（uid 正确），但网络不通。
**原因**：SELinux 域还是 `u:r:magisk:s0`，不是 `u:r:untrusted_app:s0`。
Magisk 20.1 的 `su` 没有 `-Z` 选项，改不了域。

### 24. Termux:Boot 需要 EMUI 放行自启动

见第 7 条。兜底方案：在 `~/.bashrc` 里加钩子，打开一次 Termux 就自动起 sshd。

## 五、抓包 / 分析坑

### 25. Android 7+ 默认不信任用户证书

必须把 CA 放进**系统**信任区。做法：Magisk 模块挂载到
`/system/etc/security/cacerts/<subject_hash_old>.0`
（文件名必须是 8 位小写十六进制 + `.0`，用 `openssl x509 -subject_hash_old` 算）

### 26. 手机和电脑不同网段时，代理连不上

用 **`adb reverse`**：
```bash
adb reverse tcp:8080 tcp:8080
adb shell settings put global http_proxy 127.0.0.1:8080
```

### 27. `magiskpolicy --live` 的规则语法

是 `allow <源域> <目标域> <类别> <权限>`，**没有冒号**：
```
magiskpolicy --live "allow magisk magisk_file file read"     ✅
magiskpolicy --live "allow magisk self:process setcurrent"   ❌ 语法错误
```

## 六、性能 / 稳定性坑

### 28. SD 卡里的媒体文件被反复扫描 → 系统卡死

```
media.codec (omx service)  109%
android.process.media       78%
mediaserver                 50%
[mmcqd/1]                   9.3%   ← SD 卡 IO 队列一直忙
load average 40+
```
**解法**：在 SD 卡根目录放 `.nomedia`：
```bash
adb shell su -c 'touch /storage/XXXX-XXXX/.nomedia'
```
副作用：图库/音乐看不到 SD 卡上的媒体。

### 29. USB 会间歇性掉线

表现为 `adb devices` 显示 `offline`（USB 设备还在，adbd 不响应）。
**解法**：拔插数据线，或重启手机。

### 30. `ro.boot.flash.locked` / `verifiedbootstate` 的值被 Magisk 伪装过，不可信

```bash
adb shell getprop ro.boot.flash.locked        # → 1      （假的！）
adb shell getprop ro.boot.verifiedbootstate   # → green  （假的！）
```

**真实状态要看 `/proc/cmdline`：**
```bash
adb shell su -c 'cat /proc/cmdline' | tr ' ' '\n' | grep -E 'bootlock|userlock|verifiedbootstate'
# bootlock=unlocked
# userlock=unlocked
# androidboot.verifiedbootstate=orange      ← 真实值：橙灯 = 已解锁
```

**注意**：这两个 prop 是 **magiskinit 在开机时**写进去的，**关掉 MagiskHide 也不会还原**
（实测 `magiskhide --disable` 后依然是 1 / green）。

**影响**：任何靠 `getprop ro.boot.flash.locked` 判断"设备是否解锁"的脚本都会误判。
判断解锁状态请一律读 `/proc/cmdline` 里的 `bootlock` / `userlock`。

`scripts/capture.ps1`:

```ps1
<#
.SYNOPSIS
  被动抓包（tcpdump）—— 抓手机所有网卡流量，导出 pcap 给 Wireshark
.EXAMPLE
  .\scripts\capture.ps1 start
  .\scripts\capture.ps1 stop
#>
param(
  [Parameter(Position=0)][string]$Action = 'help',
  [string]$Out = 'G:\DeepSeek Harness\Root\capture\cap.pcap',
  [string]$Filter = ''
)
$ErrorActionPreference = 'Stop'
$ADB = $env:ADB; if (-not $ADB) { $ADB = (Get-Command adb).Source }
$devArg = if ($env:PHONE_SERIAL) { @('-s', $env:PHONE_SERIAL) } else { @() }
$TCPDUMP = '/data/data/com.termux/files/usr/bin/tcpdump'
$LDPATH  = '/data/data/com.termux/files/usr/lib'
$REMOTE  = '/sdcard/_cap.pcap'

switch ($Action.ToLower()) {
  'start' {
    & $ADB @devArg shell "su -c 'pkill -f tcpdump; rm -f $REMOTE; LD_LIBRARY_PATH=$LDPATH nohup $TCPDUMP -i any -s 0 -w $REMOTE $Filter >/dev/null 2>&1 &'"
    Start-Sleep -Seconds 2
    & $ADB @devArg shell "su -c 'ps -A | grep tcpdump'"
    Write-Host '抓包已开始。停止: .\scripts\capture.ps1 stop' -ForegroundColor Green
  }
  'stop' {
    & $ADB @devArg shell "su -c 'pkill -f tcpdump'"
    Start-Sleep -Seconds 2
    New-Item -ItemType Directory -Force -Path (Split-Path $Out) | Out-Null
    & $ADB @devArg pull $REMOTE $Out
    Write-Host "已保存到 $Out —— 用 Wireshark 打开" -ForegroundColor Green
  }
  'live' { & $ADB @devArg shell "su -c 'LD_LIBRARY_PATH=$LDPATH $TCPDUMP -i any -nn $Filter'" }
  default {
    Write-Host '用法: capture.ps1 <start|stop|live> [-Out 路径] [-Filter 表达式]' -ForegroundColor Yellow
    Write-Host '过滤例子: "port 443" / "host 1.2.3.4" / "tcp and not port 22"'
  }
}

`scripts/frida-patch.ps1`:

```ps1
<#
.SYNOPSIS
  Frida Gadget 打补丁 —— 本机 frida-server 不可用（华为锁 SELinux），
  这是唯一可用的 Frida 路线：把 gadget 直接打进 APK。
.EXAMPLE
  .\scripts\frida-patch.ps1 -Package com.example.app -Install
#>
param(
  [string]$Package,
  [string]$Apk,
  [string]$OutDir = 'G:\DeepSeek Harness\Root\capture\frida',
  [switch]$Install,
  [switch]$NoNetSec
)
$ErrorActionPreference = 'Stop'
$ADB = $env:ADB; if (-not $ADB) { $ADB = (Get-Command adb).Source }
$devArg = if ($env:PHONE_SERIAL) { @('-s', $env:PHONE_SERIAL) } else { @() }
if (-not $env:PY_SCRIPTS) { throw '请先执行 . .\scripts\env.ps1' }
$OBJ = Join-Path $env:PY_SCRIPTS 'objection.exe'
New-Item -ItemType Directory -Force -Path $OutDir | Out-Null

if (-not $Apk) {
  if (-not $Package) { throw '必须指定 -Package 或 -Apk' }
  $remote = ((& $ADB @devArg shell "pm path $Package") -join '') -replace '^package:', ''
  $remote = $remote.Trim()
  if (-not $remote) { throw "设备上找不到 $Package" }
  $Apk = Join-Path $OutDir "$Package.apk"
  & $ADB @devArg pull $remote $Apk
}

$extra = if ($NoNetSec) { @() } else { @('-N') }
& $OBJ patchapk -s $Apk -a arm64-v8a @extra

$patched = Join-Path (Split-Path $Apk) ((Split-Path $Apk -Leaf) -replace '\.apk$', '.objection.apk')
if (Test-Path $patched) { Write-Host "补丁完成: $patched" -ForegroundColor Green }

if ($Install -and $Package) {

    Write-Host '== 已冻结 ==' -ForegroundColor Cyan; Sh 'pm list packages -d'

  }

    Write-Host '  install <zip> / push <本地> <远端> / pull <远端> <本地> / ssh / reboot'

<#
.SYNOPSIS
  手机代理抓包环境 —— 用 adb reverse 把电脑代理端口映射到手机 127.0.0.1
  （手机与电脑不在同一网段时，这是唯一可行的办法）
.EXAMPLE
  .\scripts\proxy.ps1 on 8080
  .\scripts\proxy.ps1 off
#>
param(
  [Parameter(Position=0)][string]$Action = 'status',
  [int]$Port = 8080
)
$ErrorActionPreference = 'Stop'
$ADB = $env:ADB; if (-not $ADB) { $ADB = (Get-Command adb).Source }
$devArg = if ($env:PHONE_SERIAL) { @('-s', $env:PHONE_SERIAL) } else { @() }

switch ($Action.ToLower()) {
  'on' {
    & $ADB @devArg reverse "tcp:$Port" "tcp:$Port"
    & $ADB @devArg shell "settings put global http_proxy 127.0.0.1:$Port"
    Write-Host "代理已开启: 手机 -> 127.0.0.1:$Port -> 电脑:$Port" -ForegroundColor Green
    Write-Host "别忘了让电脑上的 mitmproxy/Charles/Fiddler 监听 $Port" -ForegroundColor Yellow
  }
  'off' {
    & $ADB @devArg shell 'settings put global http_proxy :0'
    Write-Host '代理已关闭' -ForegroundColor Green
  }
  default {
    Write-Host '== 手机代理 ==' -ForegroundColor Cyan; & $ADB @devArg shell 'settings get global http_proxy'
    Write-Host '== reverse ==' -ForegroundColor Cyan; & $ADB @devArg reverse --list
    Write-Host '== forward ==' -ForegroundColor Cyan; & $ADB @devArg forward --list
  }
}

## ⚠️ 五条铁律（违反必翻车）

1. **`pm` / `am` / `settings` 不能用 root 跑** —— 会报 `Failed transaction (2147483646)`。

3. **别用 Magisk Manager 的「安装/修复运行环境」** —— 本机没 boot 分区，会把 recovery_ramdisk 搞坏
4. **别用 `magisk --sqlite` 跑带子查询的 SQL** —— 会把 magiskd 搞崩，root 全失效
5. **toybox 的 `dd` 不认 `bs=1M`** —— 写 `bs=1048576`
6. **判断是否解锁看 `/proc/cmdline`** —— `getprop ro.boot.flash.locked` 被 Magisk 伪装成 `1`，不可信

## 华为 EMUI 专属坑速查

| 症状 | 原因 | 解法 |
|---|---|---|
| `Failed transaction (2147483646)` | 用 root 跑了 `pm`/`am` | 改用 `adb shell pm ...` |
| `Unable to save SELinux policy` | 华为锁 SELinux | 用 Frida Gadget，别用 frida-server |
| `setenforce: Invalid argument` | 同上 | 别折腾 |
| `No daemon is currently running!` | magiskd 崩了 | 重启手机 |
| `dd: block size '1M'` | toybox dd | `bs=1048576` |
| `E: Unable to locate package tcpdump` | 不在 Termux 主仓库 | 先 `pkg install root-repo` |
| `bad addr or host: <NULL>` | 在 magisk 域跑 Termux 程序 | 在 Termux App 里跑 |
| ssh 密钥认证 Permission denied | Windows OpenSSH 9.5 的 hostbound bug | 用密码或 `tools\plink.exe` |
| 手机很卡 / 点不动 | SD 卡媒体文件被反复扫描 | SD 卡根目录放 `.nomedia` |
| 模块装不上 `Please install Magisk v20.4+` | 20.1 缺 `install_module` | 用 `scripts/install-module.sh` |

## 注意事项

- **不要**升级 Magisk 到 24+：本机没 boot 分区、没 fastboot 兜底，刷坏就失去 root
- **不要**用 Magisk Manager 的「修复运行环境」
- 抓包前先确认：证书装了没 → 代理开了没 → 有没有 Pinning → 是不是绕过代理
- 改任何系统文件都用 **Magisk 模块挂载**，不要 remount /system
