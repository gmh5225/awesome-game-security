## Day 3 (30 Oct)

Done:
- Watched Calling Functions and Local Variables.
- Stepped through SingleLocalVariable and SingleLocalVariable2 in the debugger on my own PC (retargeted the course projects to the newer toolset).
- Filled in a step table and a stack diagram for the nested calls, and worked out why func2 reserves 38h and not 40h.

What I learned:
- Locals live in space reserved with sub rsp,N. mov [rsp],value stores a local, mov eax,[rsp] reads it back, add rsp,N gives the space back. After ret the old value is still in memory but below rsp.

`month1-asm/01-add/notes.md`:

```md
\# 01-add



Source:



main.cpp

int add(int a, int b)

{

&#x20;   return a + b;

}



On Windows x64, `a` arrives in `ecx` and `b` in `edx`. An `int` result goes back in `eax`.



\## /Od (no optimisation)



```asm

int add(int,int) PROC          ; function start (a label for the assembler, not an instruction)

mov DWORD PTR \[rsp+16], edx    ; store b (2nd argument, in edx) into stack memory at rsp+16

mov DWORD PTR \[rsp+8], ecx     ; store a (1st argument, in ecx) into stack memory at rsp+8

mov eax, DWORD PTR b$\[rsp]     ; load b back from rsp+16 into eax (b$ is the compiler's name for offset 16)

mov ecx, DWORD PTR a$\[rsp]     ; load a back from rsp+8 into ecx (a$ is the name for offset 8)

add ecx, eax                   ; ecx = ecx + eax, so ecx = a + b

mov eax, ecx                   ; copy the sum into eax, where the caller expects an int result

ret 0                          ; return to the caller (main), result is in eax

int add(int,int) ENDP          ; function end (also not an instruction)

```



At /Od every variable lives in memory. The compiler saves each argument to the stack and loads it straight back before using it.



\## /O2 (optimised)



```asm

int add(int,int) PROC                 ; function start

lea eax, DWORD PTR \[rcx+rdx]          ; eax = rcx + rdx (a + b). lea does the arithmetic without reading memory, and writes the sum to a third register

ret 0                                 ; return to the caller, result already in eax

int add(int,int) ENDP                 ; function end

```



At /O2 the arguments are used straight from the registers they arrive in, so memory is never touched.



\## Differences



1./0d uses 6 instructions plus ret; four mov's, an add, and a final mov but /O2	uses 1 instruction plus ret: a single lea.

2.the unoptimized version does a lot of busywork. it saves both arguments to memory, loads them back, adds them, and copies the sum into the result register. the optimised version just adds the two registers directly and writes the result in eax.

3\. /0d uses rsp but /O2 doesn't.

4\. /Od saves a and b from ecx and edx to the stack and loads them back before adding. /O2 reads them directly from rcx and rdx.

5\. /0d needs move eax, ecx to get the sum but /O2 doesn't as it just gets it from lea eax, DWORD PTR \[rcx+rdx]



\## What confused me



\- Why does the compiler save arguments to \[rsp+8] and \[rsp+16] at all?


```

__declspec(noinline) int square(int x)
{
    return x * x;
}

{
    int sa = square(a);
    int sb = square(b);
    return sa + sb;
}

{
    int result = sum_of_squares(3, 4);
    std::printf("%d\n", result);
    return 0;
}

\# Day 2: the stack



call pushes the 8 byte return address, then jumps. ret pops 8 bytes into rip.



rsp (last 3 hex digits, one run):

\- start of main: 9C8

\- on call sum\_of\_squares: 8B0 (main setup: push rbp, push rdi, sub rsp,108h = -280)

\- inside sum\_of\_squares: 8A8 (-8, return address)

\- on call square: 770 (setup = -312)

\- inside square: 768 (-8)

\- square body: 670 (setup = -248)

\- on ret in square: 768 (lea + 2 pops undo the setup)

\- after ret: 770 (+8)



Return address at rsp after call = address of the instruction after the call in main.

square(3) = 9, square(4) = 16 (0x10), both returned in rax.



a and b are saved by mov \[rsp+8],ecx and mov \[rsp+10h],edx into the 16 bytes above the return address (shadow space, to confirm in the video).



Not yet seen: the final ret from sum\_of\_squares back into main.

`month1-asm/03-locals/notes.md`:

```md
\# Day 3: local variables and stack frames



SingleLocalVariable:

\- sub rsp,18h reserves 24 bytes. mov dword ptr \[rsp],5CA1AB1Eh stores i at rsp+0. mov eax,\[rsp] copies it into eax for the return. add rsp,18h gives the space back.

\- After ret the value is still in memory but below rsp, so it can be overwritten at any time.



SingleLocalVariable2 (main -> func -> func2 -> func3):

\- call pushes the return address and sets rip to the call target. ret pops it into rip and adds 8 to rsp.

\- Reserved sizes: func3 18h (24), func 28h (40), func2 38h (56), main 28h (40).

\- Each size plus the 8 byte return address is a multiple of 16 (Windows x64 needs rsp 16-byte aligned at every call).

\- func2 is 38h and not 40h because 40h + 8 = 48h (72), which is not a multiple of 16.

\- Frame breakdown: 8 padding + 16 locals + 32 shadow space. func3 = 8+16, func = 8+32, func2 = 8+16+32.

\- Shadow space is 32 bytes the caller reserves for the callee's 4 register arguments (rcx, rdx, r8, r9). To confirm in the Function Parameter Passing video.



Mistakes: wrong direction for call (it lowers rsp), mixed up hex and decimal (48h is 72, not 48), thought ret reads i (it reads the return address).
