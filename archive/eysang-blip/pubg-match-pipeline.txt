`README.md`:

```md
# PUBG Match Pipeline

PUBG 공식 API로 매치 데이터를 수집해 SQLite DB로 정리하고, 데이터 품질을 자동으로 점검한 뒤, SQL로 **부정행위 검토 후보**를 뽑는 파이프라인입니다.

- 매치 945개, 참가 기록 78,650건 수집 (매치별 참가자 1명당 1건이라 같은 사람이 여러 판에 나오면 중복 포함. 분석 대상: 정규 squad 매치의 사람 참가 기록 35,570건)
- 수집 → DB 구축 → 품질 점검(9개 항목) → SQL 분석을 `run_pipeline.py` 하나로 실행
- 품질 점검에 실패하면 분석 단계로 넘어가지 않음

## 파이프라인 구성

```mermaid
flowchart LR
    A["get_samples.py<br/>매치 ID 목록<br/>(누적 저장)"] --> B["collect_matches.py<br/>매치 상세 JSON<br/>(증분 수집, 429 재시도)"]
    B --> C["build_db.py<br/>SQLite DB<br/>(원본으로 매번 재생성)"]
    C --> D{"validate.py<br/>품질 점검 9개"}
    D -- 통과 --> E["analyze_sql.py<br/>sql/01~06 실행"]
    D -- 실패 --> F["중단<br/>logs/에 기록"]
    E --> G["검토 후보 CSV<br/>(저장소 비공개)"]
```

| 단계 | 스크립트 | 하는 일 |
|---|---|---|
| 1. 매치 목록 | `get_samples.py` | `/samples`에서 최근 매치 ID를 받아 기존 목록에 **추가** (덮어쓰지 않음, 새 ID를 앞에 둠) |
| 2. 매치 상세 | `collect_matches.py` | 매치 JSON을 `data/`에 저장. 이미 받은 매치와 만료된 매치는 건너뜀, 429 응답은 대기 후 재시도 |
| 3. DB 구축 | `build_db.py` | 원본 JSON에서 DB를 매번 새로 만듦. 몇 번을 돌려도 같은 결과 |
| 4. 품질 점검 | `validate.py` | 원본 대조, 중복, 결측, 논리 오류 등 9개 항목을 통과/실패로 판정하고 `logs/`에 기록 |
| 5. 분석 | `analyze_sql.py` + `sql/` | SQL 파일을 순서대로 실행하고 검토 후보를 `output/review_candidates.csv`로 저장 |
| 전체 실행 | `run_pipeline.py` | 1~5단계를 순서대로 실행, 단계별 결과를 `logs/pipeline_날짜.log`에 기록 |
| 테스트 | `test_validate.py` | 점검 로직이 일부러 넣은 오류(누락, 중복, 논리 오류 등)를 잡아내는지 확인 (7개) |

### 점검하면서 확인한 것

- **참가자 0명·1명 매치의 원인**: 원본 JSON을 열어 확인한 결과 실제 게임이 아니었습니다. 0명 매치 18개는 모두 `trainingroom`(훈련장, duration 0, 참가자 데이터 없이 asset만 있음), 1명 매치 41개는 모두 `tutorialatoz`(튜토리얼)였습니다. 이 규칙을 점검 항목으로 넣어서, 일반 매치에서 참가자가 0~1명이면 실패로 잡도록 했습니다.
- **봇이 참가 기록의 38%**: `player_id`가 `ai.`로 시작하는 참가 기록이 78,650건 중 29,544건이었습니다. 일반 매치와 봇전에는 봇이 있고 랭크 매치에는 0명이었습니다. 봇은 평균 피해량 92(사람 160), 헤드샷 비율 0.06(사람 0.24)으로 분포가 크게 달라서, 1차 분석(봇 포함)의 기준선이 왜곡되어 있었습니다.
- **봇을 빼도 분포는 치우쳐 있음**: 처음에는 피해량 Q1이 0인 이유가 봇이라고 추측했지만, 봇을 빼도 사람 중 0킬이 54%였고 Q1은 5.7이었습니다. 추측이 틀렸고, 원래 분포가 치우쳐 있는 것으로 정정했습니다.
- **매치 ID는 시간이 지나면 만료됨**: 처음 받은 ID 735개 중 265개만 조회됐고 470개는 404였습니다. 반면 받자마자 수집한 ID 680개는 모두 성공했습니다. 그래서 목록 수집 직후 상세 수집을 하도록 파이프라인을 묶었고, 404가 난 ID는 `expired_ids.txt`에 기록해 다시 요청하지 않습니다.
- **팀 구성은 모드 안에서도 가변적**: duo-fpp 매치 하나는 roster가 52개였는데(예상 50개), 확인해 보니 2인 팀 48개와 1인 팀 4개였습니다. 코드 문제가 아니라 실제 팀 구성이었습니다.

## 분석: 부정행위 검토 후보 찾기

### 정제 (`sql/01`, `sql/02`)

| 단계 | 남은 행 |
|---|---|
| 전체 참가 기록 | 78,650 |
| squad 모드만 | 51,390 |
| 정규 매치만 (봇전·훈련장·튜토리얼 제외) | 42,729 |
| 사람만 (봇 제외) | 35,570 |

### 1차 시도와 문제점

처음에는 squad 모드 피해량에 IQR 3배 기준을 적용했습니다(`exploration/analyze_outliers*.py`, 매치 50개 기준). 걸린 사람은 대부분 오래 살아남아 1위를 한 플레이어였습니다(순위 중앙값 1위, 생존 20.2분). 피해량이 높은 이유의 상당 부분이 생존 시간이었고, 봇도 섞여 있었습니다.

### 지표 설계

**최소 표본 조건이 필요한 근거** (`sql/04`): 킬 수 구간별로 헤드샷 비율 평균은 0.23 안팎으로 비슷하지만, 헤드샷 100%인 사람 비율은 1킬에서 23.1%, 5~9킬에서 0.2%입니다. 표본이 작으면 비율이 극단값으로 튀므로, 헤드샷 비율은 **킬 5 이상**인 경우만 썼습니다.

**매치 안에서 비교** (`sql/05`): 매치마다 로비 수준이 달라서, 분당 피해량을 같은 매치 사람들의 평균·표준편차와 비교한 z-score를 썼습니다(`AVG() OVER (PARTITION BY match_id)`). 5분 미만 생존자는 분모가 작아 제외했습니다. 이때 문제가 하나 나왔는데, 교전이 거의 없던 매치(참가자 98명 중 봇 64명, 사람 34명의 킬 합계 1개)에서는 분당 피해량 6.0이 z 5.57이 됐습니다. 그래서 **전체 상위 10%(분당 피해량 30.5 이상)** 라는 절대 하한을 함께 걸었습니다.

**신호끼리 독립인지 확인**: 처음에는 킬 수 상위 1%도 신호로 넣었는데, 후보가 전부 "분당 피해량 + 킬 수" 조합이고 대부분 1위였습니다. 상관계수를 보니 분당 피해량과 킬 수는 0.64로 같은 것(교전을 많이 함)을 두 번 세고 있었습니다. 반면 헤드샷 비율은 킬 수, 분당 피해량과 모두 -0.02로 거의 독립이었습니다. 그래서 킬 수 신호를 빼고 두 축으로 정리했습니다.

### 검토 후보 기준 (`sql/06`)

| 축 | 조건 |
|---|---|
| A. 교전량 | 분당 피해량이 같은 매치 대비 z ≥ 3 (비교 인원 20명 이상) **그리고** 전체 상위 10% |
| B. 정확도 | 헤드샷 비율 상위 5% (킬 5 이상 중, 헤드샷 비율 0.625 이상) |

두 축 모두 걸리면 "우선 검토", 하나만 걸리면 "일반 검토"입니다.

### 결과

| 구분 | 건수 | 순위 중앙값 | 킬 중앙값 |
|---|---|---|---|
| A만 (교전량) | 363 | 15위 | 4 |
| B만 (정확도) | 46 | 2위 | 6 |
| A와 B 모두 (우선 검토) | 0 | - | - |
| 합계 | 409 (35,570건 중 1.15%) | | |

- 시간과 매치 수준을 보정하니, 교전량 축 후보의 순위 중앙값이 1위에서 15위로 바뀌었습니다. 1차 시도처럼 "오래 살아서 이긴 사람"을 잡는 문제는 해결됐습니다.
- 두 축에 동시에 걸린 경우는 없었습니다. 공개 통계 범위에서는 교전량과 정확도가 함께 극단적인 플레이어-매치가 이 표본에 없었다는 뜻입니다.

### 한계

- **후보는 부정행위 판정이 아닙니다.** 상위 몇 %를 자르면 정상 플레이어도 항상 그만큼 걸립니다. 실제 운영이라면 리플레이 확인 등 다른 근거로 확인할 목록입니다. 그래서 후보 CSV는 저장소에 올리지 않았습니다.
- **플레이어 단위 추적이 어렵습니다.** `/samples`는 무작위 매치라서 같은 사람이 최대 3판만 나왔습니다(2판 이상 642명). 계정 단위로 행동 변화를 보려면 플레이어별 매치 이력 수집이 필요합니다.
- **매치 요약 통계만 썼습니다.** 명중률, 킬 거리, 반응 시간 같은 신호는 텔레메트리(이벤트 로그)가 있어야 계산할 수 있습니다.
- 임계값(z 3, 상위 10%, 상위 5%, 킬 5)은 분포를 보고 정했지만, 정답 라벨이 없어서 오탐률·탐지율은 측정하지 못했습니다.

오버워치처럼 공개 데이터가 없는 게임에 같은 방식을 적용하는 구상은 [docs/overwatch_extension.md](docs/overwatch_extension.md)에 정리했습니다.

## AI 활용 범위와 검증

이 프로젝트는 AI 코딩 도구를 적극적으로 활용해 진행했습니다.

- **1차 작업** (수집, DB 구축, 1차 품질 점검과 IQR 분석): Claude 채팅의 안내를 받아 각 단계를 직접 실행하고 결과를 확인했습니다.
- **2차 작업** (표본 확대, 자동화, 품질 점검 자동화, SQL 분석 재설계): Claude Code가 코드 작성, 실행, 결과 검증까지 주도했습니다.

| 구분 | 내용 |
|---|---|
| 직접 한 것 | API 키 발급과 실행 환경 구성, 1차 작업의 단계별 실행과 결과 확인, 지원 직무(안티치트)에 맞춘 프로젝트 방향 설정, 오버워치 확장 문서의 신호 가설과 오탐 사례(플레이 경험), 공개 범위 판단, AI가 낸 핵심 결과 3건의 재현 확인(아래) |
| AI가 한 것 | 코드와 SQL 작성, 분석 설계, 결과 검증과 설계 수정 |

### 작업 중 데이터로 다시 확인해서 버리거나 고친 설계

AI가 처음 낸 결과를 그대로 쓰지 않고, 수치로 다시 확인해서 바꾼 사례입니다.

- IQR 기준 → 걸린 사람 대부분이 오래 살아남은 1위였음. 생존 시간 효과로 보고 분당 피해량으로 변경
- 킬 수 신호 → 분당 피해량과 상관 0.64라서 같은 것을 두 번 세는 것으로 판단하고 제외
- 매치 내 z-score 단독 사용 → 교전이 거의 없던 매치에서 z가 튀는 것을 확인하고 절대 하한 추가
- "Q1이 0인 건 봇 때문" → 봇을 빼고 다시 계산해 보니 Q1이 여전히 낮아서, 틀린 추측으로 정정

### 직접 재현해 확인한 결과 (`verify/`)

AI가 낸 결과 중 분석 설계의 근거가 된 3건을 직접 SQL로 다시 계산해 확인했습니다. 재현 쿼리는 AI의 안내를 받아 작성했지만, AI가 만든 컬럼(`is_bot`)이나 분석 코드(`sql/`)를 쓰지 않고 원래 컬럼(`player_id` 등)으로 처음부터 계산했습니다. 3건 모두 일치했습니다.

| 확인한 것 | 기존 값 | 직접 계산 | 쿼리 |
|---|---|---|---|
| 봇 비율 (`is_bot` 대신 `player_id`가 `ai.`로 시작하는지로 집계) | 38% | 37.6% (78,650건 중 29,544건) | `verify/01_bot_ratio.sql` |
| 분당 피해량과 킬 수의 상관 (SQLite에 상관 함수가 없어 공식을 SQL로 직접 계산) | 0.64 | 0.64 (24,571건) | `verify/02_correlation.sql` |
| z가 튄 매치의 구성 | 98명, 봇 64명, 사람 34명, 사람 킬 합계 1 | 같음, 사람 평균 피해량 2.9 | `verify/03_quiet_match.sql` |

실행: `python run_sql.py verify/01_bot_ratio.sql`

import json
import sqlite3
import glob

# DB는 data/ 폴더의 원본 JSON으로 언제든 다시 만들 수 있는 "파생 데이터"다.
# 그래서 매번 테이블을 지우고 처음부터 다시 만든다.
# (컬럼을 추가해도 기존 행이 옛날 구조로 남는 문제가 없고, 몇 번을 돌려도 결과가 같다)

# 1) DB 파일 열기 (없으면 새로 만들어짐)
conn = sqlite3.connect("pubg.db")
cur = conn.cursor()

# 2) 테이블 새로 만들기
cur.execute("DROP TABLE IF EXISTS participants")
cur.execute("DROP TABLE IF EXISTS matches")

cur.execute("""
CREATE TABLE matches (
    match_id   TEXT PRIMARY KEY,
    game_mode  TEXT,
    match_type TEXT,     -- official(일반), competitive(랭크), airoyale(봇전), trainingroom(훈련장), tutorialatoz(튜토리얼)
    map_name   TEXT,
    duration   INTEGER,
    created_at TEXT
)
""")

cur.execute("""
CREATE TABLE participants (
    match_id       TEXT,
    player_id      TEXT,     -- 'account.'로 시작하면 사람, 'ai.'로 시작하면 봇
    is_bot         INTEGER,  -- 1이면 봇
    kills          INTEGER,
    assists        INTEGER,
    dbnos          INTEGER,
    headshot_kills INTEGER,
    damage_dealt   REAL,
    time_survived  REAL,
    walk_distance  REAL,
    ride_distance  REAL,
    win_place      INTEGER,
    kill_place     INTEGER,
    PRIMARY KEY (match_id, player_id),
    FOREIGN KEY (match_id) REFERENCES matches (match_id)
)
""")

# 3) data 폴더의 JSON 파일을 읽어서 저장
for path in glob.glob("data/*.json"):
    with open(path, encoding="utf-8") as f:
        data = json.load(f)

    match_id = data["data"]["id"]
    attrs = data["data"]["attributes"]

    cur.execute(
        """INSERT OR IGNORE INTO matches
           (match_id, game_mode, match_type, map_name, duration, created_at)
           VALUES (?, ?, ?, ?, ?, ?)""",
        (match_id, attrs.get("gameMode"), attrs.get("matchType"),
         attrs.get("mapName"), attrs.get("duration"), attrs.get("createdAt")),
    )

    for item in data["included"]:
        if item["type"] != "participant":
            continue
        s = item["attributes"]["stats"]
        is_bot = 1 if s["playerId"].startswith("ai.") else 0
        cur.execute(
            """INSERT OR IGNORE INTO participants
               (match_id, player_id, is_bot, kills, assists, dbnos, headshot_kills,
                damage_dealt, time_survived, walk_distance, ride_distance,
                win_place, kill_place)
               VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)""",
            (match_id, s["playerId"], is_bot, s["kills"], s["assists"], s["DBNOs"],
             s["headshotKills"], s["damageDealt"], s["timeSurvived"],
             s["walkDistance"], s["rideDistance"], s["winPlace"], s["killPlace"]),
        )

conn.commit()

# 4) 잘 들어갔는지 확인
print("matches 행 수:", cur.execute("SELECT COUNT(*) FROM matches").fetchone()[0])
print("participants 행 수:", cur.execute("SELECT COUNT(*) FROM participants").fetchone()[0])
print("봇 행 수:", cur.execute("SELECT SUM(is_bot) FROM participants").fetchone()[0])

conn.close()

`collect_matches.py`:

```py
import os
import json
import time
import requests
from dotenv import load_dotenv

# 1) 설정
load_dotenv()
API_KEY = os.getenv("PUBG_API_KEY")
PLATFORM = "steam"
LIMIT = None         # 받을 매치 개수 상한 (None이면 목록 전체)
MAX_RETRY = 3        # 429(요청 너무 많음)일 때 재시도 횟수
EXPIRED_FILE = "expired_ids.txt"   # 404로 확인된 만료 ID 기록 (다음 실행 때 다시 요청하지 않음)

headers = {
    "Authorization": f"Bearer {API_KEY}",
    "Accept": "application/vnd.api+json",
}

# 2) 매치 ID 목록과 이미 만료로 확인된 ID 읽기
with open("match_ids.txt") as f:
    match_ids = f.read().splitlines()[:LIMIT]

expired = set()
if os.path.exists(EXPIRED_FILE):
    with open(EXPIRED_FILE) as f:
        expired = set(f.read().splitlines())

os.makedirs("data", exist_ok=True)
saved, skipped, expired_now, failed = 0, 0, 0, 0


def fetch(match_id):
    """매치 하나를 요청한다. 429면 기다렸다가 재시도, 네트워크 오류도 재시도."""
    url = f"https://api.pubg.com/shards/{PLATFORM}/matches/{match_id}"
    for attempt in range(1, MAX_RETRY + 1):
        try:
            response = requests.get(url, headers=headers, timeout=30)
        except requests.RequestException as e:
            print(f"  네트워크 오류 ({attempt}/{MAX_RETRY}): {e}")
            time.sleep(5 * attempt)
            continue

        if response.status_code != 429:
            return response

        # 서버가 기다릴 시간을 알려주면 그만큼, 아니면 60초 대기
        wait = int(response.headers.get("Retry-After", 60))
        print(f"  429 호출 제한 ({attempt}/{MAX_RETRY}), {wait}초 대기")
        time.sleep(wait)
    return None


# 3) 하나씩 받아서 저장
for i, match_id in enumerate(match_ids, start=1):
    path = f"data/{match_id}.json"

    # 이미 받은 매치, 이미 만료로 확인된 매치는 건너뜀 (증분 수집)
    if os.path.exists(path) or match_id in expired:
        skipped += 1
        continue

    response = fetch(match_id)

    if response is not None and response.status_code == 200:
        with open(path, "w", encoding="utf-8") as f:
            json.dump(response.json(), f, ensure_ascii=False)
        saved += 1
    elif response is not None and response.status_code == 404:
        # 오래된 매치는 PUBG 서버에서 삭제되어 404가 난다
        expired_now += 1
        with open(EXPIRED_FILE, "a") as f:
            f.write(match_id + "\n")
    else:
        failed += 1
        code = response.status_code if response is not None else "재시도 초과"
        print(f"[{i}] 실패 {code}: {match_id}")

    time.sleep(0.5)  # 서버에 부담 주지 않게 잠깐 쉬기

# 4) 결과 요약
print(f"저장 {saved}개 / 건너뜀 {skipped}개 / 만료(404) {expired_now}개 / 실패 {failed}개")

```

# 오버워치 확장 시나리오

> 이 문서는 구현이 아니라 구상입니다. PUBG 프로젝트에서 만든 방식(정제 → 품질 점검 → 독립 신호 → 검토 후보)을 오버워치 내부 로그에 적용한다면 어떻게 할지 정리했습니다.

## 1. 왜 PUBG로 시작했나

처음에는 오버워치 데이터로 하려고 했지만, 이상 행동을 찾는 데 필요한 데이터를 구할 수 없어서 PUBG로 바꿨습니다.

- 오버워치는 매치 단위 데이터를 주는 공식 공개 API가 없습니다.
- 공개된 통계는 티어 구간별·영웅별 픽률과 승률 같은 **집계 통계**뿐입니다. 이것으로는 특정 매치에서 특정 플레이어가 어떻게 플레이했는지 볼 수 없어서, 플레이어 단위의 이상 행동 분석을 할 수 없습니다.
- 비공식 경로로 볼 수 있는 프로필 통계도 플레이어가 프로필을 비공개로 하면 볼 수 없어서, 표본이 공개 설정한 사람으로 치우칩니다.

PUBG는 공식 API 키를 발급받으면 매치 단위로 참가자별 지표(킬, 피해량, 헤드샷 킬, 생존 시간 등)를 받을 수 있어서, 같은 문제(슈터 게임의 이상 행동 후보 찾기)를 실제 데이터로 먼저 풀어볼 수 있었습니다. 이 문서는 그렇게 만든 방법을, 내부 로그가 있는 환경에서 오버워치에 적용한다면 어떻게 할지에 대한 구상입니다.

## 2. PUBG에서 배운 것 중 그대로 가져갈 것

| PUBG에서 확인한 것 | 오버워치에 적용 |
|---|---|
| 봇이 참가 기록의 38%였고, 빼지 않으면 분포가 왜곡됨 | 연습 상대 AI, 사용자 지정 게임, 아케이드를 먼저 분리 |
| 훈련장·튜토리얼 매치가 참가자 0~1명 매치의 원인 | 매치 종류(빠른 대전/경쟁전/사용자 지정)를 스키마에 반드시 저장 |
| 킬 1~2개면 헤드샷 비율이 0% 또는 100%로 튐 | 명중률·치명타 비율은 최소 발사 수/처치 수 조건을 둠 |
| 분당 피해량과 킬 수는 상관 0.64로 사실상 같은 신호 | 신호를 고를 때 서로 상관을 먼저 확인하고 독립적인 축만 조합 |
| 교전이 없던 매치는 매치 내 z-score가 튐 | 같은 매치 비교 + 전체 기준 하한을 함께 사용 |

## 3. 오버워치에서 다른 점

- **영웅마다 정상 범위가 다릅니다.** 위도우메이커의 치명타 비율과 라인하르트의 치명타 비율은 비교할 수 없습니다. 그래서 비교 단위는 "같은 매치"가 아니라 **"같은 영웅 + 같은 경쟁전 구간(티어)"** 이어야 합니다.
- **팀 구성이 고정(5:5, 역할 고정)입니다.** PUBG처럼 roster 인원이 가변적인 문제는 적지만, 역할(돌격/공격/지원)별로 지표를 나눠 봐야 합니다.
- **같은 플레이어가 계속 나옵니다.** PUBG `/samples`는 무작위 매치라 한 사람이 최대 3판만 나왔지만, 내부 로그라면 계정 단위로 시간 흐름에 따른 변화(갑자기 실력이 오르는 구간)를 볼 수 있습니다.

## 4. 플레이하면서 의심했던 경우와 로그 신호 가설

> 오버워치를 오래 플레이하면서 "대놓고 쓰는 핵"이 아닌데도 이상하다고 느꼈던 경우들입니다. 실제 로그로 검증해야 하는 가설입니다.
>
> 관찰한 범위: 주 역할은 공격(딜러)이고, 최고 그랜드마스터까지 플레이했습니다. 티어를 올려 가는 과정에서, 그리고 역할마다 티어가 다르고 소프트 리셋 뒤에는 낮은 구간에서 배치를 다시 시작했기 때문에, 중간 티어부터 그랜드마스터까지 여러 티어대를 직접 겪었습니다. 아래의 "티어마다 같은 신호의 의미가 다르다"는 내용은 이 경험에서 나왔습니다.

### 핵심 아이디어: 지표 하나가 높은 것보다 "실력끼리 안 맞는 것"이 더 강한 신호

에임이 좋은 것만으로는 의심할 수 없습니다. 잘하는 사람은 원래 에임이 좋기 때문입니다. 그런데 실제로 의심이 들었던 경우는 대부분 **에임만 기가 막히고 나머지 실력이 그 수준을 따라오지 못할 때**였습니다.

- 무빙, 지형지물 활용, 스킬 활용, 위치 선정은 부족한데 에임만 좋음
- 에임을 믿고 엄폐 없이 몸이 앞으로 쏠리는 플레이

사람의 실력은 보통 함께 오릅니다. 에임이 상위 1%인 사람은 대개 위치 선정이나 스킬 활용도 상위권입니다. 그래서 **같은 영웅·티어 안에서 에임 지표 순위와 비(非)에임 지표 순위의 차이**를 신호로 쓸 수 있습니다. PUBG 프로젝트에서 서로 상관이 낮은 두 축(교전량, 정확도)을 따로 본 것과 같은 방식으로, 오버워치에서는 에임 축과 운영 축을 나눠서 두 축의 순위가 크게 벌어지는 경우를 찾는 것입니다.

**단, 이 신호는 티어에 따라 무게가 다릅니다.** 낮은 티어와 중간 티어에서는 에임만으로도 이길 수 있어서, 운영은 부족하지만 에임이 좋은 정상 플레이어가 실제로 많습니다. 반면 최상위 티어는 에임만으로 올라갈 수 없고 운영 능력이 함께 있어야 합니다. 그래서

- 높은 티어에서 에임과 운영이 크게 안 맞으면 → 강한 신호
- 낮은 티어에서 같은 차이가 나면 → 흔한 정상 패턴이라 약한 신호 (그대로 쓰면 오탐이 많아짐)

로 보고, 같은 기준을 모든 티어에 똑같이 적용하지 않고 **티어별 분포 안에서** 비교해야 합니다. PUBG에서 "전체 기준이 아니라 같은 매치 안에서 비교"한 것과 같은 이유입니다.

**소프트 리셋 직후는 따로 봐야 합니다.** 시즌 주기에 따라 소프트 리셋이 되면 실력자도 원래보다 낮은 구간에서 배치를 다시 시작합니다. 직접 겪어 보면 리셋 직후의 배치 구간에는 원래 상위 티어인 플레이어가 섞여 있습니다. 이 시기에는 "티어에 비해 실력이 너무 좋다"는 신호가 핵이 아니라 배치 중인 실력자에게 걸리기 쉽습니다. 그래서 현재 티어만 보지 말고 **리셋 전 최고 티어나 최근 경기 수**를 함께 보고, 리셋 직후 기간은 기준을 다르게 두어야 오탐을 줄일 수 있습니다.

### 핵심 아이디어 2: 가진 정보에 비해 행동이 너무 공격적인 것

정상 플레이어는 적이 어디 있는지 모르면 사리거나 방어적으로 움직입니다. 정보가 생겨야(적이 보이거나, 팀원이 위치를 알려주거나, 소리가 들리거나) 공격적으로 들어갑니다. 그런데 월핵을 의심했던 경우는 **위치 정보가 없는 상황인데도 적이 있는 쪽으로 오히려 공격적으로 파고들어서 따내는** 모습이었습니다. 마치 위치를 다 알고 있는 것처럼요.

즉 신호는 공격성 자체가 아니라 **그 순간 가진 정보량과 행동의 공격성이 맞지 않는 것**입니다. 원래 공격적인 플레이 스타일인 사람은 정보가 없을 때도 공격적이지만, 그만큼 손해 보는 교전도 많습니다. 월핵이면 정보 없이 들어간 교전에서도 승률이 비정상적으로 높습니다.

### 사례: 빠른 대전에서 만난 챔피언 티어 아나

- 빠른 대전이라는 점을 감안해도 위치 선정과 스킬샷(수면총, 생체 수류탄)이 챔피언 티어로 볼 수 없는 수준이었음
- 우클릭(줌) 조준 사격은 평범했음
- 벽 뒤에서 나올 적을 미리 조준하고 있는 장면이 보였음
- **좌클릭(줌 없이 쏘는 투사체)의 명중률이 비정상적으로 높았음.** 움직이는 대상에게도 유도탄처럼 거의 다 맞음

이 사례에서 얻은 신호는 두 가지입니다.

1. **같은 영웅의 사격 방식끼리 안 맞음**: 아나의 줌 사격은 즉시 맞는 방식(히트스캔)이고 줌 없는 사격은 날아가는 투사체입니다. 투사체는 상대 움직임을 예측해야 해서 보통 더 어렵습니다. 그런데 어려운 쪽 명중률만 극단적으로 높고 쉬운 쪽은 평범했습니다. 핵이 특정 사격 방식에만 적용됐을 가능성이 있고, 같은 영웅의 사격 방식별 명중률 비율은 로그로 계산할 수 있습니다.
2. **티어와 운영 실력이 안 맞음**: 계정 티어는 챔피언인데 에임을 뺀 실력이 그 티어 분포와 맞지 않았습니다.

### 유형별 신호 정리

| 유형 | 플레이하면서 본 모습 | 로그로 확인할 신호 | 정상 플레이와 헷갈리는 경우 |
|---|---|---|---|
| 에임봇 | 에임만 좋고 무빙·위치 선정·스킬 활용은 부족, 에임을 믿고 몸이 앞으로 쏠림 | 같은 영웅·티어 안에서 에임 지표 순위와 운영 지표(엄폐 시간, 스킬 적중, 사망 위치) 순위의 차이 | 낮은·중간 티어의 "에임만 좋은" 정상 플레이어 (그래서 높은 티어일수록 강한 신호로 봄), 에임 연습만 많이 한 플레이어 |
| 에임봇 (목표 전환) | 영웅 여러 명이 겹칠 때 조준이 프레임 단위로 뚝뚝 끊기며 대상을 옮겨 다님 | 조준 이동이 한 프레임 안에 대상에서 대상으로 끊기는 횟수, 이동 속도가 0으로 바로 멈추는 패턴 | 네트워크 지연, 리플레이 재생 오류 |
| 월핵 + 반응 | 시야나 위치 정보가 없는데 벽 뒤에서 나올 적을 미리 조준하고 있다가, 나오는 순간 사람이 낼 수 없는 속도로 쏨 | 적이 보이기 시작한 시점부터 명중까지 걸린 시간이 사람 반응 시간 분포보다 짧은 비율, 정보(팀원 핑, 소리) 없이 사전 조준한 횟수 | 소리 정보, 팀원 콜, 맵과 상대 동선을 아는 숙련자 |
| 월핵 (공격적 동선) | 적 위치를 모를 상황인데 사리지 않고 적이 있는 쪽으로 곧장 파고들어 따냄 | 정보 없이 시작한 교전의 비율과 그 교전의 승률, 보이지 않는 적 방향으로 이동한 비율 | 원래 공격적인 스타일(정보 없는 교전 승률은 평범), 상대 동선을 읽는 숙련자 |
| 특정 사격 방식에만 적용된 핵 | 아나의 줌 사격은 평범한데 줌 없는 투사체가 유도탄처럼 맞음 | 같은 영웅의 사격 방식별 명중률 비율이 그 영웅 분포에서 극단값 | 한 사격 방식만 집중 연습한 플레이어 |
| 대리 게임 / 계정 구매 | 티어에 비해 운영 실력이 맞지 않음 | 계정 티어와 운영 지표 수준의 차이, 같은 계정의 주 영웅·명중률·접속 시간대가 갑자기 바뀜 | 새 영웅 연습, 주 역할이 아닌 역할 플레이, 소프트 리셋 직후 배치 중인 실력자 |

여러 신호 중 서로 상관이 낮은 것들을 조합하고, 여러 개에 동시에 걸린 경우를 우선 검토 대상으로 둡니다.

### 리플레이만으로는 판단하기 어려운 이유

- 통계 신호는 "확인할 대상을 좁히는" 역할입니다. 최종 판단은 리플레이 확인이나 클라이언트 탐지 같은 다른 근거와 함께 해야 오탐으로 정상 플레이어를 제재하는 일을 막을 수 있습니다.

import sqlite3
import statistics

MODE = "squad"  # 분석할 게임 모드

conn = sqlite3.connect("pubg.db")
cur = conn.cursor()

# 1) 연습장 제외 + 한 모드만 가져오기
rows = cur.execute(
    """
    SELECT p.kills, p.damage_dealt, p.headshot_kills, p.time_survived
    FROM participants p
    JOIN matches m ON p.match_id = m.match_id
    WHERE m.map_name != 'Range_Main' AND m.game_mode = ?
    """,
    (MODE,),
).fetchall()
print(f"모드 {MODE}: 참가자 {len(rows)}명")

# 2) 피해량 분포와 이상치 기준선 계산
damages = [r[1] for r in rows]
q1, q2, q3 = statistics.quantiles(damages, n=4)
fence = q3 + 3 * (q3 - q1)
print(f"피해량 Q1={q1:.0f}, 중앙값={q2:.0f}, Q3={q3:.0f}, 기준선={fence:.0f}")

# 3) 기준선을 넘은 플레이어
flagged = [r for r in rows if r[1] > fence]
print(f"기준선 초과: {len(flagged)}명 ({len(flagged) / len(rows) * 100:.1f}%)")

print("초과자 상위 10명:")
for kills, dmg, hs, surv in sorted(flagged, key=lambda r: -r[1])[:10]:
    print(f"  킬 {kills}, 피해량 {dmg:.0f}, 헤드샷킬 {hs}, 생존 {surv / 60:.1f}분")

# 4) 헤드샷 비율 비교 (킬 5 이상인 사람만)
def headshot_rate(group):
    g = [r for r in group if r[0] >= 5]
    total_kills = sum(r[0] for r in g)
    if total_kills == 0:
        return "해당자 없음"
    return f"{sum(r[2] for r in g) / total_kills:.2f} (대상 {len(g)}명)"

print("헤드샷 비율 - 전체:", headshot_rate(rows))
print("헤드샷 비율 - 초과자:", headshot_rate(flagged))

conn.close()

import sqlite3
import statistics

MODE = "squad"

conn = sqlite3.connect("pubg.db")
cur = conn.cursor()

rows = cur.execute(
    """
    SELECT p.kills, p.damage_dealt, p.headshot_kills,
           p.time_survived, p.win_place
    FROM participants p
    JOIN matches m ON p.match_id = m.match_id
    WHERE m.map_name != 'Range_Main' AND m.game_mode = ?
    """,
    (MODE,),
).fetchall()

# 1) 기준선 계산 (이전과 같은 방식)
damages = [r[1] for r in rows]
q1, _, q3 = statistics.quantiles(damages, n=4)
fence = q3 + 3 * (q3 - q1)

flagged = [r for r in rows if r[1] > fence]
normal = [r for r in rows if r[1] <= fence]

# 2) 초과자 vs 나머지: 순위와 생존 시간 (순위는 숫자가 작을수록 좋음)
for name, g in [("초과자", flagged), ("나머지", normal)]:
    place = statistics.median(r[4] for r in g)
    surv = statistics.median(r[3] for r in g) / 60
    print(f"{name} {len(g)}명: 순위 중앙값 {place}, 생존 중앙값 {surv:.1f}분")

# 3) 헤드샷 비율: 킬 3 이상인 사람만, 초과자 vs 나머지를 따로
def hs_rate(group):
    g = [r for r in group if r[0] >= 3]
    kills = sum(r[0] for r in g)
    if kills == 0:
        return "해당자 없음"
    return f"{sum(r[2] for r in g) / kills:.2f} (대상 {len(g)}명)"

print("헤드샷 비율 - 초과자:", hs_rate(flagged))
print("헤드샷 비율 - 나머지:", hs_rate(normal))

# 4) 분당 피해량 상위 5명 (5분 이상 생존한 사람만)
timed = [r for r in rows if r[3] >= 300]
timed.sort(key=lambda r: -(r[1] / (r[3] / 60)))
print("분당 피해량 상위 5명:")
for kills, dmg, hs, surv, place in timed[:5]:
    print(f"  분당 피해량 {dmg / (surv / 60):.0f}, 킬 {kills}, 생존 {surv / 60:.1f}분, 순위 {place}")

conn.close()

import json
import glob
import sqlite3
from collections import Counter

conn = sqlite3.connect("pubg.db")
cur = conn.cursor()

# 1) DB에 매치별로 몇 명이 들어갔는지
db_counts = dict(
    cur.execute("SELECT match_id, COUNT(*) FROM participants GROUP BY match_id")
)

# 2) 원본 JSON의 참가자 수와 비교
raw_total = 0
mismatch = 0
modes = Counter()

for path in glob.glob("data/*.json"):
    with open(path, encoding="utf-8") as f:
        data = json.load(f)

    match_id = data["data"]["id"]
    modes[data["data"]["attributes"]["gameMode"]] += 1

    raw = sum(1 for i in data["included"] if i["type"] == "participant")
    raw_total += raw
    saved = db_counts.get(match_id, 0)

    if raw != saved:
        mismatch += 1
        print(f"불일치: {match_id[:8]}... 원본 {raw}명 / DB {saved}명")

print("원본 참가자 합계:", raw_total, "/ DB 행 수:", sum(db_counts.values()))
print("불일치 매치 수:", mismatch)
print("게임 모드별 매치 수:", dict(modes))

# 3) 매치당 참가자 수 분포
print(
    "매치당 참가자 수 (최소, 최대, 평균):",
    cur.execute(
        "SELECT MIN(c), MAX(c), AVG(c) FROM "
        "(SELECT COUNT(*) AS c FROM participants GROUP BY match_id)"
    ).fetchone(),
)

conn.close()

import json
import glob
from collections import Counter, defaultdict

# 모드별로 "roster 하나에 몇 명이 들어 있는지" 분포 세기
sizes = defaultdict(Counter)

for path in glob.glob("data/*.json"):
    with open(path, encoding="utf-8") as f:
        data = json.load(f)

    mode = data["data"]["attributes"]["gameMode"]
    if data["data"]["attributes"]["mapName"] == "Range_Main":
        continue  # 연습장 매치는 제외

    for item in data["included"]:
        if item["type"] == "roster":
            n = len(item["relationships"]["participants"]["data"])
            sizes[mode][n] += 1

for mode, counter in sizes.items():
    print(f"{mode}: roster 인원수별 개수 {dict(sorted(counter.items()))}")

# 연습장 맵은 제외하고 보기 위한 공통 조건
BASE = """
FROM participants p
JOIN matches m ON p.match_id = m.match_id
WHERE m.map_name != 'Range_Main'
"""

def run(title, query):
    result = cur.execute(query).fetchall()
    print(f"[{title}]")
    for row in result:
        print("  ", row)
    print()

# 1) 분석 대상 규모
run("분석 대상 (매치 수, 참가자 수)",
    "SELECT COUNT(DISTINCT p.match_id), COUNT(*) " + BASE)

# 2) 누락값(NULL) 개수
run("NULL 개수 (kills, damage_dealt, time_survived, win_place)",
    "SELECT SUM(p.kills IS NULL), SUM(p.damage_dealt IS NULL), "
    "SUM(p.time_survived IS NULL), SUM(p.win_place IS NULL) " + BASE)

# 3) 음수 값
run("음수 값이 있는 행",
    "SELECT COUNT(*) " + BASE +
    " AND (p.kills < 0 OR p.damage_dealt < 0 OR p.time_survived < 0 "
    "OR p.walk_distance < 0 OR p.ride_distance < 0)")

# 4) 헤드샷 킬이 전체 킬보다 많은 경우 (논리 오류)
run("헤드샷 킬 > 킬인 행",
    "SELECT COUNT(*) " + BASE + " AND p.headshot_kills > p.kills")

# 5) 생존 시간이 매치 진행 시간보다 긴 경우 (여유 10초)
run("생존 시간 > 매치 시간 + 10초인 행",
    "SELECT COUNT(*) " + BASE + " AND p.time_survived > m.duration + 10")

# 6) 순위 범위
run("순위 범위 (win_place 최소, 최대)",
    "SELECT MIN(p.win_place), MAX(p.win_place) " + BASE)

conn.close()

    data = response.json()["data"]
    new_ids = [m["id"] for m in data["relationships"]["matches"]["data"]]
    print("받은 매치 수:", len(new_ids))

    # 4) 기존 목록에 새 ID만 추가 (덮어쓰지 않음)
    #    매일 실행하면 목록이 누적되고, 수집 단계에서 이미 받은 것은 건너뛴다
    old_ids = []
    if os.path.exists("match_ids.txt"):
        with open("match_ids.txt") as f:
            old_ids = f.read().splitlines()
    known = set(old_ids)
    added = [m for m in new_ids if m not in known]

    # 새 ID를 앞에 둔다: /samples ID는 시간이 지나면 만료되므로 최신 것부터 받기 위해
    with open("match_ids.txt", "w") as f:
        f.write("\n".join(added + old_ids))

```py
import os
import subprocess
import sys
from datetime import datetime

# 전체 파이프라인을 순서대로 실행한다: 목록 수집 -> 상세 수집 -> DB 구축 -> 품질 점검 -> 분석
# 한 단계라도 실패하면 거기서 멈춘다 (특히 품질 점검이 실패하면 분석으로 넘어가지 않음)
# 하루 1회 자동 실행은 README의 "자동 실행" 참고

STEPS = [
    ("매치 목록 수집", "get_samples.py"),
    ("매치 상세 수집", "collect_matches.py"),
    ("DB 구축", "build_db.py"),
    ("품질 점검", "validate.py"),
    ("SQL 분석", "analyze_sql.py"),
]

# 스케줄러로 실행할 때도 이 파일이 있는 폴더 기준으로 동작하게 한다
os.chdir(os.path.dirname(os.path.abspath(__file__)))
os.makedirs("logs", exist_ok=True)
log_path = f"logs/pipeline_{datetime.now():%Y%m%d}.log"
env = {**os.environ, "PYTHONIOENCODING": "utf-8"}


def log(msg):
    line = f"[{datetime.now():%Y-%m-%d %H:%M:%S}] {msg}"
    print(line)
    with open(log_path, "a", encoding="utf-8") as f:
        f.write(line + "\n")


log("파이프라인 시작")
for name, script in STEPS:
    log(f"{name} ({script}) 시작")
    result = subprocess.run([sys.executable, script], capture_output=True,
                            text=True, encoding="utf-8", env=env)

-- 킬 수 구간별 헤드샷 비율: 표본(킬 수)이 작을수록 비율이 극단값(0% 또는 100%)으로 튄다

        WHEN kills = 2 THEN '2킬'
        WHEN kills BETWEEN 3 AND 4 THEN '3~4킬'
        WHEN kills BETWEEN 5 AND 9 THEN '5~9킬'
        ELSE '10킬 이상'
    END AS kill_group,
    COUNT(*) AS players,

    ROUND(AVG(CASE WHEN headshot_kills = kills THEN 1.0 ELSE 0 END) * 100, 1) AS pct_hs_100
FROM clean_squad
WHERE kills >= 1
GROUP BY kill_group
ORDER BY MIN(kills);

`sql/05_dpm_match_zscore.sql`:

```sql
-- 매치 안에서 비교한 분당 피해량 z-score
-- 매치마다 로비 수준이 달라서, 전체 기준이 아니라 "같은 매치 사람들 대비" 얼마나 벗어났는지 본다
-- z = (내 분당 피해량 - 매치 평균) / 매치 표준편차
-- SQLite에는 표준편차 함수가 없어서 sqrt(제곱의 평균 - 평균의 제곱)으로 계산한다
-- 주의: 교전이 거의 없던 매치는 표준편차가 작아서 z가 크게 튄다 (분당 피해량 6.0인데 z 5.57이 나온 행이 그 예).
--       그래서 06번 검토 후보에서는 전체 상위 10% 하한을 함께 건다
WITH base AS (
    SELECT match_id, player_id, kills, headshot_kills, damage_dealt,
           time_survived, win_place,
           damage_dealt / (time_survived / 60.0) AS dpm      -- 분당 피해량
    FROM clean_squad
    WHERE time_survived >= 300                              -- 5분 미만 생존자는 분모가 작아 수치가 튐
),
match_stats AS (
    SELECT *,
           AVG(dpm) OVER w AS match_avg,
           SQRT(AVG(dpm * dpm) OVER w - AVG(dpm) OVER w * AVG(dpm) OVER w) AS match_sd,
           COUNT(*) OVER w AS match_n
    FROM base
    WINDOW w AS (PARTITION BY match_id)
)
SELECT match_id, player_id, kills, ROUND(damage_dealt) AS damage,
       ROUND(time_survived / 60.0, 1) AS survival_min, win_place,
       ROUND(dpm, 1) AS dpm, ROUND(match_avg, 1) AS match_avg,
       ROUND((dpm - match_avg) / match_sd, 2) AS z
FROM match_stats
WHERE match_n >= 20        -- 비교할 사람이 20명 미만인 매치는 평균이 불안정해서 제외
  AND match_sd > 0
ORDER BY z DESC
LIMIT 10;

```

`sql/06_review_candidates.sql`:

```sql
-- 검토 후보 목록: 서로 독립적인 두 축으로 신호를 만든다
--
-- 축 A (교전량): 분당 피해량이
--     (1) 같은 매치 사람들 대비 z >= 3 이고 (매치 비교 인원 20명 이상)
--     (2) 전체 정제 데이터에서도 상위 10% (PERCENT_RANK >= 0.9)
--     (2)를 넣은 이유: 교전이 거의 없던 매치는 평균·표준편차가 0에 가까워서
--     분당 피해량 6 정도로도 z가 5를 넘었다. 절대 수준 하한으로 이런 경우를 거른다.
-- 축 B (정확도): 헤드샷 비율 상위 5% (킬 5 이상인 사람 중)
--     킬 5 미만은 표본이 작아 비율이 0% 또는 100%로 튀므로 제외한다 (04번 쿼리 참고)
--
-- 킬 수 신호는 뺐다: 분당 피해량과 상관계수 0.64라 같은 것을 두 번 세게 된다.
-- 헤드샷 비율은 킬 수·분당 피해량과 상관이 거의 없다(-0.02).
--
-- 우선순위: 두 축 모두 걸리면 '우선 검토', 하나만 걸리면 '일반 검토'
-- 결과는 "부정행위 확정"이 아니라 사람이 리플레이 등으로 확인할 "검토 후보"다
WITH base AS (
    SELECT *,
           CASE WHEN time_survived >= 300
                THEN damage_dealt / (time_survived / 60.0) END AS dpm
    FROM clean_squad
),
dpm_stats AS (
    SELECT match_id, player_id,
           (dpm - AVG(dpm) OVER w)
             / SQRT(AVG(dpm * dpm) OVER w - AVG(dpm) OVER w * AVG(dpm) OVER w) AS dpm_z,
           COUNT(*) OVER w AS match_n,
           PERCENT_RANK() OVER (ORDER BY dpm) AS dpm_pct
    FROM base
    WHERE dpm IS NOT NULL
    WINDOW w AS (PARTITION BY match_id)
),
hs_stats AS (
    SELECT match_id, player_id,
           PERCENT_RANK() OVER (ORDER BY headshot_kills * 1.0 / kills) AS hs_pct
    FROM base
    WHERE kills >= 5
),
signals AS (
    SELECT b.match_id, b.player_id, b.match_type, b.kills, b.headshot_kills,
           ROUND(b.headshot_kills * 1.0 / NULLIF(b.kills, 0), 2) AS hs_ratio,
           ROUND(b.damage_dealt) AS damage,
           ROUND(b.time_survived / 60.0, 1) AS survival_min,
           b.win_place,
           ROUND(b.dpm, 1) AS dpm,
           ROUND(d.dpm_z, 2) AS dpm_z,
           ROUND(d.dpm_pct, 3) AS dpm_pct,
           ROUND(h.hs_pct, 3) AS hs_pct,
           CASE WHEN d.match_n >= 20 AND d.dpm_z >= 3 AND d.dpm_pct >= 0.9
                THEN 1 ELSE 0 END AS s_engage,
           CASE WHEN h.hs_pct >= 0.95 THEN 1 ELSE 0 END AS s_accuracy
    FROM base b
    LEFT JOIN dpm_stats d ON b.match_id = d.match_id AND b.player_id = d.player_id
    LEFT JOIN hs_stats  h ON b.match_id = h.match_id AND b.player_id = h.player_id
)
SELECT *,
       CASE WHEN s_engage + s_accuracy = 2 THEN '우선 검토' ELSE '일반 검토' END AS priority
FROM signals
WHERE s_engage + s_accuracy >= 1
ORDER BY s_engage + s_accuracy DESC, s_accuracy DESC, dpm_z DESC;

```

def make_db():
    """테스트용 작은 DB (메모리에만 만들어짐)"""

        CREATE TABLE participants (match_id TEXT, player_id TEXT, is_bot INTEGER,

`validate.py`:

```py
import glob
import json
import os
import sqlite3
import sys
from datetime import datetime

# 데이터 품질 자동 점검
# - 기존 exploration/check_*.py에서 눈으로 확인하던 항목을 "통과/실패"로 판정한다
# - 결과는 화면과 logs/validation_날짜.log에 남기고, 실패가 있으면 종료 코드 1을 돌려준다
#   (파이프라인이 실패한 데이터로 분석까지 넘어가지 않게 하기 위해)

# 참가자가 0~1명이어도 정상인 매치 종류 (원본 JSON으로 확인함)
#   trainingroom: 훈련장. duration 0, 참가자 데이터 자체가 없음
#   tutorialatoz: 튜토리얼. 혼자 플레이
NON_GAME_TYPES = ("trainingroom", "tutorialatoz")


def count_raw_participants(data_dir="data"):
    """원본 JSON의 매치별 참가자 수"""
    counts = {}
    for path in glob.glob(f"{data_dir}/*.json"):
        with open(path, encoding="utf-8") as f:
            data = json.load(f)
        counts[data["data"]["id"]] = sum(
            1 for i in data["included"] if i["type"] == "participant"
        )
    return counts


def run_checks(conn, raw_counts):
    """점검 항목을 실행하고 (이름, 통과 여부, 상세) 목록을 돌려준다"""
    cur = conn.cursor()
    one = lambda q: cur.execute(q).fetchone()[0]
    results = []

    # 1) 원본과 DB 대조: 매치 수, 매치별 참가자 수
    db_counts = dict(cur.execute(
        "SELECT match_id, COUNT(*) FROM participants GROUP BY match_id"
    ))
    db_matches = one("SELECT COUNT(*) FROM matches")
    results.append(("원본 매치 수 = DB 매치 수",
                     db_matches == len(raw_counts),
                     f"원본 {len(raw_counts)} / DB {db_matches}"))

    mismatch = [m for m, n in raw_counts.items() if db_counts.get(m, 0) != n]
    results.append(("매치별 참가자 수 원본과 일치",
                     len(mismatch) == 0,
                     f"불일치 {len(mismatch)}건"))

    # 2) 중복: 같은 매치에 같은 플레이어가 두 번 들어갔는지
    dup = one("SELECT COUNT(*) FROM (SELECT 1 FROM participants "
              "GROUP BY match_id, player_id HAVING COUNT(*) > 1)")
    results.append(("(매치, 플레이어) 중복 없음", dup == 0, f"{dup}건"))

    # 3) 참가자 0~1명 매치는 훈련장·튜토리얼이어야 함
    placeholders = ",".join("?" * len(NON_GAME_TYPES))
    odd = cur.execute(f"""
        SELECT COUNT(*) FROM matches m
        WHERE (SELECT COUNT(*) FROM participants p WHERE p.match_id = m.match_id) <= 1
          AND (m.match_type IS NULL OR m.match_type NOT IN ({placeholders}))
    """, NON_GAME_TYPES).fetchone()[0]
    results.append(("참가자 0~1명 매치는 모두 훈련장/튜토리얼", odd == 0,
                    f"원인 불명 {odd}건"))

    # 4) 값 검사: NULL, 음수, 논리 오류
    nulls = one("SELECT COUNT(*) FROM participants WHERE kills IS NULL "
                "OR damage_dealt IS NULL OR time_survived IS NULL OR win_place IS NULL")
    results.append(("주요 컬럼 NULL 없음", nulls == 0, f"{nulls}건"))

    neg = one("SELECT COUNT(*) FROM participants WHERE kills < 0 OR damage_dealt < 0 "
              "OR time_survived < 0 OR walk_distance < 0 OR ride_distance < 0")
    results.append(("음수 값 없음", neg == 0, f"{neg}건"))

    hs = one("SELECT COUNT(*) FROM participants WHERE headshot_kills > kills")
    results.append(("헤드샷 킬 <= 킬", hs == 0, f"위반 {hs}건"))

    over = one("SELECT COUNT(*) FROM participants p JOIN matches m "
               "ON p.match_id = m.match_id WHERE p.time_survived > m.duration + 10 "
               "AND m.match_type NOT IN ('trainingroom', 'tutorialatoz')")
    results.append(("생존 시간 <= 매치 시간 + 10초", over == 0, f"위반 {over}건"))

    # 5) 봇 표시가 player_id 규칙과 맞는지
    bot_bad = one("SELECT COUNT(*) FROM participants WHERE "
                  "(is_bot = 1) != (player_id LIKE 'ai.%')")
    results.append(("is_bot = player_id 'ai.' 여부", bot_bad == 0, f"불일치 {bot_bad}건"))

    return results


def main():
    conn = sqlite3.connect("pubg.db")
    results = run_checks(conn, count_raw_participants())
    conn.close()

    os.makedirs("logs", exist_ok=True)
    now = datetime.now()
    lines = [f"[{now:%Y-%m-%d %H:%M:%S}] 데이터 품질 점검"]
    for name, ok, detail in results:
        lines.append(f"  {'통과' if ok else '실패'} | {name} | {detail}")
    failed = sum(1 for _, ok, _ in results if not ok)
    lines.append(f"  결과: {len(results)}개 중 {len(results) - failed}개 통과")

    text = "\n".join(lines)
    print(text)
    with open(f"logs/validation_{now:%Y%m%d}.log", "a", encoding="utf-8") as f:
        f.write(text + "\n")

    sys.exit(1 if failed else 0)


if __name__ == "__main__":
    main()
