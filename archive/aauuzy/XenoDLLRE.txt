# Briefing: Xeno executor (v1.3.65)

**For:** Roblox security and anti-cheat teams
**From:** Gavin Hatcher ([github.com/aauuzy](https://github.com/aauuzy))
**Date:** November 2026
**Status:** Defensive research. Not a vulnerability report: everything described requires the user to run Xeno on their own machine.

## What Xeno is

A free Windows Roblox script executor in wide use. Its scale cannot be established from public data ([`docs/defense/THREAT_ASSESSMENT.md`](docs/defense/THREAT_ASSESSMENT.md) §2). The current public installer contains exactly the DLL analyzed here (`Xeno.dll` v1.3.65, SHA-256 `50318bc8…99049`).

## How it works

Xeno never loads a DLL or creates a thread in Roblox. It overwrites the bytecode of the built-in **en-us locale translation CoreScript module**, so Roblox runs Xeno's client as part of its own startup. That client talks to a **localhost HTTP server** in Xeno's DLL through `HttpService:RequestInternal`. User scripts run by having the DLL compile them and write the bytecode into a ModuleScript the client keeps `require()`ing. Memory offsets for each Roblox release are downloaded at runtime, which is why Xeno survives updates within hours.

## Key observations

1. Replaced CoreScript bytecode executes without an integrity check (G-1).
2. CoreScript context can reach arbitrary loopback ports over HTTP. This is Xeno's entire control plane (G-2).
3. Bytecode written into a `require()`d module from outside the process is executed (G-3).
4. Xeno's own deny-list suggests purchase, auth-cookie and messaging APIs may be reachable from its context (G-5, unverified).
5. Xeno harms its own users: every attached client runs code the developer publishes (`code.lua`), every script HTTP request leaks the user's hardware ID and game server, and fake "undetected" Xeno installers have spread an infostealer.

## Recommended actions

| Priority | Action | Effect on Xeno |
|---|---|---|
| 1 | Block loopback HTTP from client script contexts (C-2) | Removes its control plane |
| 1 | Record the en-us bytecode mismatch and CoreGui artifacts as telemetry (C-6, C-7) | Measures prevalence |
| 2 | Verify all CoreScript bytecode against the shipped build (C-1) | Removes its attach method |
| 2 | Reject out-of-band bytecode in `require()` (C-3) | Removes its execution method |
| 3 | Audit privileged APIs reachable from CoreScript context (C-5) | Protects executor users |

Details, risks and quick detection indicators: [`docs/defense/COUNTERMEASURES.md`](docs/defense/COUNTERMEASURES.md).

## Evidence

Static analysis only; nothing was executed and no Roblox or Xeno infrastructure was contacted. Every claim in [`docs/research/FINDINGS.md`](docs/research/FINDINGS.md) carries an evidence reference and a confidence level. # XenoDLLRE

Static reverse engineering of **Xeno v1.3.65**, a Roblox script executor, with detection tooling built from the results. The goal is to document how the executor works and what it leaves behind, for defensive and anti-cheat use. This repository does not contain or improve executor functionality.

## Summary

Xeno is a native x64 DLL (`Xeno.dll`) driven by an Electron UI. It does not load code into Roblox as a DLL or thread. It **replaces the bytecode of the en-us locale translation ModuleScript** under `RobloxGui.Modules`, so Roblox itself runs Xeno's client script when that module loads. The client then talks to a **localhost HTTP server** in the DLL, runs user scripts by having the DLL write compiled Luau bytecode into ModuleScripts it repeatedly `require()`s, and leaves distinctive objects in `CoreGui`.

The client script and a copy of Roblox's en-us table are embedded as resources protected by a **32-byte repeating XOR key over zstd**. The key was recovered from a CRT initializer and independently confirmed by known plaintext, and both resources were decrypted. On every attach the client also downloads and runs `code.lua` from the developer's host, which lets the developer push arbitrary code into every attached session without shipping a new DLL.

All of this is static analysis. Nothing was executed. Each claim in [`docs/research/FINDINGS.md`](docs/research/FINDINGS.md) carries an evidence reference and a confidence level.

## Key results

| | Result | Confidence |
|---|---|---|
| Attach | Bytecode replacement of the en-us translation ModuleScript (F-30) | Strongly supported |
| Execution | Local `require()` loop on random-named ModuleScripts; DLL compiles and writes bytecode (F-40, F-41) | Confirmed (client) / Strongly supported (DLL) |
| Protocol | `POST /f?e=<0-21>` plus `/ls`, `/rq`, `/qt`, `/cb` on localhost (F-51, F-52) | Confirmed (client) |
| Resources | XOR key `3EFD5045…A92AF5BB` + zstd; unchanged from v1.3.40 (F-60, F-61) | Confirmed |
| Remote code | `code.lua` fetched and executed on every attach (F-63) | Confirmed (client) |
| Signing | Self-signed `CN=Rizve A` Authenticode certificate with a Sectigo timestamp; usable as a detection indicator (F-04) | Confirmed |
| Identifier leakage | Script HTTP requests send the user's HWID (`exploit-guid`, `xeno-fingerprint`) and current game server to any host (F-54) | Confirmed (client) |
| Artifacts | `CoreGui/<pid>` folder with `Message` "DO NOT DELETE: BELONGS TO XENO", `shared.__Xeno` (F-70, F-71) | Confirmed |
| Platform vulnerability | None established ([`docs/DISCLOSURE.md`](docs/DISCLOSURE.md)) | — |

```py
#!/usr/bin/env python3
"""Score-based scanner for Xeno-family executor DLLs.

Built from static analysis of Xeno v1.3.40 and v1.3.65. See docs/defense/DETECTION.md.

Usage: python xeno_detector.py <file-or-directory> [-v]

Verdicts:
  PE files     score >= 60  -> "xeno (heuristic)"
               score 30-59  -> "executor-family (suspicious)"
  non-PE files any hit      -> "xeno strings (non-PE)"  (memory dumps, scripts, reports)

Thresholds are heuristics validated only against two Xeno builds and the benign set described
in docs/defense/DETECTION.md. Treat results as leads, not verdicts.
"""
import argparse
import datetime
import os
import sys

try:
    import pefile
except ImportError:
    sys.exit("pip install pefile")

XOR_KEY = bytes.fromhex(
    "3EFD5045ED61BFCA57EFA192D0076696"
    "FDC5F72112BD49367A3FB319A92AF5BB"
)
ZSTD_MAGIC = b"\x28\xb5\x2f\xfd"
RESOURCE_TYPE = 8194
SIGNER_SUBJECT = b"Rizve A"
EXPORT_SET = {"Attach", "Execute", "GetClients", "Initialize", "SetSetting", "Version"}
PE_THRESHOLD_XENO = 60
PE_THRESHOLD_FAMILY = 30

STRING_INDICATORS = [
    ("credit_rizve",     35, [b"Xeno is only maintained by Rizve", b"rizve@xeno.onl"]),
    ("pdb_path",         35, [b"Projects\\Xeno\\build\\Release\\net9.0-windows8.0\\Xeno.pdb"]),
    ("attach_module",    30, [b"Intercepted translation module @",
                              b"Attaching in-game using translation module."]),
    ("xeno_resource",    30, [b"Could not decompress a Xeno resource"]),
    ("xeno_server",      20, [b"Xeno Server is Live on http://localhost:"]),
    ("offsets_endpoint", 20, [b"https://x3no.pages.dev/ep.zst.enc"]),
    ("env_vars",         15, [b"%XENO_CLIENT_PID%", b"%XENO_SERVER_PORT%"]),
    ("port3110",         10, [b"localhost:3110"]),
    ("xor_key_raw",      35, [XOR_KEY]),
    ("xor_key_init",     35, [bytes.fromhex("C7003EFD5045C74004ED61BFCA")]),
    ("client_lua",       35, [b"DO NOT DELETE: BELONGS TO XENO", b"CLIENT.LUA -- POST OPEN SOURCE"]),
    ("code_push_url",    20, [b"https://x3no.pages.dev/code.lua"]),
    ("luau_fflags",      10, [b"LuauSolverV2", b"LuauCompileInlineThreshold"]),
    ("zstd_errors",      10, [b"ERROR_frameType_unknown", b"ERROR_blockChecksum_invalid"]),
]


def resource_decrypts(blob, key=XOR_KEY):
    """True if the blob's first 4 bytes XOR the key prefix to the zstd frame magic."""
    return len(blob) >= 4 and bytes(b ^ k for b, k in zip(blob[:4], key)) == ZSTD_MAGIC


def iter_resources(pe):
    """Yield (type_id, name_id, data) for every leaf in the resource directory."""
    if not hasattr(pe, "DIRECTORY_ENTRY_RESOURCE"):
        return
    image = pe.get_memory_mapped_image()
    for rtype in pe.DIRECTORY_ENTRY_RESOURCE.entries:
        if not hasattr(rtype, "directory"):
            continue
        for rname in rtype.directory.entries:
            if not hasattr(rname, "directory"):
                continue
            for lang in rname.directory.entries:
                off, size = lang.data.struct.OffsetToData, lang.data.struct.Size
                yield rtype.id, rname.id, image[off:off + size]


def certificate_table(pe, raw):
    """Bytes of the Authenticode certificate table (empty if the file is not signed)."""
    entry = pe.OPTIONAL_HEADER.DATA_DIRECTORY[
        pefile.DIRECTORY_ENTRY["IMAGE_DIRECTORY_ENTRY_SECURITY"]]
    return raw[entry.VirtualAddress:entry.VirtualAddress + entry.Size] if entry.Size else b""


def scan_pe(pe, raw):
    hits, score = [], 0
    if SIGNER_SUBJECT in certificate_table(pe, raw):
        hits.append("signer_rizve_cert")
        score += 35
    if hasattr(pe, "DIRECTORY_ENTRY_EXPORT"):
        names = {s.name.decode(errors="replace")
                 for s in pe.DIRECTORY_ENTRY_EXPORT.symbols if s.name}
        matched = EXPORT_SET & names
        if matched == EXPORT_SET:
            hits.append("export_contract_full")
            score += 25
        elif len(matched) >= 4:
            hits.append(f"export_contract_partial({len(matched)}/6)")
            score += 10
    for rtype, rname, blob in iter_resources(pe):
        if rtype != RESOURCE_TYPE:
            continue
        if resource_decrypts(blob):
            hits.append(f"resource_{RESOURCE_TYPE}_decrypts(id={rname})")
            score += 35
        else:
            hits.append(f"resource_{RESOURCE_TYPE}(id={rname})")
            score += 5
    return score, hits


def scan_file(path):
    with open(path, "rb") as f:
        raw = f.read()
    hits, score = [], 0
    for name, weight, needles in STRING_INDICATORS:
        if any(n in raw for n in needles):
            hits.append(name)
            score += weight

    try:
        pe = pefile.PE(data=raw, fast_load=True)
    except pefile.PEFormatError:
        return score, ("xeno strings (non-PE)" if hits else "no match"), hits

    pe.parse_data_directories(directories=[
        pefile.DIRECTORY_ENTRY["IMAGE_DIRECTORY_ENTRY_EXPORT"],
        pefile.DIRECTORY_ENTRY["IMAGE_DIRECTORY_ENTRY_RESOURCE"],
    ])
    pe_score, pe_hits = scan_pe(pe, raw)
    score += pe_score
    hits += pe_hits
    if pe.FILE_HEADER.TimeDateStamp > datetime.datetime.now(datetime.UTC).timestamp():
        hits.append("note:future_timestamp")

    if score >= PE_THRESHOLD_XENO:
        verdict = "xeno (heuristic)"
    elif score >= PE_THRESHOLD_FAMILY:
        verdict = "executor-family (suspicious)"
    else:
        verdict = "no match"
    return score, verdict, hits


def iter_paths(target):
    if os.path.isdir(target):
        for root, dirs, files in os.walk(target):
            dirs[:] = [d for d in dirs if d != ".git"]
            for f in files:
                yield os.path.join(root, f)
    else:
        yield target


def main():
    ap = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    ap.add_argument("target", help="file or directory to scan")
    ap.add_argument("-v", "--verbose", action="store_true", help="print every file and all hits")
    a = ap.parse_args()

    for p in iter_paths(a.target):
        try:
            score, verdict, hits = scan_file(p)
        except OSError as e:
            print(f"{p}\n  error: {e}", file=sys.stderr)
            continue
        if verdict != "no match" or a.verbose:
            print(f"{p}\n  score={score}  verdict={verdict}")
            for h in hits:
                print(f"    + {h}")


if __name__ == "__main__":
    main()

```md
# Security assessment and disclosure

How the findings relate to Roblox's security boundaries, why nothing here has been reported as a vulnerability, and what this repository deliberately does not publish.

## Threat model

Roblox treats the game client as untrusted. Xeno runs only because a user installs it and lets it write into their own Roblox process. Anything that depends on that starting point is a person modifying software on their own device, which is a Terms of Use matter rather than a breach of a Roblox security boundary. Three categories need to be kept apart:

| Category | Who owns the problem | Examples in this research |
|---|---|---|
| Client-side manipulation by the device owner | Roblox anti-cheat and client integrity (detection, not vulnerability) | Bytecode replacement in the en-us module (F-30), execution loop (F-40), in-game artifacts (F-70–F-72) |
| Experiences accepting what a modified client sends | The experience developer (server-side validation) | Any gameplay advantage scripts gain; not analyzed here |
| A Roblox-controlled boundary crossed without the attacker already controlling the victim's machine | Roblox security (bounty-eligible) | **None established** |

## Classification of notable findings

**Attach and execution (F-30, F-40–F-46).** Detection intelligence. Valuable to anti-cheat work because it describes how the bytecode is replaced and which artifacts persist, but it requires native code with write access to the user's own Roblox process.

**Remote code channel (F-63).** Every attached client fetches and runs `code.lua` from the developer's host with the full Xeno environment. This is a risk to Xeno's users (whoever controls that host controls every attached session), not a Roblox vulnerability.

**Identifier leakage (F-54, F-92).** Script HTTP requests send the user's hardware identifier and current game server to any host a script contacts. This is a privacy risk to Xeno's users created by Xeno, not a Roblox issue.

**Service deny-list (F-90).** Xeno blocks its own scripts from purchase, authentication-cookie, analytics and messaging APIs and calls this "vulnerabilities mitigation". This suggests those APIs are reachable from the context Xeno's scripts run in, which would mean malicious scripts shared among Xeno users (or the `code.lua` channel) could act on the user's account. Reachability has not been tested. Even if confirmed, the precondition is still the user running Xeno, so it is user-safety information rather than a platform vulnerability.

## HackerOne position

Based on Roblox's HackerOne policy (version dated 2026-03-04, read 2026-11-10; always check the live policy before testing or submitting):

- Engine and client security work such as memory corruption, sandbox escapes and RCE chains is in scope, and minimal proofs of concept are accepted. Data-model bugs that let exploiters crash game servers are explicitly encouraged.
- The policy prohibits distributing executors, cheats or bypass frameworks; building telemetry-bypass frameworks; automating exploit deployment; developing reliable arbitrary-code chains against production clients without authorization; and testing against Roblox's server, control-plane or management infrastructure.

**Current status: no report submitted.** Nothing in this repository demonstrates a Roblox-controlled boundary being crossed. Submitting executor architecture or detection notes as a vulnerability would most likely be closed as not applicable.

**What would qualify.** A reproducible issue where content Roblox delivers or the engine processes (place files, replicated instances, network messages, assets) causes harm on a client or server that its owner did not consent to, without the attacker first running native code on that machine. For example, game-server-controlled data reaching a privileged script identity on clients, a server crash triggerable through the data model, or memory corruption in the engine reachable from game content. This research may suggest where to look; it does not show any such issue.

# Countermeasures

Ways to detect, measure and disrupt Xeno, ranked by how much each would cost Xeno to work around. Observations `G-x` and dependencies come from [`THREAT_ASSESSMENT.md`](THREAT_ASSESSMENT.md); finding IDs from [`FINDINGS.md`](../research/FINDINGS.md).

These are proposals from outside analysis. The author has no visibility into Roblox's existing detections, and some of these may already be in place. Each proposal states its assumptions and risks so it can be evaluated quickly by people who do.

## 1. Platform hardening (durable)

### C-1 Verify CoreScript bytecode before it runs

**Breaks:** attach (G-1).
Compare each built-in CoreScript module's bytecode with the hash of what the release shipped, when it is loaded and periodically while the client runs. Cover every module under `RobloxGui` and `CorePackages`, not just en-us: checking one module only moves Xeno to the next.
**Cost to Xeno:** high. It would need a different way to get code into a privileged Luau context.
**Risks:** the check itself becomes a target, so it should live where Xeno cannot simply overwrite it. Performance cost depends on frequency.

### C-2 Restrict CoreScript HTTP to loopback

**Breaks:** the control plane (G-2), and with it execution, file access and the HTTP proxy.
Deny `HttpService:RequestInternal` (and equivalents) to `localhost`, `127.0.0.0/8` and `::1` from the client's script contexts, or limit CoreScript requests to an allowlist of Roblox hosts.
**Cost to Xeno:** high. Luau inside the client has no other channel to an outside process; Xeno would have to invent one through memory alone.
**Risks:** legitimate CoreScript or developer-tool traffic to loopback, if any exists, would break. That needs checking against Roblox's own usage. This is also the simplest change on this list.

### C-3 Reject externally written bytecode in `require()`

**Breaks:** script execution (G-3).
Track bytecode provenance: a ModuleScript created at runtime should only run bytecode produced by Roblox's own compile path. A module whose bytecode changed without going through that path should fail to load and be reported.
**Cost to Xeno:** high.
**Risks:** design work in the engine; must not affect legitimate dynamic modules.

### C-4 Make offset reuse harder

**Breaks:** Xeno's cheap cross-version updates (G-4).
Vary the layout of the structures Xeno reads between releases (field order, padding, encrypted pointers) so offsets cannot be aliased from one version to the next.
**Cost to Xeno:** medium per release, recurring. Does not stop Xeno, but turns "update within hours" into "re-reverse every build".
**Risks:** engineering and debugging cost for Roblox.

### C-5 Audit what CoreScript context can reach

**Addresses:** G-5.
Confirm whether purchase, authentication-cookie and messaging APIs are callable from the context Xeno's client runs in. If they are, gate them by caller as well as identity.
**Value:** protects Xeno's users (and any future executor's users) from malicious shared scripts and from the developer's remote code channel.

## 2. Detection and measurement (fast, brittle)

These rely on identifiers Xeno can change quickly. Their best use is counting how many sessions run Xeno and supporting ban waves, not lasting prevention.

| ID | Indicator | Layer | Evidence |
|---|---|---|---|
| C-6 | en-us translation module bytecode differs from the shipped original | Client integrity | F-30 |
| C-7 | `CoreGui` folder named with the client's own PID, containing `Pointer`, `Loadstring` and a `Message` named `DO NOT DELETE: BELONGS TO XENO`; `shared.__Xeno` set | Client integrity | F-70, F-71 |
| C-8 | ModuleScripts created and destroyed at high rate under one CoreGui folder, each `require()`d repeatedly | Client integrity | F-72 |
| C-9 | Loopback `RequestInternal` calls to `/f?e=`, `/ls?c=loadstring:`, `/qt?p=`, `/cb` | Client integrity | F-51, F-52 |
| C-10 | A process loading a module signed by the self-signed `CN=Rizve A` certificate (serial `3FDA0D2C31C5C2A84790E6E2F20D1306`) while holding a write handle to `RobloxPlayerBeta.exe` | Host (anti-cheat) | F-04 |
| C-11 | A process with a loopback HTTP listener that also holds memory-write access to the Roblox process | Host (anti-cheat) | F-50, F-86 |
| C-12 | Outbound requests carrying `exploit-guid` or `xeno-fingerprint` headers, or `User-Agent: Xeno/` | Any web service scripts contact | F-54 |

C-6 and C-8 are the hardest for Xeno to remove without changing how it works. C-7, C-10 and C-12 take minutes to change but are very specific while they last. File-level signatures for the DLL are in [`DETECTION.md`](DETECTION.md) and the [`detection/`](../../detection) folder.

**Prevalence.** C-6 or C-7 recorded as telemetry, without enforcement, would give Roblox the user count this repository cannot ([`THREAT_ASSESSMENT.md`](THREAT_ASSESSMENT.md) §2).

## 3. Infrastructure

Xeno depends on `x3no.pages.dev` for offsets (`ep.zst.enc`), the remote code channel (`code.lua`) and update checks, and on `xeno.now` / `xeno.onl` for distribution. Whether to pursue hosting-provider abuse reports or legal action is a decision for Roblox's legal and trust teams, not a technical measure. Expect it to delay Xeno rather than stop it, since hosting is easy to move.

## 4. Experience developers

Most of the visible damage depends on experiences trusting the client. Regardless of executor:

- Validate movement on the server: maximum speed, vertical travel without support, teleport distance between updates.
- Treat every RemoteEvent and RemoteFunction argument as attacker-controlled; check the caller, ranges, rate and game state.
- Keep currency, inventory and progression changes server-authoritative.
- Do not rely on client-side anti-exploit scripts as a boundary; Xeno runs with more privilege than any experience script and can read or disable them.

## 5. User safety

- **Impersonation malware.** Fake "undetected" Xeno installers have been used to spread a remote-access trojan and infostealer targeting Roblox and Discord tokens and browser credentials ([`THREAT_ASSESSMENT.md`](THREAT_ASSESSMENT.md) §3.4). Safety messaging aimed at players searching for executors could point this out.
- **Identifier leakage and remote code.** Xeno users are tracked by any script host (F-54) and run whatever the developer publishes as `code.lua` (F-63).

## 6. Suggested order

1. **C-2** first: one restriction, large effect, cheap to evaluate.
2. **C-6/C-7 as telemetry** at the same time, to measure prevalence before and after.
3. **C-1** and **C-3** as the durable fixes.
4. **C-5** as a user-protection audit.
5. **C-4** if the update arms race continues.

Indicators and detection approaches for Xeno, derived from [`FINDINGS.md`](../research/FINDINGS.md). Each section states which layer a defender needs access to, how specific the indicator is, and how it can fail.

**Validation status.** The tools have been checked against two Xeno builds (v1.3.40 by the author; v1.3.65 by the author and again on 2026-11-10 with the current tools), against synthetic DLLs that reproduce Xeno's export set and resource layout (`tests/`), and against the text files in this repository. ## Tools

| Tool | Input | Output |
|---|---|---|
| [`detection/xeno_detector.py`](../../detection/xeno_detector.py) | File or directory | Score and verdict per file |
| [`detection/xeno_executor.yar`](../../detection/xeno_executor.yar) | File, process memory, or capture | Matching rules |

### Detector scoring

PE files are scored on product-unique strings and three structural checks: a certificate table naming the `Rizve A` signer (+35), the full six-export interface (+25), and a type-8194 resource whose first four bytes decrypt to the zstd magic under the known key (+35 each). Verdicts: ≥60 `xeno (heuristic)`, 30–59 `executor-family (suspicious)`.

Non-PE files (memory dumps, scripts, reports) get `xeno strings (non-PE)` if any string indicator is present. They never receive a DLL verdict; a document that quotes Xeno strings, including this one, would otherwise score as Xeno.

Expected behavior, covered by tests:

| Input | Verdict |
|---|---|
| Xeno v1.3.65 DLL | `xeno (heuristic)`, score 370; YARA file rules HighConf, Signer_Certificate, ResourceKey_Initializer, EncryptedResource and API_Generic fire |
| DLL with the six exports and a resource encrypted with the known key | `xeno (heuristic)` |
| Same, but the resource key differs (simulates a key rotation) | `executor-family (suspicious)` |
| DLL with only the six exports | `no match` |
| Unrelated DLL | `no match` |
| Repository text files | `no match` or `xeno strings (non-PE)` |

| Rule | Scope | What it matches | False-positive considerations |
|---|---|---|---|
| `Xeno_Executor_DLL_HighConf` | File | MZ header and 2 of 10 product strings / PDB path | Requires a PE; low risk |
| `Xeno_Signer_Certificate` | File | Authenticode signature by the self-signed `Rizve A` certificate (subject and serial) | Very specific; stops matching when the certificate is renewed or replaced (expires 2027-05-10). Requires YARA built with OpenSSL |
| `Xeno_ResourceKey_Initializer` | File | Key immediates as emitted by the initializer | Specific to this compiler output; breaks on key rotation or code-generation changes |
| `Xeno_ResourceKey_Memory` | Memory | The 32-byte key as contiguous bytes | Any file or report containing the raw key bytes |
| `Xeno_EncryptedResource` | File | Type-8194 resource beginning `16 48 7F B8` | Independent of payload size and version while the key is unchanged; tested on synthetic DLLs and v1.3.65 |
| `Xeno_ClientLua_Payload` | Memory, file | 3 of 8 distinctive `CLIENT.LUA` strings | Matches documents that quote them |
| `Xeno_Server_Protocol` | Memory, capture | 4 of 7 protocol strings | Matches documents that quote them, including this repository |
| `Executor_API_Generic` | File | All six export names | Names are generic; triage only |

An earlier revision matched 16 bytes of each encrypted resource. Bytes 5 onward include the zstd frame header, which encodes the content size and so changes with every build. The current rule matches only the 4-byte encrypted magic within a type-8194 resource.

## Layer 1 — Files on disk

Product strings, the PDB path, the signing certificate, the key initializer, and the encrypted resources together identify Xeno builds with high specificity. The export set alone does not. Forks that strip branding would still match the structural checks while the key is unchanged. A key rotation would defeat the key-based checks; [`tools/sample_report.py`](../../tools/sample_report.py) attempts automatic recovery from the initializer pattern.

## Layer 2 — Host behavior (EDR, Sysmon)

| Observable | Specificity | Notes |
|---|---|---|
| A non-Roblox process opens `RobloxPlayerBeta.exe` with memory-write access and writes to it | Medium | Shared by all external executors and some overlays; telemetry needs handle or `WriteProcessMemory`-class events |
| Process sets `XENO_CLIENT_PID`, `XENO_SERVER_PORT`, `XENO_VERSION` | High | Inferred from the `%…%` placeholders; how they are set is not traced |
| `Xeno` directory with `workspace`, `autoexec` and a cache file | High | Location not established |
| Loopback HTTP listener in the same process, receiving `POST /f?e=<int>`, `/ls?c=`, `/rq?c=` | High | Requires loopback capture or a host-based proxy |
| Outbound HTTPS to `x3no.pages.dev`, `xeno.now`, `xeno.onl`, `pastebin.com/raw/A7n0vJtR` | High (domains) | Domains can change without a DLL update |

## Layer 3 — Inside the Roblox client

These require code or checks running in the client, which is the domain of Roblox's client integrity and anti-cheat systems. A game server cannot observe client memory or CoreGui directly, and an experience's own scripts cannot read CoreGui.

| Observable | Specificity | Notes |
|---|---|---|
| `CoreGui` folder named with the client's own PID, containing `Pointer`, `Loadstring`, and `Message` "DO NOT DELETE: BELONGS TO XENO" | Very high | Trivial for the developer to rename in a future build |
| `shared.__Xeno` present | Very high | Same caveat |
| en-us translation module's bytecode differs from the shipped original | High | Persistent for the session; does not depend on branding |
| ModuleScripts created and destroyed at high frequency under one CoreGui folder, each `require()`d repeatedly | High | The polling loop runs every ~1 ms; it is local and produces no network traffic |
| `HttpService:RequestInternal` calls to `http://localhost:<port>/f?e=`, `/ls?c=loadstring:`, `/qt?p=`, `/cb` | High | Only after an execution (op 21), on each `loadstring` (ops 20/21), and on file and API calls; not a constant stream |
| Foreign bytecode in a module | High | Transient by design in v1.3.65 (Bytecode Patch Watcher); prefer the persistent signals above |

## Layer 4 — Network

Loopback traffic is described above. Outbound, the client requests `version.txt` and `code.lua` from `x3no.pages.dev` on attach, and the DLL requests `ep.zst.enc` on startup if the primary offsets source fails. Proxied script requests carry `User-Agent: Xeno/<version>` by default, `exploit-guid` and `xeno-fingerprint` (the user's hardware identifier), and `roblox-place-id`, `roblox-game-id`, `roblox-session-id`, on traffic that is not going to Roblox. Any web service that Xeno scripts call can see these headers, which makes them the simplest server-side signal available outside Roblox (for example to operators of script-hosting or webhook endpoints).

# Threat assessment

What Xeno is used for, how widespread it appears to be, who it harms, and what its design reveals about where the Roblox client can be hardened. Finding IDs (`F-xx`) refer to [`FINDINGS.md`](../research/FINDINGS.md). Countermeasures are in [`COUNTERMEASURES.md`](COUNTERMEASURES.md).

## 1. Summary

Xeno is a free, keyless script executor for the Windows Roblox client. It lets a user run arbitrary Luau inside their own client with an environment of roughly 160 functions aimed at cheating and game manipulation. It works without loading a DLL or creating a thread in Roblox: it replaces the bytecode of a built-in CoreScript module, then drives that code over a localhost HTTP server (F-30, F-40, F-50).

The main harm falls on other players and experience developers through cheating. Xeno's own users carry real risk too: the developer can push code into every attached client (F-63), every script HTTP request discloses the user's hardware ID (F-54), and the "undetected" branding is being used by malware campaigns. Xeno does not exploit a vulnerability in Roblox as the term is used in security: it requires the user to run it on their own machine. Its design does show specific places where the client trusts its own memory and network behaviour more than it needs to (§5).

## 2. Prevalence

There is no reliable public measurement of how many people use Xeno. What can be said, and how strong each piece is:

| Indicator | What it shows | Reliability |
|---|---|---|
| The author encounters Xeno users in most Roblox experiences he joins | Broad use across experiences | Anecdotal; one observer |
| The official Xeno Discord server has about 600,000 members (author's observation) | A large audience | Membership is not usage: it includes inactive and duplicate accounts and people who joined once |
| Third-party download pages claim figures such as "838,000+ users" or "183,415 users online" | Nothing verifiable | These pages are unofficial and often clones or SEO sites; figures are unsourced |
| A malware campaign has impersonated Xeno since early 2026 (§3.4) | Enough demand that criminals find Xeno worth impersonating | Strong as an indication of popularity; says nothing about the real user count |
| Xeno's update model (offsets downloaded at runtime, F-33) lets it keep working across Roblox releases without a new build | Sustained availability | Confirmed design |

**Conclusion.** Xeno is clearly widely used, but its scale cannot be established from public data, and this repository does not claim a number. Roblox can measure it directly: the in-client indicators in [`COUNTERMEASURES.md`](COUNTERMEASURES.md) §2 (a modified en-us module, the `CoreGui/<pid>` container, `shared.__Xeno`) can count Xeno-attached sessions in telemetry without banning anyone.

## 3. Who is harmed

### 3.1 Other players

Xeno exposes input synthesis, property and signal access, metatable and function hooking (partly stubbed, F-48), HTTP, and file I/O to scripts shared through script hubs. In practice this enables movement cheats (flying, speed, teleport), automation, and abuse of each experience's remote events. Players in affected servers lose fair play; the harm is the same in kind as any executor's.

### 3.2 Experience developers

Most gameplay damage happens because an experience trusts what the client sends. Developers bear the cost: economy abuse, lost players, and time spent on anti-exploit work. Server-side validation is their main defense whatever the executor ([`COUNTERMEASURES.md`](COUNTERMEASURES.md) §4).

### 3.3 Xeno's own users

- **Remote code channel.** Every attached client downloads `code.lua` from the developer's host and runs it with the full Xeno environment (F-63). Whoever controls that host, the developer or anyone who compromises the account, can run code in every attached session at once.
- **Identifier leakage.** Every script HTTP request sends the user's hardware ID as `exploit-guid` and `xeno-fingerprint`, plus their current server's JobId and PlaceId, to whatever host the script contacts (F-54). Script and webhook operators can track users across sessions and accounts.
- **Privileged APIs.** Xeno blocks its own scripts from purchase, authentication-cookie and messaging APIs (F-90). That implies the developers believe these APIs are reachable from the context Xeno's scripts run in; if so, a malicious shared script that got around the block, or the remote code channel, could act on the user's account. Reachability is unverified.
- **Account action.** Use violates Roblox's Terms of Use and risks moderation.

### 3.4 Impersonation malware

Bitdefender reported a campaign distributing a fake "undetected" Xeno through gaming forums and Discord communities. It installs a Java-based remote access trojan and infostealer that takes browser passwords and cookies, Discord and Roblox tokens, and cryptocurrency wallet data, and allows keylogging, screen and webcam capture, and remote command execution. The campaign began in early 2026, peaked in March 2026, and remained active as of August 2026 ([TechRadar, 4 August 2026](https://techradar.com/pro/security/new-malware-disguised-as-popular-roblox-cheat-tool-could-give-hackers-full-control-of-your-pc-including-the-webcam)).

### 3.5 Roblox

Trust in fair play, moderation and support load, and the ongoing engineering cost of the anti-cheat arms race.

## 4. How Xeno works, in brief

1. The Electron UI loads `Xeno.dll`, which downloads per-Roblox-version memory offsets (F-33) and starts a localhost HTTP server (F-50).
2. The DLL finds each Roblox client, locates the en-us locale translation ModuleScript under `RobloxGui.Modules`, and overwrites its bytecode with Xeno's client script (F-30).
3. Roblox loads that module as part of its own startup, so Xeno's client runs as a CoreScript. It builds a container in `CoreGui`, sets `shared.__Xeno`, fetches `code.lua`, and calls the DLL over loopback HTTP (F-70, F-71, F-63).
4. To run a user script, the DLL compiles it with an embedded Luau compiler and writes the bytecode into a ModuleScript the client is repeatedly `require()`ing; `require` returns the compiled function and the client runs it (F-40, F-41).
5. Everything else (file access, HTTP, clipboard, teleport queue) goes through `/f?e=<op>` and related endpoints on the localhost server (F-51, F-52).

Full detail: [`ARCHITECTURE.md`](../research/ARCHITECTURE.md).

## 5. What Xeno's design shows about the client

Each item below is inferred from the fact that Xeno works as documented. None is a vulnerability in the bounty sense, because all of them require the user to run Xeno on their own machine. They are the places where hardening would cost Xeno the most.

| ID | Observation | Basis | Confidence |
|---|---|---|---|
| G-1 | A built-in CoreScript module whose bytecode has been replaced in memory still loads and runs. Nothing checks the module's bytecode against what Roblox shipped before executing it. | F-30, F-73 | Inferred |
| G-2 | Code running as that CoreScript can send HTTP requests to arbitrary loopback ports through `HttpService:RequestInternal`. Xeno's entire control plane depends on this. | F-50, F-51; `P:122` uses `RequestInternal` | Strongly supported |
| G-3 | A ModuleScript created at runtime in `CoreGui` and then given bytecode written from outside the process is executed by `require()` without any provenance check. | F-40, F-42 | Inferred |
| G-4 | Roblox's internal object layout changes little enough between releases that Xeno can reuse ("alias") offsets across versions and update them remotely within hours. | F-33 | Inferred |
| G-5 | The context Xeno's scripts run in may reach purchase, authentication-cookie and messaging APIs, judging by Xeno's own deny-list. | F-90 | Unverified |

## 6. Xeno's structural dependencies

Each is something Xeno currently cannot work without. The cost column estimates how much engineering it would take Xeno to replace the dependency if Roblox removed it; these are the analyst's estimates.

| Dependency | Evidence | If broken | Estimated cost to Xeno |
|---|---|---|---|
| A built-in CoreScript module it can overwrite and that Roblox will load (en-us) | F-30 | No attach | High if all CoreScripts are integrity-checked; low if only en-us is (Xeno moves to another module) |
| Loopback HTTP from CoreScript context | G-2 | No control plane: no execution, files or HTTP proxy | High; Luau inside the client has no other channel to an outside process |
| Out-of-band bytecode in `require()`d modules | F-40, F-42 | No script execution | High |
| Runtime offsets from its own host | F-33 | No attach after each Roblox update until restored | Medium; hosting moves easily, but stable layouts are what make aliasing cheap |
| Fixed artifacts (`CoreGui/<pid>`, `Message`, `shared.__Xeno`) | F-70, F-71 | Detection only | Low; renaming takes minutes |
| Fixed signing certificate | F-04 | Detection only | Low; a new self-signed certificate takes minutes |
| Unchanged resource key | F-61 | Detection only | Low |

The pattern matters for prioritizing: the identifiers are cheap for Xeno to change and best used for measurement and ban waves; the execution primitives (G-1 to G-3) are expensive to replace and are where hardening has lasting effect.

# Architecture — Xeno v1.3.65

How Xeno's components fit together, reconstructed from static analysis of the DLL and the decrypted client script. Finding IDs (`F-xx`) refer to [`FINDINGS.md`](FINDINGS.md), which holds the evidence and confidence for each claim. RVAs are relative to image base `0x180000000`. ## 1. Components

```
┌──────────────┐  exports / named pipe (F-55)  ┌───────────────────────────────┐
│  Xeno UI     │ ─────────────────────────────► │ Xeno.dll (native core)        │
│  (Electron)  │                                │  • offsets fetch (curl)       │
└──────────────┘                                │  • Luau compiler              │
                                                │  • localhost HTTP/WS server   │
                                                │  • cross-process memory I/O   │

                                   bytecode writes     │              │ POST /f /ls /rq /qt /cb
                                   (Nt*VirtualMemory)  ▼              │ (HttpService:RequestInternal)
                                                ┌───────────────────────────────┐
                                                │ RobloxPlayerBeta.exe          │
                                                │  en-us module → CLIENT.LUA    │

The DLL never runs Luau inside Roblox by itself. It writes compiled bytecode into ModuleScripts that the Roblox client already executes or that the Xeno client `require()`s, and serves everything else over loopback HTTP.

## 2. Binary layout

```
.text   VA=0x1000    VS=0x1A948B   code

## 4. Attach

Ordered from log strings and client code. Steps marked † are inferred.

1. Enumerate processes and create an `RBXClient` per Roblox PID (`"Creating new RBXClient: {}"`); reuse cached PIDs (`"Reattaching to cached client PID: {}"`).
2. Refuse elevated targets when not elevated (F-32).
3. Wait for the client window and the DataModel.
4. Locate `RobloxGui → Modules → en-us` (`"Could not find RobloxGui->Modules..."`). Offsets for the running Roblox version come from the downloaded RBXClient data (§7).
5. Replace the module's bytecode with compiled `CLIENT.LUA` (`"Intercepted translation module @{:#x}"`). † The write uses the resolved `NtWriteVirtualMemory`; † suspension around the write is plausible but not traced.
6. Roblox runs the module. `CLIENT.LUA` recognises the en-us context (`P:396`), builds its container, and calls `Activate` (op 0) until the DLL answers. The DLL logs `"Attach ping received..."`.
7. If no ping arrives, force a window refresh (`"Did not receive the success ping from client. Using RefreshRBXWindowV2..."`, backed by `SetWindowPos`, `RedrawWindow`, `LockWindowUpdate` and `DwmSetWindowAttribute` imports), retry, then `"Still did not receive the success ping from client. Treating this as failed."` (F-36).
8. On `PlayerRemoving` for the local player, the client sends op 19 and the DLL reattaches after the next place loads.

**Why this target.** A ModuleScript under `RobloxGui` is loaded by Roblox's own Lua as part of normal startup, so replacing its bytecode gives Xeno a Luau thread without creating a native thread or loading a DLL into the process. Xeno also bundles Roblox's original en-us table (resource `8196`), most plausibly so that translation lookups keep working after the module is replaced; how the two are combined was not traced. *This rationale is the analyst's interpretation; the mechanism is F-30.*

## 5. Execution and protocol

### 5.1 Path A — `Execute` export

```
UI ──Execute(script, pids)──► DLL: queue per client
                              DLL: compile with embedded Luau + wrapper (F-41, F-43)
                              DLL: locate current execution module in CoreGui/<pid>
                              DLL: write bytecode, read back to verify
Roblox (CLIENT.LUA, P:4826-4872):
    loop every ~1 ms:
        ok, f = pcall(require, ExecutionModule)
        if f is a function:
            ExecutionModule:Destroy()
            setfenv(f, {getfenv, setfenv, setmetatable, error, Xeno})
            task.spawn(f)
            POST /f?e=21   (LockCustomBytecode)
            create new random-named module
```

The client sends nothing until a script has run. How the DLL identifies the current execution module (its name is random) was not traced.

### 5.2 Path B — `loadstring`

```
CLIENT.LUA (P:1994-2080):
    module = ModuleScript "loadstring:<rand>[:chunkName]" in CoreGui/<pid>/Loadstring
    POST /ls?c=<module name>&p=<pid>  body = source     -- 400 = compile error, 500 = server error
    repeat every 50 ms, up to 3 s:
        POST /f?e=20   (UnlockCustomBytecode)
        res = require(module)
        POST /f?e=21   (LockCustomBytecode)
        if res[XENO_PID] is a function: return it
```

Returning a table keyed by PID means a module compiled for one client cannot be consumed as another client's result.

## 6. Resource encryption

`LoadResource`/`SizeofResource`/`LockResource` at `0x18CD06–0x18CD7F` copy the blob into a `std::string` and call `0x1906B0`:

```asm
0x190737: mov   r8,  [rip+0xC25DA]   ; key.begin   (.data 0x252D18)
0x19073e: mov   rcx, [rip+0xC25DB]   ; key.end     (.data 0x252D20)
0x190745: sub   rcx, r8              ; key length (32)
0x19074a: mov   rax, r9
0x19074d: div   rcx                  ; rdx = i % 32
0x190750: movzx ecx, byte [r10+r9]
0x190755: xor   cl, byte [rdx+r8]
0x19075d: mov   [rax+r9], cl
```

The key pointers are zero in the file and filled by a CRT dynamic initializer at `0x3B10`, which allocates 32 bytes and stores eight immediates (the `mov dword [rax], imm32` sequence begins at `0x3B30`):

```
0x4550FD3E 0xCABF61ED 0x92A1EF57 0x966607D0 0x21F7C5FD 0x3649BD12 0x19B33F7A 0xBBF52AA9
→ 3E FD 50 45 ED 61 BF CA 57 EF A1 92 D0 07 66 96 FD C5 F7 21 12 BD 49 36 7A 3F B3 19 A9 2A F5 BB
```

After XOR the routine checks for the zstd magic (`0x1908DD: cmp ecx, 0xFD2FB528`), calls `ZSTD_getFrameContentSize` and `ZSTD_decompress`, and logs `"Could not decompress a Xeno resource: {}"` on failure.

*Reconstruction:*

```cpp
std::string LoadXenoResource(int id) {
    HRSRC   h    = FindResourceW(g_module, MAKEINTRESOURCEW(id), MAKEINTRESOURCEW(8194));
    HGLOBAL g    = LoadResource(g_module, h);
    DWORD   size = SizeofResource(g_module, h);
    std::string buf(static_cast<const char*>(LockResource(g)), size);
    for (size_t i = 0; i < buf.size(); ++i)
        buf[i] ^= g_key[i % g_key.size()];
    if (memcmp(buf.data(), "\x28\xB5\x2F\xFD", 4) != 0) return {};
    std::string out(ZSTD_getFrameContentSize(buf.data(), buf.size()), '\0');
    if (ZSTD_isError(ZSTD_decompress(out.data(), out.size(), buf.data(), buf.size()))) return {};
    return out;
}
```

## 7. Offsets and remote content

Roblox ships frequently, so Xeno does not hard-code internal offsets. At startup the DLL downloads zstd-compressed RBXClient data, falling back to `https://x3no.pages.dev/ep.zst.enc` if the primary source fails. Entries are keyed by Roblox version; one version can alias another's offsets, and unknown versions fall back to a default with a warning (F-33). The primary source is unknown (F-34).

The client separately fetches `version.txt` (update notice) and `code.lua`, which it runs with the full Xeno environment on every attach (F-63).

## 8. Script environment

The client builds a `Xeno` table of roughly 160 functions in the common "UNC" style (`getgenv`, `hookfunction`, `getscriptbytecode`, `request`, file I/O, `Drawing`, input synthesis, and so on). Not all are functional: the header says some are fake (F-48), and identity functions only store a number (F-47). Before exposing any of this, the client wraps a list of Roblox services so that selected methods raise `"Attempt to call a blocked function"` (F-90; `P:441-577`).

## 9. Cache

One binary file in the Xeno directory holds client PIDs, compiled bytecode, flags and client info, plus queued teleport scripts. A bad header is non-fatal (`"No valid cache found (Starting new fresh cache)"`).

# Limitations

What this research does not establish, and why it matters for reading the other documents.

**Static analysis only.** No Xeno binary was executed. Behavior is reconstructed from code, strings, imports and the decrypted client script. Findings marked "Confirmed" are confirmed as present in the artifacts, not observed at runtime. Timing, ordering and error paths described in [`ARCHITECTURE.md`](ARCHITECTURE.md) may differ in practice.

**Two builds.** Only v1.3.40 and v1.3.65 were examined. Xeno updates frequently and its offsets and some code arrive at runtime (`ep.zst.enc`, `code.lua`), so the behavior of any given session can differ from what is described here without a DLL change.

**Partial disassembly.** The exported functions, the resource loader, the decrypt routine and the key initializer were disassembled. The internal attach routine, the server handlers, the write path into Roblox memory and the Bytecode Patch Watcher were not; their descriptions rest on log strings and client code. Field names (`hProcess`, `state`) are interpretations of how values are tested.

**Evidence availability.** Samples are not redistributed, so DLL-level evidence (RVAs, strings, imports) can only be checked by someone who obtains the same build. Hashes are given so they can confirm they have it. As of 2026-11-10 the public v1.3.65 installer still contains the analyzed DLL (F-08); that will change when Xeno updates.

**Detection validation.** The detector and YARA rules have been tested on two real builds, synthetic fixtures and this repository's text. There is no benign-corpus result and no measurement against other executors. Thresholds are heuristics.

**Generated reports.** [`SAMPLE_REPORT.md`](../../reports/SAMPLE_REPORT.md) was regenerated with the current tools on 2026-11-10. The committed [`COMPARE_REPORT.md`](../../reports/COMPARE_REPORT.md) was produced by a version of `compare_samples.py` whose function-level import diff covered only the first DLL, so its "Imported functions: No changes" line is not reliable; it needs regenerating with the v1.3.40 sample.

**Unresolved questions.** Listed at the end of [`FINDINGS.md`](FINDINGS.md). The most consequential are the actual script identity of the hijacked module and whether the APIs Xeno blocks for its users are reachable from it (F-47, F-90).

**Prevalence.** No public data establishes how many people use Xeno. Discord membership and third-party download figures are not usage counts ([`THREAT_ASSESSMENT.md`](../defense/THREAT_ASSESSMENT.md) §2).

**Countermeasures are proposals.** [`COUNTERMEASURES.md`](../defense/COUNTERMEASURES.md) is written without knowledge of Roblox's existing detections or internal constraints; some measures may already exist or be impractical.

**Scope.** This is research on one third-party executor. It says nothing about other executors, including Potassium, and does not by itself establish any vulnerability in Roblox (see [`DISCLOSURE.md`](../DISCLOSURE.md)).

# Methodology

How the analysis was performed, in the order it happened, and why each step was chosen. Results are in [`FINDINGS.md`](FINDINGS.md); the reconstructed design is in [`ARCHITECTURE.md`](ARCHITECTURE.md).

## Environment and constraints

- **Static only.** No Xeno binary was executed and no debugger was attached. Every behavioral statement is derived from code, strings, imports or the decrypted client script.
- **Samples.** Two builds extracted from the official installers: v1.3.65 (SHA-256 `50318bc8…99049`, the subject of this report) and v1.3.40 (SHA-256 prefix `37e78bb4944ed703`, used for comparison). Samples are not redistributed.
- **No interaction with Roblox or Xeno infrastructure** is part of the documented method: none of the steps below requires a request to Roblox services, `x3no.pages.dev`, `xeno.now` or the pastebin URL.

| Tool | Version | Use |
|---|---|---|
| Python | 3.14 | Scripting |
| pefile | 2024.8.26 | Headers, sections, imports, exports, resources |
| capstone | 5.0.7 | x86-64 disassembly |
| zstandard | 0.25.0 | Decompression |
| PowerShell `Get-AuthenticodeSignature` | Windows built-in | Signature check |
| 7-Zip | 16.02 (7za) | Installer extraction ([`tools/update_sample.py`](../../tools/update_sample.py)) |
| OpenSSL | 3.x | Certificate parsing |

## Phase 1 — Triage and capability mapping

**1. Format.** `file` and pefile: PE32+ DLL, x86-64, six sections with standard names, `.pdata` intact, no section both writable and executable. This indicated an unpacked MSVC build, so the analysis went straight to static work without an unpacking step.

**2. Exports.** Six exports: `Attach`, `Execute`, `GetClients`, `Initialize`, `SetSetting`, `Version`. The names describe an injector/executor interface driven by a separate UI.

**3. Imports.** Grouped by DLL to map capabilities before reading code: libcurl/OpenSSL (HTTPS client), WS2_32 (sockets), process and memory APIs (cross-process access), USER32 window APIs (window discovery and manipulation), named-pipe APIs (IPC), `GetCurrentHwProfileW` (hardware identifier). Imports show what the program *can* do, not what it does; each was later tied to strings or code where possible.

**4. Strings.** ASCII (`[\x20-\x7e]{4,}`, 10,366 strings) and UTF-16 extraction, filtered by keyword. Because the binary is not obfuscated and logs with fmt-style `{}` placeholders, searching for `[{}` and `{}]:` recovered component names (`RBXClient`, `XenoServer`, `::Loadstring`, `::PlayerRemoving`, `::UnlockModule`, …) and most of the attach sequence. UTF-16 strings contained nothing of interest.

**5. Resources.** Besides the manifest, two resources of custom type `8194` (IDs `8192`, `8196`) with the same first five bytes and near-maximal entropy (≈7.99 bits/byte). Entropy alone cannot separate compression from encryption, since zstd output is also close to 8 bits/byte. What pointed to encryption was that neither blob began with the zstd magic even though the string `"Could not decompress a Xeno resource"` showed zstd was involved.

**6. Signature.** `Get-AuthenticodeSignature` returned `UnknownError`, which was first read as "unsigned". An unsigned file returns `NotSigned`. Parsing the 8,016-byte certificate table later showed a signature from a self-signed `CN=Rizve A` certificate with a Sectigo timestamp; recomputing the Authenticode SHA-256 digest matched the signed value (F-04). Windows reports `UnknownError` because the chain does not reach a trusted root.

**7. Targeted disassembly.** capstone at each export RVA, resolving RIP-relative operands to strings. This established calling conventions and object-field offsets for `Execute` and `GetClients`, the `Version` small-string pattern, the `Attach` thunk, and the `ntdll` resolution in `Initialize`.

**8. Timestamp.** The PE timestamp (2026-10-20) was first misread as forged. It precedes the analysis date and is a plausible build date.

## Phase 2 — Breaking the resource encryption

**1. Differential test.** XORing the two blobs against each other gave zeros for the shared prefix and high entropy afterwards. Identical ciphertext over an identical plaintext prefix (both are zstd frames) is what a fixed keystream produces; a block cipher in CBC mode with distinct IVs would not.

**2. Known plaintext.** Assuming the plaintext starts with the zstd magic `28 B5 2F FD`, XOR with the ciphertext prefix `16 48 7F B8` gives keystream bytes `3E FD 50 45`.

**3. Cross-references from strings.** For each resource error string, `.text` was scanned for `lea reg, [rip+disp]` (REX.W `8D`, ModRM mod=00 r/m=101) whose target is the string's RVA. This located the log sites (`0x190A97`, `0x18CD14`, `0x18CDC1`).

**4. The cipher.** Reading back from the log sites found the resource load sequence at `0x18CD06` and the transform at `0x1906B0`: a byte loop indexing a key by `i mod len`, with the key held as a begin/end pointer pair in `.data` (`0x252D18`/`0x252D20`).

**5. The key.** Those `.data` slots are zero in the file, so they are filled at runtime. A full-`.text` scan for stores to those addresses found one writer, a CRT dynamic initializer at `0x3B10` that allocates 32 bytes and writes eight immediate dwords. The first four bytes matched the known-plaintext result.

**6. Decryption.** XOR, check the magic, zstd-decompress ([`tools/decrypt_resources.py`](../../tools/decrypt_resources.py)). Both resources decompressed to text: `CLIENT.LUA` (145,004 B) and Roblox's en-us table (336,884 B). Successful decompression of both is the decisive confirmation of the key.

**7. Client analysis.** `CLIENT.LUA` is unobfuscated Luau. It provided the attach target check, the container layout, the protocol, the execution loops, the remote channels and the service deny-list. Its line numbers are indexed in [`payloads/README.md`](../../payloads/README.md).

**Lesson.** For an unobfuscated binary, the fastest path to a cipher is through its error messages: cross-reference them and read backwards.

## Phase 3 — Version comparison

[`tools/update_sample.py`](../../tools/update_sample.py) extracts `Xeno.dll` from each installer; [`tools/compare_samples.py`](../../tools/compare_samples.py) diffs exports, imports, URLs, environment variables, resources, filtered strings and section sizes between two builds. Comparing v1.3.40 with v1.3.65 dated the attach rework, the Bytecode Patch Watcher and the `dwmapi.dll` import, and showed the resource key did not change.

## Phase 4 — Review and correction (November 2026)

A full review of the repository against the client source and the generated reports found claims that went further than the evidence, several technical errors, and a bug in `compare_samples.py` that limited the function-level import diff to one DLL. Corrections are listed at the end of [`FINDINGS.md`](FINDINGS.md). Each finding now carries a confidence level and an evidence reference, the tools gained a test suite (`tests/`) built on synthetic DLLs, and the redistributed payloads were replaced by hashes and a line index.

## Phase 5 — Verification against the sample (November 2026)

The current public installer was extracted with 7-Zip (NSIS layer, then the embedded `app-64.7z`), and its `Xeno.dll` matched the analyzed build's SHA-256. On that copy: every disassembly excerpt in [`ARCHITECTURE.md`](ARCHITECTURE.md) was re-checked at its address with capstone; imports and strings behind the unverified findings were checked (F-36, F-86, F-98 updated); the signature was parsed and its digest recomputed (F-04); both resources decrypted to the hashes in [`payloads/README.md`](../../payloads/README.md); [`SAMPLE_REPORT.md`](../../reports/SAMPLE_REPORT.md) was regenerated and the detector and YARA rules were run. Run from the repository root:  python -m unittest discover -s tests -v

The PE tests build small, harmless DLLs at test time (clang + lld-link + llvm-rc). They mimic
Xeno's structure (export names, an XOR+zstd type-8194 resource) without containing any Xeno
code. If the toolchain is missing, those tests are skipped rather than failed.
"""
import os
import shutil
import subprocess
import sys
import tempfile
import unittest

ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
sys.path.insert(0, os.path.join(ROOT, "tools"))
sys.path.insert(0, os.path.join(ROOT, "detection"))

import zstandard  # noqa: E402

import compare_samples  # noqa: E402
import decrypt_resources  # noqa: E402
import xeno_detector  # noqa: E402

try:
    import yara
except ImportError:
    yara = None

KEY = xeno_detector.XOR_KEY
EXPORTS = ["Attach", "Execute", "GetClients", "Initialize", "SetSetting", "Version"]
TOOLCHAIN = all(shutil.which(t) for t in ("clang", "lld-link", "llvm-rc"))


def encrypt(payload, key=KEY):
    frame = zstandard.ZstdCompressor().compress(payload)
    return bytes(b ^ key[i % len(key)] for i, b in enumerate(frame))


def build_dll(workdir, name, exports, resource=None):
    """Build a minimal x64 DLL with the given exports and an optional type-8194 resource."""
    src = os.path.join(workdir, f"{name}.c")
    with open(src, "w") as f:
        for e in exports:
            f.write(f"__declspec(dllexport) int {e}(void) {{ return 0; }}\n")
        f.write("int unused_symbol(void) { return 0; }\n")
    obj = os.path.join(workdir, f"{name}.obj")
    subprocess.run(["clang", "--target=x86_64-pc-windows-msvc", "-c", src, "-o", obj], check=True)
    inputs = [obj]
    if resource is not None:
        blob = os.path.join(workdir, f"{name}.bin")
        with open(blob, "wb") as f:
            f.write(resource)
        rc = os.path.join(workdir, f"{name}.rc")
        with open(rc, "w") as f:
            f.write(f'8192 8194 "{os.path.basename(blob)}"\n')
        res = os.path.join(workdir, f"{name}.res")
        subprocess.run(["llvm-rc", "/fo", res, rc], check=True, cwd=workdir)
        inputs.append(res)
    out = os.path.join(workdir, f"{name}.dll")
    subprocess.run(["lld-link", "/dll", "/noentry", "/nodefaultlib", f"/out:{out}", *inputs],
                   check=True, capture_output=True)
    return out

"""compare_samples.py
Diffs two Xeno-family DLLs and writes a markdown change report.

Usage:  python tools/compare_samples.py <old.dll> <new.dll> [-o COMPARE_REPORT.md]

Typical use after `update_sample.py` (which leaves timestamped .bak files):

import argparse
import datetime
import os
import re
import sys

sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from sample_report import analyze  # noqa: E402

WORKSPACE = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))

# strings matching these are "interesting" for the string-level diff
INTERESTING = re.compile(
    r"xeno|attach|offset|module|loadstring|bytecode|http|localhost|pipe|"
    r"hook|script|client|server|teleport|autoexec|cache|hwid|key|version", re.I)


def diff_sets(old, new):
    old_s, new_s = set(old), set(new)
    return sorted(new_s - old_s), sorted(old_s - new_s)


def diff_imports(old, new):
    """Function-level import diff across every DLL, including DLLs added or removed."""
    added, removed = [], []
    for dll in sorted(set(old) | set(new)):
        a, r = diff_sets(old.get(dll, []), new.get(dll, []))
        added += [f"{dll}!{x}" for x in a]
        removed += [f"{dll}!{x}" for x in r]
    return added, removed


def section(title, added, removed, limit=60):
    L = [f"## {title}", ""]
    if not added and not removed:
        L += ["No changes.", ""]
        return L
    if added:
        L.append(f"**Added ({len(added)}):**")
        L.append("")
        L += [f"+ `{x}`" for x in added[:limit]]
        if len(added) > limit:
            L.append(f"+ ... and {len(added) - limit} more")
        L.append("")
    if removed:
        L.append(f"**Removed ({len(removed)}):**")
        L.append("")
        L += [f"- `{x}`" for x in removed[:limit]]
        if len(removed) > limit:
            L.append(f"- ... and {len(removed) - limit} more")
        L.append("")
    return L

    ap.add_argument("new")

        f"| {new['detector']['score']} ({new['detector']['verdict']}) |")
    k_old = old["xor_key"] or "—"
    k_new = new["xor_key"] or "—"

        f"| `{k_new[:32]}...`{changed} |")
    add("")

    if old["sha256"] == new["sha256"]:

        add("")
    else:

        # imports: dll-level then function-level

                sec_changes.append(
                    f"section `{nm}` vsize {o['vsize']:,} -> {n['vsize']:,} "
                    f"({n['vsize'] - o['vsize']:+,})")
        L += section("Section layout", sec_changes, [])

    open(out, "w", encoding="utf-8").write("\n".join(L))
    print(f"[OK] comparison written -> {out}")


if __name__ == "__main__":
    main()

#!/usr/bin/env python3
"""Decryptor for Xeno embedded resources (PE resource type 8194).

Pipeline recovered from the v1.3.65 DLL (.text:0x1906B0):
    resource bytes --XOR(32-byte repeating key)--> zstd frame --zstd--> payload

Key recovered from the CRT dynamic initializer at .text:0x3B10. Verified against v1.3.40 and
v1.3.65; other builds may use a different key (sample_report.py attempts automatic recovery).

Usage: python decrypt_resources.py <dll> [out_dir]
"""
import argparse
import io
import os
import sys

import pefile
import zstandard as zstd

KEY = bytes.fromhex(
    "3EFD5045ED61BFCA57EFA192D0076696"
    "FDC5F72112BD49367A3FB319A92AF5BB"
)
ZSTD_MAGIC = b"\x28\xb5\x2f\xfd"
RESOURCE_TYPE = "8194"


def xor(data, key=KEY):
    return bytes(b ^ key[i % len(key)] for i, b in enumerate(data))


def decrypt_blob(blob, key=KEY):
    """Return the decompressed payload, or None if the key does not produce a zstd frame."""
    dec = xor(blob, key)
    if dec[:4] != ZSTD_MAGIC:
        return None
    return zstd.ZstdDecompressor().stream_reader(io.BytesIO(dec)).read()


def get_resources(pe):
    img = pe.get_memory_mapped_image()
    blobs = {}

    def walk(d, path=()):
        for e in d.entries:
            name = e.name.string.decode() if e.name else str(e.id)
            p = path + (name,)
            if hasattr(e, "directory"):
                walk(e.directory, p)
            elif p[0] == RESOURCE_TYPE:
                off, sz = e.data.struct.OffsetToData, e.data.struct.Size
                blobs[p[1]] = img[off:off + sz]

    if hasattr(pe, "DIRECTORY_ENTRY_RESOURCE"):
        walk(pe.DIRECTORY_ENTRY_RESOURCE)
    return blobs


def main():
    ap = argparse.ArgumentParser(description=__doc__.splitlines()[0])
    ap.add_argument("dll")
    ap.add_argument("out_dir", nargs="?", default=".")
    a = ap.parse_args()

    blobs = get_resources(pefile.PE(a.dll))
    if not blobs:
        sys.exit(f"no type-{RESOURCE_TYPE} resources in {a.dll}")
    os.makedirs(a.out_dir, exist_ok=True)
    for name, blob in blobs.items():
        out = decrypt_blob(blob)
        if out is None:
            print(f"resource {name}: no zstd magic after XOR - key differs in this build")
            continue
        path = os.path.join(a.out_dir, f"xeno_resource_{name}.bin")
        with open(path, "wb") as f:
            f.write(out)
        print(f"resource {name}: {len(blob)} -> {len(out)} bytes -> {path}")


if __name__ == "__main__":
    main()

#!/usr/bin/env python3
"""sample_report.py
Analyzes a Xeno DLL (default: sample/TEST.dll) and (re)writes reports/SAMPLE_REPORT.md.
The analysis is factored into analyze() so tools/compare_samples.py can reuse it.

Usage:  python tools/sample_report.py [dll-path] [-o report-path]
"""

import argparse
import datetime
import hashlib
import io
import os
import re
import sys

import pefile

WORKSPACE = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
sys.path.insert(0, os.path.join(WORKSPACE, "detection"))
from xeno_detector import scan_file  # noqa: E402

SAMPLE    = os.path.join(WORKSPACE, "sample", "TEST.dll")
REPORT    = os.path.join(WORKSPACE, "reports", "SAMPLE_REPORT.md")

KNOWN_KEY = bytes.fromhex(
    "3EFD5045ED61BFCA57EFA192D0076696"
    "FDC5F72112BD49367A3FB319A92AF5BB"
)
ZSTD_MAGIC = b"\x28\xb5\x2f\xfd"


def sha256(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for chunk in iter(lambda: f.read(1 << 20), b""):
            h.update(chunk)
    return h.hexdigest()


def entropy(data):
    from collections import Counter
    import math
    if not data:
        return 0.0
    c = Counter(data)
    n = len(data)
    return -sum(v / n * math.log2(v / n) for v in c.values())


def display_path(path):
    """Workspace-relative path for files in the repo, bare file name otherwise."""
    rel = os.path.relpath(os.path.abspath(path), WORKSPACE)
    return os.path.basename(path) if rel.startswith("..") else rel


def get_resources(pe):
    img = pe.get_memory_mapped_image()
    blobs = {}
    if not hasattr(pe, "DIRECTORY_ENTRY_RESOURCE"):
        return blobs

    def walk(d, path=()):
        for e in d.entries:
            name = e.name.string.decode() if e.name else str(e.id)
            p = path + (name,)
            if hasattr(e, "directory"):
                walk(e.directory, p)
            else:
                off, sz = e.data.struct.OffsetToData, e.data.struct.Size
                blobs["/".join(p)] = img[off:off + sz]
    walk(pe.DIRECTORY_ENTRY_RESOURCE)
    return blobs


def recover_xor_key(text_bytes):
    """Yield 32-byte key candidates from `mov dword [reg], imm32` x8 stores
    (the CRT initializer pattern Xeno uses)."""
    pat = re.compile(
        rb"\xC7\x00(....)"
        rb"\xC7\x40\x04(....)\xC7\x40\x08(....)\xC7\x40\x0C(....)"
        rb"\xC7\x40\x10(....)\xC7\x40\x14(....)\xC7\x40\x18(....)\xC7\x40\x1C(....)",
        re.DOTALL)
    for m in pat.finditer(text_bytes):
        yield b"".join(m.groups())


def try_decrypt(blobs, key):
    out = {}
    for name, blob in blobs.items():
        if not name.startswith("8194/"):
            continue
        dec = bytes(b ^ key[i % len(key)] for i, b in enumerate(blob))
        out[name] = dec if dec[:4] == ZSTD_MAGIC else None
    return out


def payload_info(dec):
    try:
        import zstandard as zstd
        raw = zstd.ZstdDecompressor().stream_reader(io.BytesIO(dec)).read()
        first = raw.split(b"\n", 1)[0][:80].decode(errors="replace")
        return len(raw), first
    except Exception as e:
        return None, f"decompress failed: {e}"


def analyze(path):
    """Full static profile of a Xeno-family DLL. Returns a plain dict."""
    raw = open(path, "rb").read()
    pe = pefile.PE(path)
    now = datetime.datetime.now(datetime.UTC).timestamp()

    data = {
        "path": path,
        "size": len(raw),
        "sha256": sha256(path),
        "machine": hex(pe.FILE_HEADER.Machine),
        "timestamp": pe.FILE_HEADER.TimeDateStamp,
        "timestamp_str": datetime.datetime.fromtimestamp(
            pe.FILE_HEADER.TimeDateStamp, datetime.UTC).strftime("%Y-%m-%d %H:%M:%S"),
        "timestamp_future": pe.FILE_HEADER.TimeDateStamp > now,
        "subsystem": pe.OPTIONAL_HEADER.Subsystem,
        "cert_table_size": pe.OPTIONAL_HEADER.DATA_DIRECTORY[
            pefile.DIRECTORY_ENTRY["IMAGE_DIRECTORY_ENTRY_SECURITY"]].Size,
        "imagebase": hex(pe.OPTIONAL_HEADER.ImageBase),
        "entrypoint": hex(pe.OPTIONAL_HEADER.AddressOfEntryPoint),
        "sections": [{
            "name": s.Name.decode(errors="replace").rstrip("\x00"),
            "va": s.VirtualAddress, "vsize": s.Misc_VirtualSize,
            "raw": s.SizeOfRawData, "chars": s.Characteristics,
        } for s in pe.sections],
        "exports": {},
        "imports": {},
        "versions": [],
        "urls": [],
        "env_vars": [],
        "resources": {},          # name -> {size, magic, entropy}
        "xor_key": None,          # hex str, "UNCHANGED", or None
        "xor_key_status": "none", # unchanged | rotated | failed | none
        "payloads": {},           # name -> {size, head}
        "detector": {},
    }

    if hasattr(pe, "DIRECTORY_ENTRY_EXPORT"):
        for e in pe.DIRECTORY_ENTRY_EXPORT.symbols:
            if e.name:
                data["exports"][e.name.decode()] = hex(e.address)

    for entry in getattr(pe, "DIRECTORY_ENTRY_IMPORT", []):
        data["imports"][entry.dll.decode()] = sorted(
            i.name.decode() for i in entry.imports if i.name)

    from collections import Counter
    vers = Counter(v.decode() for v in re.findall(rb"v\d+\.\d+\.\d+", raw))
    data["versions"] = [v for v, _ in vers.most_common(5)]

    strs = set(s.decode() for s in re.findall(rb"[\x20-\x7e]{6,}", raw))
    data["urls"] = sorted(s for s in strs if re.match(r"https?://", s)
                          and "sectigo" not in s and "usertrust" not in s)
    data["env_vars"] = sorted(s for s in strs if re.match(r"%XENO_", s))
    data["strings"] = strs  # used by compare_samples; trimmed there

    blobs = get_resources(pe)
    enc = {k: v for k, v in blobs.items() if k.startswith("8194/")}
    for k, v in enc.items():
        data["resources"][k] = {
            "size": len(v), "magic": v[:4].hex(), "entropy": round(entropy(v), 3)}

    if enc:
        dec_map = try_decrypt(blobs, KNOWN_KEY)
        if all(dec_map.get(k) for k in enc):
            data["xor_key"] = KNOWN_KEY.hex().upper()
            data["xor_key_status"] = "unchanged"
        else:
            text = pe.sections[0].get_data()
            for cand in recover_xor_key(text):
                dm = try_decrypt(blobs, cand)
                if all(dm.get(k) for k in enc):
                    dec_map = dm
                    data["xor_key"] = cand.hex().upper()
                    data["xor_key_status"] = "rotated"
                    break
            else:
                data["xor_key_status"] = "failed"
        if data["xor_key"]:
            for k, dec in dec_map.items():
                size, head = payload_info(dec)
                data["payloads"][k] = {"size": size, "head": head}

    score, verdict, hits = scan_file(path)
    data["detector"] = {"score": score, "verdict": verdict, "hits": hits}
    return data


# ── rendering ───────────────────────────────────────────────────

def render(d):
    L = []
    add = L.append
    add("# SAMPLE_REPORT.md — AUTO-GENERATED")

    add("")

    forged = " **(later than report time)**" if d["timestamp_future"] else ""
    add("## File identity")
    add("")
    add("| Attribute | Value |")
    add("|---|---|")
    add(f"| Path | `{display_path(d['path'])}` |")
    add(f"| Size | {d['size']:,} bytes |")
    add(f"| SHA-256 | `{d['sha256']}` |")
    add(f"| Machine | {d['machine']}{' (x86-64)' if d['machine'] == '0x8664' else ''} |")

    add(f"| Subsystem | {d['subsystem']} |")
    cert = (f"present ({d['cert_table_size']:,} bytes)" if d["cert_table_size"]
            else "absent (no Authenticode signature)")
    add(f"| Certificate table | {cert} |")
    add(f"| ImageBase | {d['imagebase']} |")
    add(f"| EntryPoint | {d['entrypoint']} |")
    add("")

    add("|---|---|---|---|---|")

        add(f"| `{s['name']}` | {hex(s['va'])} | {hex(s['vsize'])} | "

    add("## Exports")
    add("")

        add("")

    add("")

        add("")
    else:
        add("| Resource | Size | Magic | Entropy |")

        if status == "unchanged":

        elif status == "rotated":
            add(f"XOR key: **ROTATED - auto-recovered:** `{d['xor_key']}`")
        else:

        add("")
        if d["payloads"]:
            add("| Resource | Decrypted size | Payload head |")

#!/usr/bin/env python3
"""update_sample.py
Extracts Xeno.dll from the Xeno Electron NSIS installer and installs it
as the workspace analysis sample at sample/TEST.dll (backing up the old one).

Usage:
    python tools/update_sample.py [path-to-installer.exe]

If no installer path is given, the workspace root and sample/ are searched
for a *.exe installer. After replacement the detector is run automatically
to confirm the new sample is identified.

Requires 7-Zip (auto-detected in common install locations, or set SEVEN_ZIP).
"""

import glob
import os
import shutil
import subprocess
import sys
import tempfile
import time

WORKSPACE = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
SAMPLE    = os.path.join(WORKSPACE, "sample", "TEST.dll")
DETECTOR  = os.path.join(WORKSPACE, "detection", "xeno_detector.py")
REPORTER  = os.path.join(WORKSPACE, "tools", "sample_report.py")

SEVEN_ZIP_CANDIDATES = [
    os.environ.get("SEVEN_ZIP", ""),
    r"C:\Program Files\7-Zip\7z.exe",
    r"C:\Program Files (x86)\7-Zip\7z.exe",
    shutil.which("7z") or "",
]


def find_7z():
    for c in SEVEN_ZIP_CANDIDATES:
        if c and os.path.exists(c):
            return c
    sys.exit("ERROR: 7-Zip not found. Install it or set the SEVEN_ZIP env var.")


def find_installer():
    if len(sys.argv) > 1:
        exe = os.path.abspath(sys.argv[1])
        if not os.path.exists(exe):
            sys.exit(f"ERROR: installer not found: {exe}")
        return exe
    candidates = [p for p in glob.glob(os.path.join(WORKSPACE, "*.exe"))
                  + glob.glob(os.path.join(WORKSPACE, "sample", "*.exe"))]
    if not candidates:
        sys.exit("ERROR: no installer .exe found. Drop it in the workspace root "
                 "or pass its path: python tools/update_sample.py <installer.exe>")
    candidates.sort(key=os.path.getsize, reverse=True)
    return candidates[0]


def run_7z(args, cwd=None):
    cmd = [find_7z()] + args
    print(f"  Running: {' '.join(cmd)}")
    result = subprocess.run(cmd, capture_output=True, text=True, cwd=cwd)
    if result.returncode not in (0, 1):  # 7z returns 1 for warnings
        print(f"  STDERR: {result.stderr[:500]}")
        raise RuntimeError(f"7z exited with code {result.returncode}")
    return result.stdout


def find_files(root, name):
    return [os.path.join(dp, f)
            for dp, _, fs in os.walk(root)
            for f in fs if f.lower() == name.lower()]


def main():
    installer = find_installer()
    print(f"Installer: {installer} ({os.path.getsize(installer):,} bytes)")

    # ── Stage 1: extract the NSIS .exe ──────────────────────────
    stage1 = tempfile.mkdtemp(prefix="xeno_stage1_")
    print(f"[1/4] Extracting NSIS installer -> {stage1}")
    run_7z(["x", installer, f"-o{stage1}", "-y"])
    print(f"      Top-level items: {os.listdir(stage1)}")

    # ── Stage 2: extract inner electron archive if present ──────
    inner = (glob.glob(os.path.join(stage1, "**", "app-64.7z"), recursive=True)
             + glob.glob(os.path.join(stage1, "**", "app.7z"), recursive=True)
             + glob.glob(os.path.join(stage1, "**", "*.7z"), recursive=True))
    stage2 = tempfile.mkdtemp(prefix="xeno_stage2_")
    if inner:
        inner.sort(key=os.path.getsize, reverse=True)
        print(f"[2/4] Extracting inner archive: {inner[0]} -> {stage2}")
        run_7z(["x", inner[0], f"-o{stage2}", "-y"])
        search_root = stage2
    else:
        print("[2/4] No inner 7z found - searching stage1 directly")
        search_root = stage1
    print(f"      Search root contents: {os.listdir(search_root)[:20]}")

    # ── Stage 3: locate Xeno.dll ────────────────────────────────
    print(f"[3/4] Searching for Xeno.dll ...")
    matches = find_files(search_root, "Xeno.dll") or find_files(stage1, "Xeno.dll")
    if not matches:
        print("\nERROR: Xeno.dll not found in extracted content. Files seen:")
        for r, _, fs in os.walk(stage1):
            for f in fs:
                print(f"  {os.path.join(r, f)}")
        sys.exit(1)
    matches.sort(key=os.path.getsize, reverse=True)  # largest = real DLL, not a stub
    source_dll = matches[0]
    print(f"  Found: {source_dll} ({os.path.getsize(source_dll):,} bytes)")

    # ── Stage 4: install as sample/TEST.dll ─────────────────────
    if os.path.exists(SAMPLE):
        stamp = time.strftime("%Y%m%d_%H%M%S")
        backup = SAMPLE + f".{stamp}.bak"
        shutil.copy2(SAMPLE, backup)
        print(f"[4/4] Backed up old sample ({os.path.getsize(SAMPLE):,} bytes) -> {backup}")
        os.chmod(SAMPLE, 0o777)  # clear read-only before overwrite
    else:
        print("[4/4] No existing sample - fresh install")
    shutil.copy2(source_dll, SAMPLE)
    print(f"  Installed new sample -> {SAMPLE} ({os.path.getsize(SAMPLE):,} bytes)")

    shutil.rmtree(stage1, ignore_errors=True)
    shutil.rmtree(stage2, ignore_errors=True)

    # ── Verify with the detector ────────────────────────────────
    print("\nRunning detector on the new sample...")
    subprocess.run([sys.executable, DETECTOR, SAMPLE, "-v"])

    # ── Regenerate the auto report ──────────────────────────────
    print("\nRegenerating reports/SAMPLE_REPORT.md ...")
    subprocess.run([sys.executable, REPORTER])

    print("\n[OK] Sample updated.")


if __name__ == "__main__":
    main()
