# Contribuir

## La persona objetivo

Imagina a alguien que hoy no sabe la diferencia entre RAM y disco. Esa persona no es “demasiado principiante”: **es nuestro lector de referencia**.

## Plantilla pedagógica

Una página ideal contiene:

1. Qué vas a aprender.
2. Idea en una frase.
3. Analogía (si ayuda).
4. Modelo técnico real.
5. Conexión con Source 2.
6. Ejemplo verificable de CS2.
7. Errores comunes.
8. Qué puede cambiar en una actualización.
9. Fuentes.
10. Mini ejercicio opcional.

## No pegues números sin contexto

Mal:

```text
EntityList = 0xDEADBEEF
```

Mejor:

> Un dumper puede publicar un **RVA respecto de `client.dll`** para una referencia asociada a la entity list. Ese valor pertenece a una build concreta; lo estable es el concepto y el método para interpretarlo.

## Etiqueta la evidencia

- ✅ Documentado
- 🔬 Observado
- 🧩 Community RE
- ⚠️ Volátil
- 🤔 Inferencia

## Fuentes

Prioridad aproximada:

1. especificación/documentación primaria;
2. artefacto público del juego o dump reproducible;
3. proyecto open source con código/metodología visible;
4. wiki comunitaria mantenida;
5. foro/post individual.

Una fuente de nivel 5 puede ser brillante. Simplemente **no recibe autoridad gratis**.

# Glosario rápido

Este archivo es deliberadamente corto. Si una definición te deja con ganas de preguntar “sí, pero ¿por qué?”, el capítulo enlazado es el lugar correcto.

| Término | Definición corta |
|---|---|
| **Address / dirección** | Número que identifica una ubicación dentro del espacio de direcciones de un proceso. |
| **ASLR** | Aleatorización de ubicaciones de módulos/datos para que una misma imagen no dependa de una dirección absoluta fija. |
| **Base address** | Dirección donde comienza una imagen/módulo cargado en memoria. |
| **Byte** | Unidad de 8 bits. |
| **Class** | Plantilla que describe datos y comportamiento de objetos. |
| **Component** | Pieza de un objeto/sistema separada para una responsabilidad concreta. |
| **ConVar / CVar** | Variable registrada en el sistema de consola. |
| **Console command** | Acción registrada que puede invocarse mediante la consola/sistema de comandos. |
| **Controller** | Objeto que representa aspectos persistentes/lógicos del jugador y referencia al Pawn. |
| **DLL** | Biblioteca dinámica cargada como módulo dentro de un proceso. |
| **Entity** | Objeto gestionado por el sistema de entidades. |
| **Entity handle** | Referencia indirecta/identificador que necesita resolución; no es lo mismo que un pointer. |
| **Field offset** | Distancia desde el comienzo de un objeto hasta uno de sus campos. |
| **Handle** | Identificador indirecto de un objeto/recurso. |
| **Hexadecimal** | Sistema numérico base 16, cómodo para representar bytes y direcciones. |
| **Image** | Ejecutable/DLL en el contexto del loader y formato PE. |
| **Inheritance / herencia** | Una clase deriva de otra y obtiene parte de su estructura/comportamiento. |
| **Interface** | Contrato/API mediante el cual un módulo expone funcionalidad. |
| **KV3** | Formato de datos de Valve usado ampliamente en Source 2. |
| **Module** | Unidad cargada dentro de un proceso, p. ej. EXE o DLL. |
| **Netvar** | Término histórico de Source 1; en Source 2 suele usarse de forma imprecisa si se aplica a cualquier field de Schema. |
| **Offset** | Distancia relativa. Siempre pregunta “¿desde qué base?”. |
| **Pattern / signature** | Patrón de bytes usado para localizar una región de código/datos cuando una dirección no es estable. |
| **Pawn** | Entidad/cuerpo que el jugador controla dentro del mundo. |
| **PE** | Portable Executable, formato de ejecutables/DLL en Windows. |
| **Pointer** | Valor que almacena una dirección. |
| **Prediction** | Simulación/estimación local para reducir sensación de latencia. |
| **Protobuf** | Protocol Buffers; formato/esquema de mensajes usado en partes del ecosistema de Source 2/CS2. |
| **RVA** | Relative Virtual Address: dirección relativa a la base de una imagen cargada. |
| **Schema System** | Sistema de metadata/reflection de Source 2 para clases, fields y tipos. |
| **Scene node** | Nodo de la jerarquía espacial/escena asociado a transforms y relaciones parent/child. |
| **Service** | Objeto especializado al que otro objeto delega un grupo de responsabilidades. |
| **Snapshot** | Representación del estado usada en un punto de la simulación/red. |
| **Subtick** | Información temporal dentro del intervalo de tick usada por CS2 para registrar ciertos eventos/input con más precisión. |
| **Tick** | Paso discreto de simulación. |
| **VPK** | Paquete de archivos usado por juegos Source/Source 2. |
| **VTable** | Tabla de funciones virtuales producida habitualmente por implementaciones de C++. |
| **World-to-screen** | Transformación matemática desde coordenadas 3D del mundo a coordenadas 2D de pantalla. |

git status

No uses `git add -A` a ciegas. Compara primero:

```bash
git status
git diff --no-index ruta/repo-actual ruta/este-paquete
```

# CS2 Internals — desde cero

**Una guía educativa para entender Counter-Strike 2 y Source 2 desde adentro, aunque hoy no sepas programar.**

Este repositorio no quiere enseñarte a copiar `0x12345678` de un paste y rezar para que Valve no actualice el juego. Quiere enseñarte **qué significa ese número, de dónde puede salir, qué objeto representa, por qué puede cambiar y cómo comprobarlo**.

Si nunca viste un pointer, una DLL, un schema, una CVar o una vtable, estás en el lugar correcto.

## La regla del repositorio

Cada tema sigue, siempre que sea posible, esta escalera:

```text
1. Idea cotidiana
        ↓
2. Concepto informático
        ↓
3. Cómo aparece en un programa real
        ↓
4. Cómo lo usa Source 2
        ↓
5. Cómo aparece en CS2
        ↓
6. Cómo comprobarlo con evidencia pública
```

No asumimos C++, assembly ni reverse engineering previo.

## Dos rutas para aprender

### Ruta A — No sé programar

Empieza en [`docs/00-start-here/01-ruta-sin-programacion.md`](docs/00-start-here/01-ruta-sin-programacion.md).

Primero vas a aprender a leer dumps, clases, direcciones y diagramas. **No necesitas abrir Visual Studio** para los primeros laboratorios.

### Ruta B — Ya programo

Puedes comenzar en fundamentos y saltar lo que conozcas. La ruta recomendada es:

```mermaid
flowchart TD
    A[Fundamentos] --> B[Arquitectura de CS2]
    B --> C[Memoria y offsets]
    C --> D[Schema System]
    D --> E[Entity System]
    E --> F[Player / Controller / Pawn]
    F --> G[Rendering y escena]
    F --> H[Input y networking]
    B --> I[CVars y eventos]
    B --> J[Resources]
    C --> K[Reverse engineering]
    H --> L[Demos y protobufs]
```

## Qué cubre

- bits, bytes, hexadecimal y memoria virtual;
- procesos, módulos, DLL, PE, VA y RVA;
- pointers, clases, herencia y estructuras;
- Source 2 y los módulos de CS2;
- offsets, signatures y por qué se rompen;
- Schema System y cómo leer dumps;
- Entity System, handles, Controller/Pawn, services y lifecycle;
- scene graph, transforms, models, skeletons, materiales y partículas;
- inputs, ticks, subticks, snapshots, prediction e interpolation;
- ConVars/CVars, commands, flags y game events;
- weapons, Econ, paint kits, wear, pattern/seed e inventory;
- VPK, KV3 y recursos compilados de Source 2;
- PE, imports/exports, strings, xrefs, RTTI y vtables;
- demos, protobufs y parsers;
- metodología de investigación y cómo distinguir evidencia de especulación.

## Qué NO cubre

Este es un proyecto de **arquitectura, documentación y reverse engineering educativo**. No incluye instrucciones para evadir VAC u otros anti-cheat, ocultar software, desarrollar bypasses o automatizar ventajas injustas en partidas públicas.

Los laboratorios usan archivos públicos, dumps, demos, Workshop Tools, datos estáticos o entornos locales/de prueba.

## Etiquetas de evidencia

Encontrarás estas marcas por todo el repo:

| Marca | Significa |
|---|---|
| ✅ **Documentado** | Fuente primaria/oficial o especificación pública. |
| 🔬 **Observado** | Se puede verificar en una build/dump concreto. |
| 🧩 **Community RE** | Reverse engineering comunitario; útil, pero no oficial. |
| ⚠️ **Volátil** | Puede cambiar con una actualización. |
| 🤔 **Inferencia** | Explicación razonable que aún necesita más evidencia. |

La versión incluida aquí es una **base extensa v0.1**: ya tiene el recorrido completo y capítulos nucleares escritos, pero “TODO CS2” es una meta viva. CS2 cambia, Source 2 es grande y nadie debería fingir que una wiki comunitaria está terminada.

# Cómo leer este repositorio

## Qué vas a aprender

- seguir una ruta sin ahogarte en nombres de clases
- distinguir concepto de dato de build
- usar los enlaces de evidencia

> **Idea en una frase:** No necesitas memorizar CS2; necesitas construir un modelo mental y saber comprobarlo.

## No leas como una enciclopedia

Si abres un header de `C_CSPlayerPawn` el día uno vas a encontrar decenas de campos, services, tipos y clases base. Eso no significa que seas malo: significa que abriste el capítulo 8 antes del capítulo 1.

Lee en capas:

```text
dirección → pointer → objeto → clase → herencia
                           ↓
                      field offset
                           ↓
                  Schema System
                           ↓
                 Entity / Pawn / etc.
```

## Cuando veas un nombre raro

Haz tres preguntas:

1. **¿Qué tipo de cosa es?** clase, field, handle, command, recurso...
2. **¿Quién lo posee?** módulo, objeto, service, entity system...
3. **¿Qué evidencia tengo?** documentación, dump, observación o una inferencia de terceros.

## No memorices offsets

Un offset actual puede durar días, semanas o meses. Su valor pedagógico es pequeño si no sabes qué base usa.

En cambio, entender que un *field offset* describe la distancia entre el inicio de un objeto y un miembro seguirá siendo útil aunque Valve recompile todo mañana.

## Las cajas de evidencia

Cuando una página diga **🔬 Observado**, intenta seguir el enlace y verlo tú mismo. Esa costumbre es el músculo principal del reverse engineering.

# Bits, bytes y hexadecimal

## Qué vas a aprender

- qué es un bit y un byte
- por qué direcciones y bytes suelen escribirse en hexadecimal
- convertir valores simples sin miedo

> **Idea en una frase:** Hexadecimal no es “lenguaje hacker”: es una forma compacta de escribir bits.

## Bit: un interruptor

Un **bit** puede representar dos estados: `0` o `1`.

Ocho bits forman normalmente un **byte**:

```text
0100 0001
└── 8 bits ──┘
```

Un byte puede representar 256 combinaciones: desde 0 hasta 255.

## Por qué hexadecimal

Binario crece muy rápido:

```text
11111111₂ = 255₁₀ = FF₁₆
```

Cada dígito hexadecimal representa exactamente cuatro bits:

```text
0 = 0000    8 = 1000
1 = 0001    9 = 1001
...
A = 1010    F = 1111
```

Por eso un byte se escribe cómodamente con dos dígitos hex: `00`–`FF`.

## El prefijo `0x`

En C/C++ y mucha documentación:

```text
0x10 = 16 decimal
0x20 = 32 decimal
0x100 = 256 decimal
```

El prefijo no forma parte del número “físicamente”. Sólo te dice la base.

## Esto aparecerá en CS2

Verás hexadecimal en:

- direcciones virtuales;
- RVAs;
- field offsets;
- dumps hexadecimales;
- bytes de instrucciones;
- identificadores/flags impresos como bitmasks.

## Ejemplo de offset

Si un objeto empieza en `0x1000` y un field está a `+0x20`:

```text
0x1000 + 0x20 = 0x1020
```

Todavía no hace falta saber qué objeto es. Sólo entendiste una suma relativa.

## Error común

`0x100` **no** significa “cien”. Significa 256 decimal. Si mezclas bases sin darte cuenta, el debugger te va a cobrar intereses.

## Mini ejercicio

Sin calculadora:

- ¿cuánto es `0x10` decimal?
- ¿cuántos bytes hay entre `0x1000` y `0x1010`?
- ¿qué representa `FF` en 8 bits?

# Programas, procesos y módulos

## Qué vas a aprender

- diferenciar archivo ejecutable de proceso
- entender por qué CS2 carga muchas DLL
- ubicar threads a nivel conceptual

> **Idea en una frase:** El `.exe` es un archivo; el proceso es una instancia viva que Windows está ejecutando.

## Archivo vs proceso

En disco tienes algo como `cs2.exe`. Cuando Windows lo inicia crea un **proceso** con:

- un espacio de direcciones virtuales;
- memoria para código/datos/heap/stacks;
- handles a recursos del sistema;
- uno o más threads;
- módulos cargados.

Dos ejecuciones del mismo `.exe` serían dos procesos distintos.

## Módulos

Un ejecutable no tiene que contener todo. Puede cargar DLLs con subsistemas.

Modelo simplificado:

```text
Proceso cs2.exe
│
├─ cs2.exe
├─ client.dll
├─ engine2.dll
├─ schemasystem.dll
├─ inputsystem.dll
└─ ...muchos otros módulos
```

**Módulo** describe aquí una imagen PE cargada en el proceso.

## Threads

Un thread es una secuencia de ejecución dentro del proceso. Un programa moderno puede repartir trabajo entre varios threads: rendering, tareas de recursos, trabajo del engine, etc.

No asumas que “el juego” ejecuta todo línea por línea en un único lugar.

## Por qué importa para internals

Cuando alguien dice:

> “esto está en `client.dll`”

está delimitando **qué imagen/módulo contiene el código o dato observado**. Eso es importante para RVAs, symbols, imports y análisis.

## Error común

DLL ≠ “archivo de offsets”. Es código y datos compilados que el loader mapea en memoria.

# Memoria virtual: el mapa privado del proceso

## Qué vas a aprender

- qué significa dirección virtual
- por qué una dirección no es “un lugar físico de RAM”
- qué papel tiene el sistema operativo

> **Idea en una frase:** Cada proceso trabaja con su propio mapa de direcciones virtuales; el sistema operativo se encarga de mapearlo a memoria real.

## La analogía del edificio

Imagina que cada proceso recibe un plano numerado de oficinas. El proceso usa números de oficina; no necesita saber en qué ladrillo físico del edificio terminó cada cosa.

Eso se parece a **virtual memory**.

## Dirección virtual

Un valor como:

```text
0x00007FF6ABCDEF00
```

puede ser una dirección virtual válida en un proceso concreto. Otro proceso puede tener la misma dirección numérica mapeada a algo completamente diferente.

✅ **Documentado:** Windows da a cada proceso de user mode un espacio de direcciones virtuales privado. Las páginas virtuales se traducen mediante estructuras administradas por el sistema.

## Páginas y regiones

La memoria se gestiona en páginas/regiones con propiedades como:

- reservada o committed;
- readable;
- writable;
- executable.

Eso explica por qué código y datos suelen vivir en regiones con protecciones distintas.

## ASLR

Address Space Layout Randomization hace que no debas confiar en que una imagen estará siempre en la misma dirección absoluta.

Por eso aparece tanto el patrón:

```text
base del módulo + RVA
```

## Lo importante para CS2

Nunca construyas tu modelo mental alrededor de una dirección absoluta que viste en una captura. Pregunta:

1. ¿a qué proceso pertenece?
2. ¿a qué módulo/región?
3. ¿es dirección absoluta o relativa?
4. ¿es válida sólo para esa ejecución/build?

## Fuentes y siguiente lectura

- [Microsoft: Virtual Address Spaces](https://learn.microsoft.com/en-us/windows-hardware/drivers/gettingstarted/virtual-address-spaces)
- [Microsoft: PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)

# Pointers sin trauma

## Qué vas a aprender

- qué guarda realmente un pointer
- diferenciar objeto, dirección y pointer
- entender una cadena de referencias

> **Idea en una frase:** Un pointer es una variable cuyo valor se interpreta como la dirección de otra cosa.

## Tres cosas distintas

Supongamos que un `Player` está en `0x5000`.

```text
Dirección        Contenido
0x1000           0x5000   ← variable pointer
...
0x5000           Player   ← objeto
```

- `0x5000` es una **dirección**.
- el objeto vive en esa dirección.
- una variable almacenada en `0x1000` contiene `0x5000`: esa variable actúa como **pointer**.

## En C++

```cpp
Player* player;
```

El `*` en una declaración indica que `player` es un pointer a `Player`.

```cpp
player->health
```

significa, de forma conceptual: “ve al objeto apuntado por `player` y accede a su field `health`”.

## Pointer nulo

Un pointer puede no apuntar a un objeto válido. `nullptr` es la forma moderna de expresar ausencia de objeto en C++.

## Pointer ≠ handle

Esto será esencial en CS2:

```text
Pointer ───────────────► dirección del objeto

Handle ─► identificador ─► sistema que lo resuelve ─► objeto
```

Un `CHandle<T>` no debe imaginarse como `T*` con otro nombre.

## Pointer chain

Los objetos pueden referenciar otros objetos:

```text
A ─► B ─► C
```

Eso no significa que C esté “dentro” de A. Puede ser composición mediante referencias.

## Error clásico

Si una dirección fue válida hace un instante, no prueba que el objeto siga vivo. Lifecycle y ownership importan tanto como el tipo.

# Structs, clases, fields, herencia y composición

## Qué vas a aprender

- leer una clase C++ básica
- entender field offsets
- diferenciar herencia de composición

> **Idea en una frase:** Una clase describe la forma de un objeto; herencia dice “es un tipo de”, composición dice “tiene un”.

## Clase simplificada

```cpp
class Player {
public:
    int health;
    int team;
};
```

Un objeto `Player` contiene estado. Cada field ocupa bytes dentro de la disposición del objeto.

### Field offset

Ejemplo inventado:

```text
Player base
+0x00  health
+0x04  team
```

`+0x04` significa “cuatro bytes desde el comienzo de este objeto”.

## Herencia

```cpp
class Entity { ... };
class Pawn : public Entity { ... };
```

`Pawn` deriva de `Entity`.

Modelo mental:

```text
Pawn
├─ parte heredada de Entity
└─ fields propios de Pawn
```

En dumps de Schema vas a seguir cadenas de herencia todo el tiempo.

## Composición

```cpp
class Pawn {
    MovementServices* movement;
};
```

Ahora `Pawn` **tiene una referencia a** otro objeto especializado. No es lo mismo que heredar de él.

## Por qué Source 2 parece una matrioshka

Las clases grandes delegan responsabilidades a componentes/services y scene nodes. Si buscas “todo lo del player” en una sola clase, vas a frustrarte.

## Error común

Encontrar `m_iHealth` en una clase base no significa que “no pertenezca” al Pawn. Un objeto derivado incluye la parte heredada de sus bases.

# DLL, PE, VA y RVA

## Qué vas a aprender

- qué es PE/COFF
- diferenciar file offset, VA y RVA
- entender `base + RVA`

> **Idea en una frase:** Un RVA es una dirección relativa a la base de una imagen cargada; no es lo mismo que una posición en el archivo.

## Portable Executable

Windows usa el formato **PE/COFF** para imágenes ejecutables como EXE y DLL.

Una imagen contiene headers y secciones. Algunas secciones agrupan código o datos; también existen estructuras para imports, exports, relocations y resources.

✅ **Documentado:** Microsoft define **RVA** como la dirección de un elemento después de cargar la imagen, **menos la base de la imagen**.

## Fórmula

```text
VA = ImageBase + RVA
RVA = VA - ImageBase
```

Ejemplo inventado:

```text
base(client.dll) = 0x7FF600000000
RVA              = 0x00123450
VA               = 0x7FF600123450
```

## File offset no es RVA

El archivo en disco tiene su propia disposición. Un byte en posición `0x500` del archivo no tiene por qué terminar en RVA `0x500` cuando la imagen se carga.

Esto es una fuente clásica de errores al saltar entre hex editor, disassembler y memoria.

## Imports y exports

- **Imports**: símbolos que la imagen necesita de otras DLL.
- **Exports**: símbolos que la imagen hace visibles a consumidores externos.

No todo lo interesante está exportado. Reverse engineering existe, en parte, porque muchos detalles internos no tienen símbolo público cómodo.

## Relocations y ASLR

Si la imagen no carga en su base preferida, relocations permiten ajustar referencias que lo necesiten. ASLR hace que apoyarse en VA absolutas sea frágil.

## Conexión directa con offsets de CS2

Cuando un dumper publica algo asociado a `client.dll`, pregunta si está publicando:

- un RVA respecto a la base del módulo;
- un field offset de una clase;
- otra clase de desplazamiento.

La palabra “offset” sola es insuficiente.

## Fuentes y siguiente lectura

- [Microsoft PE Format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)

## Qué vas a aprender

- leer declaraciones comunes sin aprender todo C++
- interpretar pointers, templates y herencia
- reconocer tipos de tamaño fijo

> **Idea en una frase:** Para leer dumps necesitas alfabetización de C++, no convertirte primero en ingeniero de compiladores.

## Tipos

```cpp
bool alive;
int32_t health;
uint64_t id;
float speed;
```

Los prefijos `int32_t`, `uint64_t`, etc. explicitan tamaño/signo mejor que tipos dependientes de plataforma.

## Pointer y reference

```cpp
Player* p;   // pointer
Player& r;   // reference C++
```

No confundas `reference` del lenguaje con “referencia” usada informalmente en arquitectura.

## Templates

```cpp
CHandle<C_BasePlayerPawn> m_hPawn;
```

`CHandle<...>` es una plantilla parametrizada por el tipo de objeto esperado. Léelo primero como:

> “un handle que conceptualmente referencia un `C_BasePlayerPawn`”.

No necesitas conocer metaprogramming para seguir.

## Herencia

```cpp
class CCSPlayerController : public CBasePlayerController
```

Significa que el primero deriva del segundo.

## Namespace

```cpp
namespace offsets { ... }
```

Agrupa nombres para evitar colisiones y dar estructura.

## `const`, `constexpr`, `static`

Aparecen mucho en código de herramientas. Para leer documentación inicial:

- `const`: no modificar a través de esa vista;
- `constexpr`: puede evaluarse como constante en compile time en contextos válidos;
- `static`: tiene varios significados según contexto; no asumas uno sin ver dónde aparece.

## Lo que todavía puedes ignorar

# Qué es realmente un offset

## Qué vas a aprender

- definir offset como relación
- calcular un field offset sencillo
- preguntar siempre cuál es la base

> **Idea en una frase:** Offset significa distancia relativa; sin saber “desde dónde”, el número está incompleto.

## Un ejemplo que no tiene nada que ver con CS2

Imagina una fila de casilleros:

```text
Base del objeto = 0x1000

+0x00  [ id     ]
+0x04  [ health ]
+0x08  [ team   ]
```

La dirección de `health` sería:

```text
0x1000 + 0x04 = 0x1004
```

El `0x04` es un **field offset**.

## El mismo término, bases distintas

En internals verás “offset” para:

- field offset dentro de un objeto;
- RVA dentro de una imagen;
- displacement codificado en una instrucción;
- offset dentro de un archivo;
- índice/desplazamiento dentro de estructuras.

Escribe siempre la relación completa:

```text
field_address = object_address + field_offset
symbol_va     = module_base + rva
```

## Offset no es pointer

Un offset normalmente no “apunta”. Es un número que se suma/interpreta respecto de una base.

## ¿Por qué la comunidad habla tanto de offsets?

Porque cuando no tienes source code del juego, necesitas formas de ubicar datos y reconstruir layouts. Pero reducir reverse engineering a “buscar offsets” es como reducir mecánica a “saber dónde está el tornillo”.

## La pregunta que te salva

Cada vez que alguien publique:

```text
foo = 0xABC
```

pregunta:

> **¿0xABC respecto de qué?**

Si la fuente no puede responderlo, todavía no tienes una explicación.

# Taxonomía de offsets en CS2

## Qué vas a aprender

- separar field offsets de module RVAs
- entender datos derivados por Schema y por pattern
- leer outputs sin mezclar categorías

> **Idea en una frase:** “Offset de CS2” no es una categoría técnica única; es un paraguas comunitario para relaciones muy distintas.

## 1. Field/schema offset

Describe dónde cae un miembro dentro de una instancia:

```text
object + field_offset → field
```

Schema puede exponer metadata útil para muchas clases/fields.

## 2. Module-relative RVA

Describe una ubicación respecto de la base de una imagen:

```text
base(client.dll) + RVA → location
```

Un dumper puede publicar RVAs para objetos globales o referencias internas descubiertas por análisis/patterns.

## 3. Instruction displacement

En x86-64 hay instrucciones con desplazamientos relativos. Una herramienta puede leer los bytes de una instrucción y calcular un destino. Ese displacement **no es automáticamente el RVA final que quieres publicar**.

## 4. File offset

Es posición dentro del archivo en disco. PE establece una relación entre secciones en archivo y en memoria, pero no son idénticas.

## 5. Array/index stride

A veces “offset” se usa informalmente para desplazarse dentro de arrays/entries. Debes conocer tamaño/stride y estructura.

## Tabla mental

| Si tengo... | Base | Resultado |
|---|---|---|
| field offset | address del objeto | address del field |
| RVA | image base | VA runtime |
| file offset | comienzo del archivo | posición en disco |
| instruction displacement | contexto de la instrucción | destino calculado |

## Por qué importa

Copiar un field offset y sumarlo a `client.dll` puede producir una dirección numéricamente válida que significa absolutamente nada. Los bugs más crueles suelen tener números perfectamente hexadecimales.

# Signatures y pattern scanning — concepto

## Qué vas a aprender

- entender por qué buscar bytes puede ser más robusto que una dirección fija
- distinguir pattern de resultado
- conocer sus límites

> **Idea en una frase:** Una signature intenta reconocer una región por su forma en bytes, no por una dirección absoluta.

## El problema

Supón que una función estaba en RVA `0x100000` y una update la mueve a `0x110000`. Guardar el RVA viejo falla aunque el código relevante siga teniendo una secuencia reconocible.

## Idea de pattern

Ejemplo **inventado** sobre un archivo de práctica:

```text
48 8B 05 ?? ?? ?? ?? 48 85 C0
```

Los `??` son wildcards: bytes que no exigimos que coincidan.

La herramienta busca regiones que encajen con la forma.

## Pattern ≠ target

Encontrar el comienzo de una instrucción puede ser sólo el primer paso. En x86-64 una instrucción puede usar un displacement relativo. El target final se calcula usando:

- dirección de la instrucción;
- longitud de la instrucción;
- displacement decodificado.

## Calidad de una signature

Una signature útil intenta ser:

- suficientemente única;
- suficientemente estable;
- lo bastante corta para no incluir bytes volátiles innecesarios.

Eso es un equilibrio, no magia.

## Limitaciones

Una optimización del compilador puede reescribir por completo la secuencia. También puede aparecer el mismo pattern en varios lugares.

## Alcance de este repo

Los laboratorios de pattern scanning usarán blobs/binarios de práctica o snapshots estáticos. No enseñaremos evasión de anti-cheat ni scanning operativo destinado a abuso en partidas públicas.

# Entity System: quién administra los objetos del mundo

## Qué vas a aprender

- qué es una entity
- por qué existe un sistema central de entidades
- diferenciar entity de cualquier objeto C++

> **Idea en una frase:** Una entity es un objeto integrado al sistema de entidades del juego; no toda clase del engine es una entity.

## Qué cuenta como entity

Jugadores, armas, proyectiles, bombas y muchos objetos del mundo pueden aparecer como clases de entidad. Pero también existen objetos auxiliares/services/nodes que no deben imaginarse automáticamente como entidades independientes.

Un Entity System necesita resolver problemas como:

- crear/destruir entidades;
- identificarlas;
- permitir referencias;
- iterarlas/consultarlas;
- evitar confundir una entidad destruida con otra que reutilizó recursos/slots.

flowchart TD

    E1 --> PC[Player Controller]
    E2 --> PP[Player Pawn]

```text
handle ─► resolver/registry ─► object actual

Supón:

Si tu referencia sólo decía “42”, podrías confundir B con A.

## Stale handle

Un handle stale es conceptualmente una referencia cuyo objetivo original ya no es válido.

Esto importa muchísimo en:

- muerte/respawn;
- cambio de Pawn;
- destrucción de weapons/projectiles;
- entidades visuales/temporales;
- cambio de mapa.

## Regla de oro

Nunca uses:

> “el número del handle sigue igual”

como prueba suficiente de:

> “es el mismo objeto vivo”.

Valida el resultado y lifecycle.

# Espacios de coordenadas: local, world, view y screen

## Qué vas a aprender

## Coordenadas locales

Un objeto hijo puede expresar su posición respecto de su parent.

    C --> N[NDC]

# View, projection y World-to-Screen

## Qué vas a aprender

- entender la matemática conceptual de W2S
- saber qué hace la división por w
- reconocer puntos detrás de cámara

> **Idea en una frase:** World-to-Screen es álgebra lineal: transformar un punto 3D hasta coordenadas de pantalla.

## Sin código de juego

Tomemos un punto homogéneo:

```text
p_world = (x, y, z, 1)
```

Una pipeline típica usa matrices de view y projection:

```text
p_clip = Projection × View × p_world
```

A veces se dispone de una matriz combinada view-projection.

## La componente W

Después de la multiplicación obtienes algo del estilo:

```text
(xc, yc, zc, wc)
```

Se realiza la división perspectiva:

```text
x_ndc = xc / wc
y_ndc = yc / wc
```

Si `wc` está cerca de cero o representa un punto detrás del plano visible según la convención usada, debes tratarlo adecuadamente.

## De NDC a píxeles

Para una convención común con NDC en `[-1, +1]`:

```text
screen_x = (x_ndc + 1) * width  / 2
screen_y = (1 - y_ndc) * height / 2
```

El signo/orientación vertical depende de la convención de pantalla/API.

## Lo importante

No existe una función mística `W2S`. Existen:

1. coordinate spaces;
2. matrices/transforms;
3. projection;
4. perspective divide;
5. viewport mapping.

## Práctica segura

Implementa W2S sobre un cubo 3D inventado en Python/C++ o papel. No necesitas leer CS2 para aprender la matemática.

## Qué vas a aprender

## Tick

Un servidor de juego actualiza simulación en pasos. A una frecuencia de 64 Hz, por ejemplo, un intervalo dura aproximadamente 15,625 ms.

> ciertos inputs/eventos llevan timing más preciso dentro del intervalo de simulación.

> “CS2 ya no tiene ticks”.

       ^ click
       ^ movement change
             ^ release

Subtick permite representar esos offsets temporales con más detalle que asignar todo al borde del tick.

# Prediction e interpolation

## Qué vas a aprender

- entender por qué existen
- diferenciarlas
- ver cómo encajan con latencia y snapshots

> **Idea en una frase:** Prediction intenta responder antes de la confirmación; interpolation intenta presentar suavemente estados recibidos.

## El problema de la red

Si tu ping es 40 ms, esperar confirmación remota antes de mostrar cada movimiento haría el control desagradable.

## Prediction

El cliente puede simular localmente resultados previsibles del input. Cuando llega estado autoritativo, compara/reconcilia.

```text
input → predicción local
        ↓
      servidor → estado confirmado
        ↓
   comparar/corregir
```

## Interpolation

Para otros objetos, el cliente puede tener snapshots separados en el tiempo y renderizar un estado intermedio para suavidad.

```text
snapshot A ---- render aquí ---- snapshot B
```

## Extrapolation

Proyectar más allá del último estado conocido. Es diferente y más arriesgado cuando cambian acciones bruscamente.

## CS2

Los detalles exactos de prediction/netcode son complejos y cambian. Este capítulo enseña el vocabulario para luego leer con criterio dumps, networking docs y demo parsers.

## Error común

“Prediction” no significa “el cliente decide”. La autoridad y la respuesta visual local pueden coexistir.

# Snapshots, deltas y estado de red

## Qué vas a aprender

- entender por qué no se envía “toda la RAM”
- qué significa delta conceptualmente
- relacionar snapshots con interpolation

> **Idea en una frase:** Networking transmite representaciones seleccionadas del estado; los deltas evitan reenviar todo cuando sólo cambió una parte.

## Snapshot conceptual

Un snapshot es una vista del estado relevante en un instante/sequence.

```text
Snapshot A: player x=10, hp=100
Snapshot B: player x=12, hp=100

La implementación real usa serializers, baselines, entity state y mecanismos específicos del engine.

- interpolation;
- packet loss recovery;
- entity creation/destruction;

# Strings, xrefs, RTTI y vtables

## Qué vas a aprender

- usar strings como pistas
- entender cross-references
- reconocer RTTI/vtables en C++

> **Idea en una frase:** Los binarios pierden mucha información humana al compilar, pero dejan pistas: strings, tipos, tablas y relaciones de código.

## Strings

Mensajes de error, nombres de commands, paths y logs pueden sobrevivir compilación. Buscar una string y ver quién la referencia es una técnica estática básica.

## Xref

Cross-reference = lugar que referencia otra cosa.

```text
string "example" ← referenced by function A
function A        ← called by function B
```

Seguir xrefs permite navegar desde una pista humana hacia código.

## RTTI

C++ puede incluir Run-Time Type Information para soportar ciertas operaciones de tipos. Tooling puede aprovechar metadata residual para reconstruir nombres/jerarquías en algunos binarios.

No todos los tipos aparecen ni toda build conserva la misma riqueza.

## VTable

Clases con funciones virtuales suelen implementarse mediante una tabla de function pointers:

```text
object
└─ vptr ─► vtable
           ├─ virtual fn 0
           ├─ virtual fn 1
           └─ ...
```

El standard de C++ describe semantics virtuales; el layout binario depende de ABI/compiler.

## Por qué importa

Interfaces y clases polimórficas del engine pueden estudiarse mediante vtables/RTTI. Pero asignar “index 37 = función X” sin build/fuente es extremadamente volátil.

# Assembly x86-64 mínimo

## Qué vas a aprender

- leer registers y operaciones básicas
- entender load/store/branch/call
- reconocer RIP-relative addressing

> **Idea en una frase:** No necesitas escribir assembly; necesitas poder leer la historia básica que cuentan unas instrucciones.

## Registers

En x86-64 encontrarás registros generales como:

```text
RAX RBX RCX RDX RSI RDI RSP RBP R8...R15
```

Subregistros (`EAX`, `AX`, `AL`) representan partes del mismo registro con reglas específicas.

## Operaciones comunes

```asm
mov rax, [rcx+20h]   ; cargar desde memoria
lea rdx, [rax+10h]   ; calcular dirección
cmp eax, 0           ; comparar
test rax, rax        ; test de bits / null frecuente
je somewhere         ; branch condicional
call function        ; llamada
ret                   ; retorno
```

Son ejemplos genéricos, no instrucciones extraídas de CS2.

## Corchetes

`[address]` significa acceso a memoria en sintaxis Intel.

```asm
mov eax, [rcx+20h]
```

si `rcx` apunta a un objeto, `+20h` podría ser un field displacement. Pero **sólo el contexto** te permite afirmar qué field.

## RIP-relative

x86-64 usa frecuentemente addressing relativo al instruction pointer para globals/static data. Por eso un pattern scanner puede encontrar una instrucción y luego resolver su displacement.

## No decompiles a fe ciega

Un decompiler produce pseudocódigo aproximado. Cuando una línea importa, vuelve al assembly y revisa tipos/branches.

# Calling conventions y parámetros

## Qué vas a aprender

- entender qué problema resuelve una calling convention
- leer argumentos en Windows x64 a nivel básico
- no inferir firmas sólo por nombres

> **Idea en una frase:** Una calling convention define cómo caller y callee acuerdan pasar argumentos, retorno y preservar estado.

## Windows x64 — idea básica

En la ABI x64 de Microsoft, los primeros argumentos integer/pointer suelen viajar en registros como:

```text

Para una función miembro no estática, el pointer `this` se pasa como argumento implícito según ABI. En Windows x64 normalmente ocupa el primer registro integer correspondiente (`RCX`).

Eso ayuda a reconocer patterns como:

```asm
mov rax, [rcx+...]
```

al comienzo de una función miembro.

Una llamada virtual puede obtener function pointer desde vtable antes de `call`. El índice observado depende del layout/build.

# Errores comunes de principiante

## “Offset” sin base

Pregunta siempre desde qué address/image/object se mide.

## Address = object

Una dirección sólo te lleva a bytes. Interpretarlos como `Player` exige evidencia de tipo/lifecycle.

## Pointer = handle

No. Un handle necesita resolución/validación y existe para resolver problemas distintos.

## Field de Schema = netvar

No necesariamente. Schema metadata y networking son capas diferentes.

## Controller = Pawn

No. Están relacionados, pero son objetos distintos.

## Pawn = persona

No necesariamente a través del tiempo. El mismo participante puede tener distintos Pawns.

## “Está en client.dll, entonces el cliente manda”

Ubicación de representación/código no determina autoridad del servidor.

## “Mismo nombre, mismo layout client/server”

No lo asumas. Comprueba el scope/módulo.

## “El pattern es eterno”

Puede romperse por recompilación/optimización.

## “El número cambió, sólo actualizo números”

Tal vez cambió la semántica. Revalida invariantes.

## “UnknownCheats lo dijo”

Puede ser una pista excelente. Sigue la evidencia, el commit, el dump o la prueba reproducible.

## “El dump es source code de Valve”

No. Es una representación generada/extraída por tooling. Diferencia source original de reverse-engineered/generated output.

# FAQ

## ¿Necesito C++?

Para empezar, no. Para reverse engineering profundo y leer código/tooling, sí conviene aprenderlo.

## ¿Necesito saber assembly?

No para Schema/demos/resources. Sí para análisis binario serio.

## ¿Por qué no publicamos una tabla “offsets actuales”?

Porque ya existen herramientas dedicadas y esa tabla envejece rápido. Aquí enseñamos qué representan y cómo verificarlos.

## ¿Schema elimina la necesidad de signatures?

No. Schema ayuda con metadata de tipos/fields; localizar otros objetos/functions/globals puede requerir otras técnicas.

## ¿Todo lo que existe en `commands.txt` funciona en mi consola?

No. Lee flags y restricciones (`developmentonly`, `cheat`, contexto client/server, etc.).

## ¿Source 2 es open source?

No. Hay tooling/documentación oficial parcial y una enorme cantidad de reverse engineering comunitario.

## ¿Puedo aprender con un servidor local?

Sí; para runtime experiments, un entorno local/development autorizado es preferible a matchmaking.

## ¿Este repo enseña cheats?

No. Explica internals y RE. Muchos conceptos son dual-use, así que los laboratorios evitan bypass/evasión y abuso competitivo.

## ¿Qué es lo primero que debería poder explicar?

La diferencia entre **address, pointer, offset, RVA y handle**. Si eso está sólido, todo lo demás se vuelve mucho menos hostil.

# De Source 1 a Source 2: qué vocabulario quedó viejo

## Qué vas a aprender

- identificar términos heredados
- entender Controller/Pawn y Schema como cambios mentales
- leer tutoriales viejos con contexto

> **Idea en una frase:** Muchos errores modernos vienen de aplicar un mapa mental de Source 1 a un engine que reorganizó tipos y sistemas.

## Netvars

En Source 1, send/recv tables popularizaron el vocabulario de netvars. En Source 2, Schema System es una fuente mucho más amplia de metadata de tipos; llamar netvar a todo schema field pierde precisión.

## Player entity

El modelo Controller/Pawn hace explícita una separación que obliga a preguntar qué parte de “player” necesitas.

## Resources

Source 2 usa un pipeline moderno de compiled resources/KV3 y nuevas herramientas/formatos.

## Tools/APIs

Plugin frameworks tuvieron que reconstruir soporte para Source 2. El tracker de AlliedModders HL2SDK para CS2 muestra trabajo comunitario específico en ConVar/ConCommand e interfaces, evidencia de que no fue un simple cambio de nombre.

## Regla al leer material viejo

Para cada tutorial de CS:GO/Source 1 pregunta:

- ¿es concepto general o implementación de Source 1?
- ¿existe equivalente en Source 2?
- ¿cambió el ownership/lifecycle?
- ¿hay una fuente CS2 actual que lo confirme?
