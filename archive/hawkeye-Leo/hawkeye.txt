      <h3>Illustrated guide</h3>
      <p>
        This is the Community walkthrough. Run <code>!help</code> for the full
        command catalog; run any command with no arguments for usage.
        Hawkeye Lab includes every command here plus detection and
        <code>!analyze</code> &mdash; see the <a href="lab/">Lab page</a>.

      <article class="guide-step" id="driver-setup">
        <strong>1. Driver setup</strong>
        <p>
          Start Hawkeye Community and open <strong>Driver setup</strong>.
          The last row, <strong>Driver</strong>, is the one that matters.
        </p>
        <p>
          If you see Figure 1, work the red rows. <strong>Enable test signing</strong>
          turns on the test-signing environment and installs the Hawkeye test
          certificate. <strong>Open Windows Security</strong> is where you turn
          Memory integrity off.
        </p>
        <figure class="figure">
          <img src="guide/driver-setup-1.png" alt="Driver setup with test signing off and Memory integrity on. The status-bar Driver setup button opens this window.">
          <figcaption>Figure 1. Driver is not loaded. Use the links on the red rows.</figcaption>
        </figure>
        <p>Figure 2 means the changes are staged. Restart Windows.</p>
        <figure class="figure">
          <img src="guide/driver-setup-2.png" alt="Driver setup after test signing is set and Memory integrity is off. Both rows say Restart needed.">
          <figcaption>Figure 2. Restart Windows, then start Hawkeye again.</figcaption>
        </figure>
        <p>
          If the machine boots with Secure Boot, Windows blocks <code>bcdedit</code>.
          Turn Secure Boot off in firmware first, start Windows, then use
          <strong>Enable test signing</strong>.
        </p>
        <p>
          After the restart, <strong>Driver OK</strong> on the status bar means
          the environment is ready. <code>!help</code> is the full catalog.
          Run any command with no arguments for usage.
        </p>
        <figure class="figure">
          <img src="guide/help-catalog.png" alt="Hawkeye Community after Driver OK, showing the !help command reference.">
          <figcaption>Figure 3. Driver OK, and <code>!help</code> listing the bench.</figcaption>
        </figure>
        <p>
          If you hit a bug, or you have a suggestion, run <code>!support</code>
          and write to us.
        </p>
      </article>

      <article class="guide-step" id="probe">
        <strong>2. <code>!probe</code> &mdash; the entry</strong>
        <p>
          If you are curious about a process &mdash; System (kernel, PID 4), or
          <code>dwm.exe</code> &mdash; you need one place to start. That is
          <code>!probe</code>.
        </p>
        <p>
          The question is rarely one name. How composition works. How the
          desktop keeps a window's pixels from other clients. How the kernel
          schedules threads. How ETW reaches a third-party driver. Those
          trails cross modules.
        </p>
        <p>
          <code>!probe</code> attaches a live symbol context to that process
          (or the kernel) and lets you query many names together, so the
          clues stay in one view. IDA &mdash; or IDA-MCP &mdash; is how you get to the
          one you want.
        </p>
        <p>
          Run <code>!probe</code> with no arguments for usage. Attach, then
          <code>-find</code>.
        </p>
        <figure class="figure">
          <img src="guide/probe-usage.png" alt="!probe usage in Hawkeye Community: attach, -find, and the dwm.exe example with -mod:.">
          <figcaption>Figure 4. <code>!probe</code> with no arguments &mdash; read this, then attach.</figcaption>
        </figure>
        <p>
          <code>-find</code> only searches symbols that are already indexed.
          The first time, pass <code>-mod:</code> with the modules you care
          about. Missing PDBs are downloaded and loaded &mdash; that takes a
          moment.
        </p>
        <p>
          Example from the usage:
          <code>!probe -find:swapchain,present -mod:dwmcore,dwmredir,udwm -kind:all</code>.
          Those three DLLs are the ones you are looking at. The comma is AND:
          a name must contain both <code>present</code> and
          <code>swapchain</code>. That joint hit is the start of the next
          question, not the answer.
        </p>
        <figure class="figure">
          <img src="guide/probe-find.png" alt="!probe -find across dwmcore, dwmredir, and udwm. Missing PDBs load, then 73 joint hits.">
          <figcaption>Figure 5. The same line: missing PDBs load, then the joint hits.</figcaption>
        </figure>
        <p>
          <code>!probe -status</code> shows what is loaded so far.
        </p>
        <figure class="figure">
          <img src="guide/probe-status.png" alt="!probe -status: attached PID, indexed symbol count, and which modules have a PDB.">
          <figcaption>Figure 6. <code>!probe -status</code> &mdash; which symbols are loaded.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="etw">
        <strong>3. <code>!etw</code> &mdash; who actually ran</strong>
        <p>
          <code>!probe</code> is names. <code>!etw</code> is execution:
          which addresses ran in this window.
        </p>
        <p>
          Injected code is often not a module. It lives on the heap inside
          another process. Nothing in the module list names it. Sampling
          sees it only if a thread ran it.
        </p>
        <p>
          Run <code>!etw</code> with no arguments for usage. Pick a process,
          a thread, or <code>-all</code>.
        </p>
        <figure class="figure">
          <img src="guide/etw-usage.png" alt="!etw usage in Hawkeye Community: sample a process, a thread, or the whole system.">
          <figcaption>Figure 7. <code>!etw</code> with no arguments &mdash; read this, then pick a scope.</figcaption>
        </figure>
        <p>
          Default sampling lists RIP under each thread &mdash; the instruction
          pointers that thread was seen at. That is enough to sketch what
          it was doing.
        </p>
        <figure class="figure">
          <img src="guide/etw-rip-1.png" alt="!etw RIP samples grouped under a process, then a thread.">
          <figcaption>Figure 8. RIP under the thread &mdash; addresses it was sampled at.</figcaption>
        </figure>
        <p>
          For one thread,
          <code>!etw -tid:&lt;tid&gt; -stack:1</code>
          samples call stacks instead. Stacks hit in that window are shown.
        </p>
        <p>
          Figure 9 is the thread that composes in <code>dwm.exe</code>.
          The stacks are <code>dwm</code> putting windows together.
        </p>
        <figure class="figure">
          <img src="guide/etw-stack.png" alt="!etw -stack:1 on a dwm.exe thread: composition stacks with symbols resolved.">
          <figcaption>Figure 9. <code>dwm.exe</code> &mdash; composition stacks for that thread.</figcaption>
        </figure>
        <p>
          <code>!sym</code> downloads and loads symbols. <code>!etw</code>
          resolves names from what is loaded. Run <code>!sym</code> for
          usage.
        </p>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="kernel-region">
        <strong>4. <code>!kernel_region</code> &mdash; which band</strong>
        <p>
          A kernel VA has a type. <code>!kernel_region</code> names it.
        </p>
        <p>
          <code>!kernel_region -list</code> shows the live IDs on this
          machine. They differ by OS.
        </p>
        <p>
          Typically <code>ntoskrnl</code>, driver images, and UEFI land in
          <code>imageMType</code>. Kernel stacks in
          <code>stackMType</code>. Paged pool in
          <code>pagedMType</code>. Nonpaged pool in
          <code>nonpagedMType</code>. Unexpected kernel code often lands in
          <code>systemMType</code>.
        </p>
        <p>
          Run <code>!kernel_region</code> with no arguments for usage.
          <code>-list</code> is the map. <code>-va:</code> asks one address.
        </p>
        <figure class="figure">
          <img src="guide/kernel-region-list.png" alt="!kernel_region usage and -list: live region IDs on this system.">
          <figcaption>Figure 10. Usage, then <code>-list</code> &mdash; IDs on this machine.</figcaption>
        </figure>
        <p>
          <code>-va:</code> takes one address. Use a RIP from
          <code>!etw</code>. This one is in <code>ntoskrnl</code>, so the
          type is image. That narrows the scope. Deeper analysis starts
          from there.
        </p>
        <figure class="figure">
          <img src="guide/kernel-region-va.png" alt="!kernel_region -va example: a sampled ntoskrnl RIP classified as image region.">
          <figcaption>Figure 11. Example of <code>-va:</code> &mdash; this RIP is image.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="memory">
        <strong>5. Memory &mdash; ReadMemory</strong>
        <p>
          A VA from the bench is enough. <strong>Memory</strong> opens the
          viewer. PID, address, <strong>ReadMemory</strong>. One page:
          disassembly and hex.
        </p>
        <p>
          One way to get that VA:
          <code>!iguard_scan -all</code>.
          It walks kernel modules for
          <code>_guard_dispatch_icall</code> pits. A hit is a placeholder
          that points at executable system or nonpaged memory.
          <code>-all</code> is every kernel module;
          <code>-m:</code> is one driver. Run
          <code>!iguard_scan</code> with no arguments for usage.
        </p>
        <figure class="figure">
          <img src="guide/memory-iguard-sym.png" alt="!iguard_scan -m:ntoskrnl.exe -sym:1: named pit targets, and the Memory button.">
          <figcaption>Figure 12. <code>!iguard_scan -m:ntoskrnl.exe -sym:1</code> &mdash; a pit with names, then <strong>Memory</strong>.</figcaption>
        </figure>
        <p>
          Copy the target into Memory.
        </p>
        <figure class="figure">
          <img src="guide/memory-viewer.png" alt="Memory Viewer after ReadMemory: disassembly and hex for one kernel page.">
          <figcaption>Figure 13. <strong>ReadMemory</strong> &mdash; one page, disassembly and hex.</figcaption>
        </figure>
        <p>
          After the read, the console counts what the page decoded. That is
          the start of looking closer, not a verdict.
        </p>
        <figure class="figure">
          <img src="guide/memory-stats.png" alt="Console instruction stats after ReadMemory on the same page.">
          <figcaption>Figure 14. The same page, counted in the console.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="support">
        <strong>6. <code>!support</code></strong>
        <p>
          When something breaks, run <code>!support</code>.
          It prints a system report. Email that to us.
        </p>
        <figure class="figure">
          <img src="guide/support.png" alt="!support in Hawkeye Community: a system report, website, and email.">
          <figcaption>Figure 15. <code>!support</code> &mdash; the report to send.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>

        <p>In a short window, records active pages in the target process virtual address space &mdash; RWX or RX. User-mode or kernel. <code>!active_pages_sim</code> stages both.</p>

      <article class="card">
        <h3><a href="#hidden-windows"><code>!hidden_windows</code></a></h3>
        <p>Detects windows hidden on the DisplayAffinity path &mdash; <code>SetWindowDisplayAffinity</code> or <code>win32kfull!ChangeWindowTreeProtection</code>. <code>!hidden_windows_sim</code> hides Hawkeye's own main window.</p>

        <p>Detects Visuals hidden from capture &mdash; in-process or cross-process, and bindable to another process's window. <code>!hidden_visuals_sim</code> stages a local Visual.</p>
      </article>
      <article class="card">
        <h3><a href="#ukexec"><code>!ukexec</code></a></h3>
        <p>Detects executable pages in the kernel region of a process address space that remain user-accessible &mdash; a newer injection technique. <code>!ukexec_sim</code> stages a case.</p>
      </article>
      <article class="card">
        <h3><a href="#hidden-process"><code>!hidden_process</code></a></h3>

        <strong>1. Clues &mdash; the plugin</strong>
        <p>
          <code>!analyze</code> does not guess the target. It needs clues:
          which process, and which addresses in that process you treat as
          high-risk.
        </p>
        <p>
          Lab ships <code>HawkHotTargets.dll</code> (under
          <code>plugins\</code>). The built-in plugin stages a detection
          target: it opens Notepad titled
          <strong>Hawkeye Lab target -- do not close</strong>,
          then hands Hawkeye that PID and two fixed addresses &mdash;
          the PE header of <code>notepad.exe</code>, and the PE header of
          <code>ntdll.dll</code> in that process.

          <a href="https://github.com/hawkeye-Leo/hawkeye-community/tree/main/samples/HawkHotTargets"><code>samples\HawkHotTargets</code></a>

          A game security engineer, for example, writes the code that
          tells Hawkeye the game process PID and the sensitive addresses
          in that process's memory. Hawkeye takes those clues and runs
          automated detection for suspicious behavior.
        </p>

          The demo uses Notepad as the target. Lab stages high-risk behavior

          that run &mdash; a close simulation of a live system.

      <article class="guide-step" id="cross-rw">
        <strong>6. <code>!cross_rw</code> &mdash; who else is reading this process</strong>
        <p>
          <code>!cross_rw</code> watches a target PID for cross-process access
          &mdash; <code>ReadProcessMemory</code> and the like. The window is
          short. The scan is threads currently on the CPU, across the system;
          then it reports who was in that process.
        </p>
        <p>
          That is a bench question, not a verdict. It shows up around a game
          process, a build you are testing, or any software you run: is
          something else reading it.
        </p>
        <p>
          <code>!cross_rw_sim</code> stages that access on a background thread
          so you can see the detector fire. Run either command with no
          arguments for usage. Pair them on the same PID;
          <code>!cross_rw_sim -stop</code> ends the sim.
        </p>
        <figure class="figure">
          <img src="../guide/lab-cross-rw-usage.png" alt="Hawkeye Lab: !cross_rw and !cross_rw_sim usage in the console.">
          <figcaption>Figure 6. Usage &mdash; pair the detector with the sim on the same PID.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>

      <article class="guide-step" id="phys-read">
        <strong>7. <code>!phys_read</code> &mdash; physical-memory reads</strong>
        <p>
          Cross-process access is not one technique.
          <code>!cross_rw</code> covers attach-based reads such as
          <code>ReadProcessMemory</code>.
          <code>!phys_read</code> covers another:
          <code>MmCopyMemory</code> with <code>MM_COPY_MEMORY_PHYSICAL</code>
          &mdash; a physical-memory read of a process address.
        </p>
        <p>
          <code>-pid</code> is the process being read.
          <code>-va</code> is the virtual address inside it.
          Both sides of the pair take the same two flags.
        </p>
        <p>
          <code>!phys_read_sim</code> stages the same
          <code>MmCopyMemory</code> (<code>MM_COPY_MEMORY_PHYSICAL</code>)
          read so you can see the detector fire. Run either command with
          no arguments for usage. Pair them on the same PID and VA.
        </p>
        <figure class="figure">
          <img src="../guide/lab-phys-read-usage.png" alt="Hawkeye Lab: !phys_read and !phys_read_sim usage in the console.">
          <figcaption>Figure 7. Usage &mdash; same <code>-pid</code> and <code>-va</code> on both commands.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="map-io">
        <strong>8. <code>!map_io</code> &mdash; MmMapIoSpace mapping</strong>
        <p>
          Physical-memory access is not one technique either.
          <code>!phys_read</code> covers <code>MmCopyMemory</code>
          (<code>MM_COPY_MEMORY_PHYSICAL</code>).
          <code>!map_io</code> covers another:
          a kernel map of a process address through
          <code>MmMapIoSpace</code>.
        </p>
        <p>
          Two cache modes. <code>-cache:0</code> is
          <code>MmNonCached</code>. <code>-cache:1</code> is
          <code>MmCached</code>.
          <code>-pid</code> is the process being mapped.
          <code>-va</code> is the virtual address inside it.
          Both sides of the pair take the same three flags.
        </p>
        <p>
          Detection is probabilistic; default is a short scan,
          <code>-strong</code> widens it. Run more than once to confirm.
          <code>!map_io_sim</code> stages each mode: map, then unmap,
          no read. Run either command with no arguments for usage.
          Pair them on the same PID, VA, and cache.
        </p>
        <figure class="figure">
          <img src="../guide/lab-map-io-usage.png" alt="Hawkeye Lab: !map_io and !map_io_sim usage in the console.">
          <figcaption>Figure 8. Usage &mdash; same <code>-pid</code>, <code>-va</code>, and <code>-cache</code> on both commands.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="active-pages">
        <strong>9. <code>!active_pages</code> &mdash; active pages in the target process virtual address space</strong>
        <p>
          Finding the code body of malware, or of software that should not
          be there, is slow if you walk the address space by hand.
          <code>!active_pages</code> samples a very short window and
          records the pages that were active in that process virtual
          address space.
        </p>
        <p>
          <code>-pid</code> is the target. <code>-pid:4</code> is the
          kernel. <code>-rx:0</code> is RWX pages.
          <code>-rx:1</code> is RX pages.
          <code>-pid:all</code> walks busy processes for RWX (not PID 4);
          capture costs more CPU. User-mode hits can be checked against
          VAD protection.
        </p>
        <p>
          <code>!active_pages_sim</code> stages an active page in
          user-mode (<code>-pid</code> above 4) or in the kernel
          (<code>-pid:4</code>). One sim at a time;
          <code>-stop</code> when you are done. Pair the detector on the
          same PID with <code>-rx:</code>. Run either command with no
          arguments for usage.
        </p>
        <p>
          <code>-lab_miflag36</code> is experimental: Windows 11
          <code>MiFlags</code> research. It is not part of the detector.
        </p>
        <figure class="figure">
          <img src="../guide/lab-active-pages-usage.png" alt="Hawkeye Lab: !active_pages and !active_pages_sim usage in the console.">
          <figcaption>Figure 9. Usage &mdash; user-mode or kernel; pair the detector on the same PID with <code>-rx:</code>.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="hidden-windows">
        <strong>10. <code>!hidden_windows</code> &mdash; DisplayAffinity hidden windows</strong>
        <p>
          Some windows are kept out of capture along the DisplayAffinity
          path: <code>SetWindowDisplayAffinity</code>, or
          <code>win32kfull!ChangeWindowTreeProtection</code>.
          <code>!hidden_windows</code> detects that behavior.
        </p>
        <p>
          Detection needs <code>-init</code> first, once.
          After that, <code>!hidden_windows</code> with no flags runs the
          scan. Run with no arguments before <code>-init</code> for usage.
        </p>
        <p>
          <code>!hidden_windows_sim</code> hides Hawkeye's own main window
          so you can see the same class of behavior.
          <code>-enable:1</code> hides it from capture;
          <code>-enable:0</code> shows it again.
        </p>
        <figure class="figure">
          <img src="../guide/lab-hidden-windows-usage.png" alt="Hawkeye Lab: !hidden_windows and !hidden_windows_sim usage in the console.">
          <figcaption>Figure 10. Usage &mdash; <code>-init</code> then detect; the sim hides Hawkeye's main window.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="hidden-visuals">
        <strong>11. <code>!hidden_visuals</code> &mdash; Visuals hidden from capture</strong>
        <p>
          Hiding a window (DisplayAffinity) is one technique.
          Hiding a Visual is another: fuse a Visual in-process or
          across processes, keep it out of capture, and bind it to any
          process window.
        </p>
        <p>
          <code>!hidden_visuals</code> detects Visuals that are hidden
          from capture. It needs <code>dwmcore.dll</code> symbols; if they
          are missing, the console gives the <code>!sym</code> line.
        </p>
        <p>
          <code>!hidden_visuals_sim</code> creates a Visual locally
          (a red overlay) and hides it from capture.
          <code>-enable:1</code> stages it;
          <code>-enable:0</code> restores.
        </p>
        <figure class="figure">
          <img src="../guide/lab-hidden-visuals-usage.png" alt="Hawkeye Lab: !hidden_visuals and !hidden_visuals_sim in the console.">
          <figcaption>Figure 11. Usage &mdash; load <code>dwmcore</code> symbols if asked; sim <code>-enable:1</code> / <code>-enable:0</code>.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="ukexec">
        <strong>12. <code>!ukexec</code> &mdash; user-accessible pages in the kernel region</strong>
        <p>
          Classic injection sits in user-mode mappings. A newer technique
          places executable code in the kernel region of the target
          process's address space, still reachable from user mode.
          Ordinary user-mode injection checks do not cover that region.
          <code>!ukexec</code> scans for those pages.
        </p>
        <p>
          <code>-pid</code> scans one process.
          <code>-busy</code> scans busy processes (higher CPU at capture).
          Use one of these, not both.
        </p>
        <p>
          <code>!ukexec_sim</code> plants one user-accessible page in that
          kernel region for a user-mode PID (not PID 4). One sim at a
          time; <code>-stop</code> when you are done, or when the process
          exits. Run either command with no arguments for usage.
        </p>
        <figure class="figure">
          <img src="../guide/lab-ukexec-usage.png" alt="Hawkeye Lab: !ukexec and !ukexec_sim usage in the console.">
          <figcaption>Figure 12. Usage &mdash; <code>-busy</code> or <code>-pid</code>; sim takes a user-mode PID.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="hidden-process">
        <strong>13. <code>!hidden_process</code> &mdash; hidden processes and threads</strong>
        <p>
          Malware that injects into a legitimate process often starts a
          thread there, then hides that process or thread so the usual
          lists do not show it.
          <code>!hidden_process</code> looks for that: what is running,
          compared with what the system reports.
        </p>
        <p>
          The scan is system-wide. <code>-run</code> starts it.
          Run with no arguments for usage. There is no simulator for
          this command.
        </p>
        <figure class="figure">
          <img src="../guide/lab-hidden-process-usage.png" alt="Hawkeye Lab: !hidden_process usage in the console.">
          <figcaption>Figure 13. Usage &mdash; <code>!hidden_process -run</code>.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="invlpg">
        <strong>14. INVLPG / special instructions</strong>
        <p>
          Much modern malware reaches another process's memory through
          PTE remap paired with <code>INVLPG</code>, not only through
          familiar cross-process APIs. That makes instruction recognition
          on the pages that actually ran more important, not less.
        </p>
        <p>
          Hawkeye decodes active memory and ETW RIP samples into an
          instruction report: counts for <code>invlpg</code>,
          virtualization opcodes, control-register moves, MSRs, and
          related classes, with a risk line when a pattern stands out.
          Pair it with <code>!active_pages</code> to find hot pages and
          with <a href="../#etw"><code>!etw</code></a> to see where the CPU
          ran in a short window.
          Together they narrow a large address space down to a few
          high-risk code pages quickly.
        </p>
        <p>
          Lab can stage a kernel page full of synthetic high-risk
          instructions. Run <code>!active_pages_sim -run -pid:4</code>,
          then detect with <code>!active_pages -pid:4 -rx:0</code>.
          Open the page in the Memory viewer &mdash; see
          <a href="../#memory">Community Memory</a> for
          <strong>ReadMemory</strong> and the console stats line.
          Lab also lets you edit bytes at a chosen VA in that viewer
          (hex edit after read) when you need to patch test data by hand.
        </p>
        <figure class="figure">
          <img src="../guide/lab-invlpg-report.png" alt="Hawkeye Lab: instruction decode report on a simulated high-risk kernel page with INVLPG flagged HIGH.">
          <figcaption>Figure 14. A staged kernel code page &mdash; instruction decode with <code>[risk] HIGH</code> on <code>invlpg</code>.</figcaption>
        </figure>
        <p class="guide-up"><a href="#guide-toc" aria-label="Back to contents">&uarr; Contents</a></p>
      </article>
      <article class="guide-step" id="analyze">
        <strong>15. <code>!analyze</code> &mdash; automated detection and report</strong>
        <p>
          <code>!analyze</code> runs automated detection and writes an analysis
          report from clues you supply. You must provide those clues first.
          Write a plugin per the contract, or set the target PID and sensitive
          addresses yourself.
        </p>
        <p>
          The built-in example uses Notepad and fixed addresses inside that
          process as the target and clues, then runs simulation and detection.
          That walkthrough shows what Hawkeye can do and where its limits are
          &mdash; not a live incident.
        </p>
        <p>
          In <code>-demo</code> mode, Hawkeye actively stages sensitive
          behavior, then detects it.
          In <code>-live</code> mode it does not simulate anything; it
          detects only on the clues you gave. That is the setup for real work.
          Each dimension in the PDF comes from the behavior-signature library
          &mdash; the check itself plus the Assessment that explains the finding.
        </p>
        <p>
          Default plugin: <code>plugins\HawkHotTargets.dll</code> (demo and live).
          Your own DLL: <code>!analyze -plugin:plugins\MyGame.dll -load</code>.
          Must export <code>HawkHotTargetsQuery</code>.
          See
          <a href="https://github.com/hawkeye-Leo/hawkeye-community/tree/main/samples/HawkHotTargets"><code>samples\HawkHotTargets</code></a>.
          Run <code>!analyze</code> with no arguments in the console for full usage.
        </p>
        <figure class="figure">
          <img src="../guide/lab-analyze-usage.png" alt="Hawkeye Lab: !analyze usage in the console.">
          <figcaption>Figure 15. Usage &mdash; run <code>!analyze</code> with no arguments.</figcaption>
        </figure>

    <h2>SetWindowDisplayAffinity: mechanism &amp; detection</h2>
    <p class="article-meta">
      <span>Hidden windows &amp; anti-capture series</span>
      <span>Tools: IDA · CE · Hawkeye Community · Cursor MCP</span>
    </p>

    <nav class="guide-nav" aria-label="On this page">
      <strong>Contents</strong>
      <ol>
        <li><a href="#background">Background &amp; series</a></li>
        <li><a href="#win32k">win32k chain</a></li>

        <li><a href="#opensource">Open-source implementation</a></li>
      </ol>

    <article class="guide-step" id="background">
      <strong>1. Background &amp; series</strong>
      <p>
        <code>SetWindowDisplayAffinity</code> (typically with <code>WDA_EXCLUDEFROMCAPTURE</code>)
        is a well-known way to keep a window visible on the desktop while excluding it from
        most screen-capture and recording APIs.
      </p>
      <p>This series has three parts. This article is part 1:</p>
      <ul class="article-list">
        <li><strong>Part 1 (this page)</strong>: <code>SetWindowDisplayAffinity</code> &mdash; mechanism &amp; detection</li>
        <li>Part 2: Visual-layer hiding &mdash; mechanism &amp; detection</li>
        <li>Part 3: BitBlt-style &ldquo;super screenshot&rdquo; approach</li>
      </ul>
    </article>

    <article class="guide-step" id="win32k">
      <strong>2. win32k chain</strong>
      <p>
        The user-mode API enters the kernel at
        <code>win32kfull!NtUserSetWindowDisplayAffinity</code>; core logic lives in
        <code>SetDisplayAffinity</code>. Simplified flow:
      </p>
      <pre class="flow-block">NtUserSetWindowDisplayAffinity
  └─ SetDisplayAffinity
       ├─ ComposeWindowIfNeeded
       ├─ InternalSetProp / InternalRemoveProp("SysDispAffinity")
       └─ ChangeWindowTreeProtection
            └─ ProtectWindowBitmap
                 ├─ ChangeWindowBitmapOwner
                 └─ GreProtectSpriteContent
                      └─ DwmAsyncUpdateSprite → dwm.exe</pre>
      <p>
        <code>DwmAsyncUpdateSprite</code> ultimately delivers an LPC message to the
        <code>dwm.exe</code> process. Aside from updating the <code>SysDispAffinity</code>
        property on the window (tagWND), other kernel-side changes are relatively few.
        Property atom indices also shift between Windows versions, so detecting hidden windows
        from kernel state alone tends to be less stable and less portable.
      </p>
      <p>
        Study of <code>dwmcore.dll</code> shows separate paths for capture and direct display,
        corresponding to <code>CCaptureRenderTarget</code> and <code>CDDisplayRenderTarget</code>
        respectively. With further observation, the split is clear: for anti-capture, the
        <code>dwm.exe</code> process owns the full logic; the kernel plays a limited role.
      </p>
    </article>

    <article class="guide-step" id="dwm">
      <strong>3. DWM leads</strong>
      <p>
        Whether a window is hidden from capture should, in principle, show up in DWM
        <code>CCaptureRenderTarget</code> composed output.
        <code>dwm.exe</code> loads many modules; our primary suspects are
        <code>dwm.exe</code>, <code>dwmcore.dll</code>, <code>dwmredir.dll</code>, and
        <code>uDWM.dll</code> (we search these first below) &mdash; the names all carry
        <code>dwm</code>.
      </p>
      <p>
        In Hawkeye Community, attach to <code>dwm.exe</code> with
        <code>!probe -pid:&lt;dwm_pid&gt;</code>, then search for <code>protect</code> across the
        four modules below:
        <code>!probe -find:protect -mod:dwmcore,dwmredir,udwm,dwm</code>
      </p>
      <figure class="figure">
        <img src="images/probe-protect-search.png" alt="Hawkeye !probe search for protect in DWM modules, listing IsProtected and HasProtectedContent symbols.">
        <figcaption>Figure 1. <code>!probe -find:protect</code> &mdash; many protection-related symbols; below we focus on <code>CWindowContext</code>.</figcaption>
      </figure>
      <p>Strongest candidates in <code>dwmredir</code> &mdash; two functions tied to window content:</p>
      <ul class="article-list">
        <li><code>CWindowContext::HasProtectedContent</code></li>
        <li><code>CWindowContext::NotifyProtectionChange</code></li>
      </ul>
      <p>
        The names are explicit: test whether window content is protected, and notify the
        composition pipeline when protection changes. DWM also exposes many
        <code>IsProtected</code> / <code>SetHardwareProtection</code> symbols worth
        following separately.
      </p>
    </article>

    <article class="guide-step" id="has-protected">
      <strong>4. What HasProtectedContent does</strong>
      <p>
        Disassembly of <code>dwmredir!CWindowContext::HasProtectedContent</code> is straightforward:
      </p>
      <figure class="figure">
        <img src="images/has-protected-content-asm.png" alt="HasProtectedContent loads dword at object offset 0x114, shifts right 6, ANDs with 1.">
        <figcaption>Figure 2. Load <code>[rcx+0x114]</code>, <code>SHR 6</code>, <code>AND 1</code> &mdash; i.e. test <strong>bit 6 (0x40)</strong> of that DWORD.</figcaption>
      </figure>
      <p>
        So <code>CWindowContext</code> carries a flag DWORD at offset <code>+0x114</code>;
        bit 6 marks protected content (consistent with anti-capture semantics).
      </p>
      <p>
        When locating <code>CWindowContext</code> instances, note the class has
        <strong>two vftables</strong>. Use the one for <code>IDwmWindow</code>
        (example from our test machine below):
      </p>
      <figure class="figure">
        <img src="images/probe-vftable-find.png" alt="!probe finds two CWindowContext vftables; IDwmWindow at 0x7FFAF582A000.">
        <figcaption>Figure 3. <code>!probe -find:CWindowContext,vftable -mod:dwmredir</code> &mdash; locate the <code>IDwmWindow</code> vftable.</figcaption>
      </figure>
      <figure class="figure">
        <img src="images/vftable-idwmwindow.png" alt="Memory Viewer at CWindowContext IDwmWindow vftable address in dwmredir.dll.">
        <figcaption>Figure 4. Vftable lives in <code>dwmredir.dll</code> &mdash; use it to scan DWM heap objects.</figcaption>
      </figure>
    </article>

    <article class="guide-step" id="memory">
      <strong>5. Memory validation</strong>
      <p>
        Experiment: call <code>SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)</code> on a window,
        then search for that HWND value in <code>dwm.exe</code> with Cheat Engine to land on the
        matching <code>CWindowContext</code> object.
      </p>
      <figure class="figure">
        <img src="images/cwindowcontext-memory.png" alt="CWindowContext memory: vftable at +0, 0x40 protection bit at +0x114, HWND and PID fields.">
        <figcaption>Figure 5. Layout check: first 8 bytes = vftable; at <code>+0x114</code>, value <code>0xC7</code> has bit 6 (<code>0x40</code>) set; cross-check HWND and owning PID.</figcaption>
      </figure>
      <table class="article-table">
        <thead>
          <tr>
            <th>Field</th>
            <th>Example</th>
            <th>Notes</th>
          </tr>
        </thead>
        <tbody>
          <tr>
            <td>vftable</td>
            <td><code>0x00007FFAF582A000</code></td>
            <td><code>CWindowContext</code> (<code>IDwmWindow</code>) vtable pointer</td>
          </tr>
          <tr>
            <td>Protection flag</td>
            <td><code>+0x114</code>, bit 6 = 1</td>
            <td>Matches <code>HasProtectedContent</code> disassembly</td>
          </tr>
          <tr>
            <td>Window kind</td>
            <td><code>0x1</code> / <code>0x2</code> / <code>0x4</code></td>
            <td>DWM internal type enum (rough guess): <code>0x1</code> console-class, <code>0x2</code> GUI window (frameless / custom title bar), <code>0x4</code> GUI window</td>
          </tr>
          <tr>
            <td>HWND / PID</td>
            <td colspan="2">Window handle and owning process ID</td>
          </tr>
        </tbody>
      </table>
      <p>
        First 8 bytes of the object are the vftable pointer. Exact offsets move between
        Windows builds, but the combination <strong>vftable + protection bit + HWND/PID</strong>
        has been stable enough across versions we tested to build detection around.
      </p>
    </article>

    <article class="guide-step" id="detection">
      <strong>6. Detection</strong>
      <p>
        Window composition for capture exclusion lives mainly in the DWM process and is
        largely decoupled from the kernel path, so scanning <code>dwm.exe</code> is a practical
        detection surface.
      </p>
      <p>
        A workable scheme mirrors the manual CE steps above, but automates layout discovery:
      </p>
      <ul class="article-list">
        <li>Resolve the <code>IDwmWindow</code> vtable address from <code>dwmredir.dll</code> symbols (PDB).</li>
        <li>Scan <code>dwm.exe</code> read-write regions for pointers equal to that vtable.</li>
        <li>
          During <strong>calibration</strong>, enable anti-capture on a known window &mdash; Hawkeye
          uses its own main window via <code>SetWindowDisplayAffinity</code> &mdash; then select the
          matching object by vtable, protection bit 6, window kind, HWND, and owning PID.
        </li>
        <li>Record object-relative offsets for flags, kind, HWND, and PID; reuse them on later scans.</li>
      </ul>
      <p>
        Absolute field offsets (such as <code>+0x114</code> for the flag DWORD on our test build)
        change between Windows versions. Anchoring on the vtable and calibrating once keeps the
        scanner portable. In the Community tool, window kind is filtered to <code>0x2</code> and
        <code>0x4</code> during scans even though <code>0x1</code> may appear in memory dumps.
      </p>
    </article>

    <article class="guide-step" id="opensource">
      <strong>7. Open-source implementation</strong>
      <p>
        The detection approach in this article is implemented in <strong>Hawkeye Community</strong>:
        <code>!hidden_windows</code> (run <code>-init</code> first) and the staging command
        <code>!hidden_windows_sim</code>. The Community build anchors on the
        <code>CWindowContext</code> / <code>IDwmWindow</code> vtable in <code>dwmredir.dll</code>,
        calibrates relative offsets for flags, kind, HWND, and PID, then scans <code>dwm.exe</code>
        memory.
      </p>
      <p>
        Source:
        <a href="https://github.com/hawkeye-Leo/hawkeye-community">github.com/hawkeye-Leo/hawkeye-community</a><br>
        Binaries:
        <a href="https://github.com/hawkeye-Leo/hawkeye-community/releases/latest">GitHub Releases (latest)</a>
      </p>
      <p>
        <strong>Next in the series:</strong> Visual-layer hiding &mdash; a more flexible and covert
        anti-capture approach.
      </p>

    </article>
