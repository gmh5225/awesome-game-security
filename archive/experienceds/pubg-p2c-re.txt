## The three TslGame processes (verified)

BattlEye + PUBG use a chain of three processes to launch the game:

| Process | Purpose | Bitness | Modules loaded |
|---|---|---|---|
| `TslGame_ZK.exe` | Zurikawaka launcher stub | x64 | ~11 (minimal, includes 2 `_notlinked-ntdll.dll` copies) |
| `TslGame_BE.exe` | BattlEye 32-bit wrapper | x86 (WoW64) | ~68 |
| `TslGame.exe` | Real game process | x64 | ~155 |

The two `_notlinked-ntdll.dll` entries in `TslGame_ZK.exe` are a **BattlEye anti-tamper technique** — BE loads multiple ntdll copies at different addresses to detect user-mode API hooks by comparing them.

## Stub PE dissection

Both dropped stubs (`li5k2hokg.exe`, `uzx0odykv8p2.exe`, `suk4itsj.exe`, ...) are byte-identical up to filename:

```
File offset 0x00: 4D 5A 78 00 01 00 00 00 04 00 00 00 00 00 00 00
                  |  MZ signature
                  └─ DOS header (minimal)

File offset 0x40: 0E 1F BA 0E 00 B4 09 CD 21 B8 01 4C CD 21 54 68
                  └─ "!This program cannot be run in DOS mode.$"

File offset 0x78: 50 45 00 00 64 86 01 00 F4 82 23 00 00 00 00 00
                  │  PE header
                  └─ Machine=x64, 1 section

File offset 0x80: 00 00 00 00 F0 00 22 00 0B 02 0E 00 00 02 00 00
                  └─ Optional header: PE32+, 512 bytes code

File offset 0x180: 2E 74 65 78 74 00 00 00 03 00 00 00 00 10 00 00
                   └─ Section header: ".text", VirtualSize=3, VirtualAddress=0x1000

File offset 0x200: <first byte of .text>
File offset 0x203: <last byte of .text — only 3 bytes real code>
File offset 0x204 onward: CC CC CC ... CC (padding to 1024)
```

The 3 bytes of `.text`:
```
54 24 48    →   push rsp; and eax, 0x48
             OR
             push rsp; rex.WB (invalid alone) — never actually executes as this
```

Regardless of interpretation, entry-point RVA is `0x1000` which is the start of `.text`. Windows loader loads this, applies imports, hands control. The 3 bytes execute (or crash), the stub main thread exits, but **all imported DLLs remain resident** because Windows loader loaded them for the process.

Result: the stub process is basically an `LoadLibrary` proxy for its import list. That import list — d3d11.dll, dxgi.dll, dwmapi.dll, apphelp.dll, MSVCP140.dll, VCRUNTIME140.dll, VCRUNTIME140_1.dll, WINMM.dll, KERNELBASE.dll, ntdll.dll, USER32.dll, gdi32full.dll, msvcp_win.dll, ucrtbase.dll, RPCRT4.dll, IMM32.DLL, combase.dll — is exactly the set the cheat renderer needs at runtime.

Purpose: unclear but architecturally the stubs are session-persistence tokens. If the cheat requires "at least one stub alive" to remain active, killing all stubs would deactivate it. This was not tested destructively during the analysis.

## Threading model

Loader process (during active phase):
- Main thread — WebView2 host / UI
- ~5 WebView2 child threads
- libcurl worker threads (2-3, dependent on connection state)
- Total ~15 threads

Stub processes: 2-3 threads each (main + implicit runtime workers from CRT init)

DWM process (post-injection):
- Baseline DWM threads (~30-40)
- No additional threads spawned by the cheat — it runs inside DWM's existing render thread by way of the hook

`INJECTION.md`:

```md
# DWM Injection Mechanism

Full step-by-step of how the loader gets its cheat renderer into `dwm.exe`.

## Why DWM?

`dwm.exe` (Desktop Window Manager) is the Windows compositor — every visible pixel of every application window passes through DWM before reaching the screen. A DWM-resident overlay can therefore draw over any target window, including a full-screen game, without ever touching that game's process.

For a BattlEye-protected game like PUBG, this is architecturally significant:

- BattlEye scans the game process (`TslGame.exe`) for injected modules, thread-hijacks, memory tampering. **It does not scan `dwm.exe`.**
- BattlEye scans the game's HWND for known overlay windows. **A DWM-side render bypasses this — the overlay is composited into the game's own presented backbuffer.**
- The game process is never opened, never written to, never read.

The trade-off: DWM injection needs `SeDebugPrivilege` and the ability to `OpenProcess(PROCESS_ALL_ACCESS)` on the compositor. Both are available to any local Administrator on default Windows 10/11 installations because DWM does not have `PROCESS_MITIGATION_DYNAMIC_CODE_POLICY` (ACG) or `PROCESS_MITIGATION_BINARY_SIGNATURE_POLICY` enabled.

## Confirmed via `Get-ProcessMitigation -Id <dwm_pid>`

```
Dep             : Enabled
Aslr            : Enabled
DynamicCode     : OFF     ← ACG is NOT enforced
BinarySignature : OFF     ← DLL signing not required
ChildProcess    : Enabled
Cfg             : Enabled ← CFG active but only limits indirect-call targets
```

## Injection steps (as executed by the loader)

1. **Elevate**
   ```c
   OpenProcessToken(GetCurrentProcess(), TOKEN_ADJUST_PRIVILEGES, &token);
   LookupPrivilegeValueA(NULL, "SeDebugPrivilege", &luid);
   TOKEN_PRIVILEGES tp = { 1, {luid, SE_PRIVILEGE_ENABLED} };
   AdjustTokenPrivileges(token, FALSE, &tp, 0, NULL, NULL);
   ```

2. **Find dwm.exe PID**
   Snapshot via `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS)` or `NtQuerySystemInformation(SystemProcessInformation)`. Match on `dwm.exe`.

3. **Open the compositor**
   ```c
   HANDLE h = OpenProcess(PROCESS_ALL_ACCESS, FALSE, dwm_pid);
   // On default Win10/11: succeeds with SeDebugPrivilege.
   ```

4. **Allocate RWX in DWM address space**
   Two allocations observed (both 4 KB, protection `p-rwx-`):
   - `0x00750000` — ESP renderer #1
   - `0x09360000` — ESP renderer #2

5. **Write ESP renderer bytes**
   Both regions contain identical-shape x64 code — vector math on XMM0-XMM15, `movaps`/`mulps`/`addps`, matrix constants (float `1/256 = 0x3B808081`, `1.0f = 0x3F800000`, `NaN sentinel = 0x7FFFFFFF`) followed by Direct2D drawing primitives. This is WorldToScreen + DrawRectangle/DrawLine.

6. **Install hook-target dispatch table** at `0x06410000` (4 KB, private RW) — array of function pointers, populated with pointers into the ESP renderer.

7. **Wire it into DWM's render loop** — the exact hook site was not conclusively identified in this analysis. Zakynthos' diagnostic buffer inside `TslGame.exe` names three hook types that it observes:
   - `Dwmcore CRenderTarget Vtable Hook`
   - `D2d1 D2DDeviceContextBase Vtable Hook`
   - `Dwmcore RenderBlackContent Code Hook`
   
   The dwmcore `.rdata + 0x287058` vtable slots were checked and match a clean baseline — they point to stock ntdll CFG validators, not to injected code. The actual hook mechanism therefore uses one of the other observed vectors (D2D vtable swap in a heap-allocated interface, or an inline code patch elsewhere in dwmcore).

8. **Loader self-terminates** ~5 seconds after `onDownloadComplete` fires. Persistence is carried by the resident decoy stubs (see `README.md §7`).

## What the ESP renderer does at runtime

Once the two 4 KB RWX pages are executing inside DWM's render thread, they:

1. Read player position / view matrix / entity list from a **caller-provided buffer** in DWM heap.
2. Multiply world-space vectors by the view+projection matrix (the `movaps/mulps/addps` sequence).
3. Convert to screen-space coordinates using DWM's known render target dimensions.
4. Emit Direct2D `FillRectangle` / `DrawLine` / `DrawTextLayout` calls against the D2D device context that DWM already has open for composition of the game window.

The result: a bounding box and health bar drawn per player, composited over the game's frame, with zero pixels ever going through `TslGame.exe`.

## What was NOT observed

- No kernel driver load at runtime (loader has `kdmapper` + `iqvw64e.sys` strings but no modules appear in the live kernel module table).
- No modification of `TslGame.exe` at any point.
- No modification of `BEDaisy.sys` or `navagio.sys` (both present, both stock).
- No hooks in game DLLs (`BEClient_x64.dll`, `steam_api64.dll`, `discord_game_sdk.dll`, `nvwgf2umx.dll`).
- No injection into `explorer.exe`, `svchost.exe`, or any other system process.

## Anti-tamper on the payload DLL

The extracted payload PE has VMProtect's built-in self-CRC. Any modification of the on-disk PE — even purely editing section-header fields to make a memory-format PE loadable via `LoadLibraryA` — triggers a modal dialog:

> `File corrupted! This program has been manipulated and maybe it's infected by a Virus or cracked. This file won't work anymore.`

To load the payload without triggering this, the exact bytes from the on-wire download buffer must be preserved. This is a known VMProtect protection (`VMProtectIsValidImageCRC`).

Independently, the payload's `DllMain` (RVA `0x843F40`, virtualized by VMP) contains a context check. When the DLL is manually mapped into DWM by any code path other than the vendor's loader — verified by allocating a full 10 MB RWX region in DWM, writing the exact payload bytes, applying base relocations, resolving imports via `LoadLibraryA`/`GetProcAddress`, and invoking `DllMain(base, DLL_PROCESS_ATTACH, NULL)` through a remote-thread thunk — `DllMain` returns `FALSE` and the cheat does not activate. The check is inside the VMP p-code and its specific mechanism (caller identity, PEB module walk, memory marker, or stack unwinding) is not established.

# Payload DLL Analysis

The cheat itself — a VMProtect-packed x64 DLL delivered by the loader.

## Provenance

Captured from the loader's memory in the ~5-second window between `onDownloadComplete()` and `ExitProcess`. The buffer address (in one capture) was `0x05640000` — a 6 MB private R/W VAD in the loader's process, populated to 98% non-zero, entropy ≈ 8.00 (indistinguishable from pure random — consistent with a VMProtect-packed image whose interior is encrypted).

The first 0x60 bytes of the buffer are a wrapper header — not part of the PE. Starting at offset `0x60`:

```
0x60: 4D 5A 90 00 03 00 00 00 04 00 00 00 FF FF 00 00
      │  MZ signature
      └── standard MS-DOS header

The 0x60-byte prefix content:
```

**Notably absent** — `wininet.dll`, `winhttp.dll`, `ws2_32.dll`, `bcrypt.dll`, `advapi32.dll`, `ntdll.dll` (explicit). The payload has:
- No network code — cannot phone home, cannot fetch keys
- No cryptography — cannot verify licenses
- No token / process manipulation — cannot spawn processes or elevate

Every non-graphics decision the payload makes must come from bytes present at load time — either in the DLL image itself (VMP-encrypted config) or in the process address space where it's loaded (marker planted by loader).

Two API strings survive in plaintext across the entire 10.6 MB image:
- `GetModuleHandleA` at file offset `0x47BB06` (inside `.0Z0`)
- `LoadLibraryA` at file offset `0x8EEDF0` (visible IAT thunk region)

These are the bootstrap primitives VMP needs to resolve everything else dynamically. Everything else — including `"dwmcore"` as a string (neither `64 77 6D 63 6F 72 65` in ASCII nor UTF-16LE) — is hashed or constructed at runtime.

## VMProtect specifics

- **CRC self-check** — modifying any byte of the on-disk PE (including section-header fields for `SizeOfRawData` / `PointerToRawData`) triggers a modal dialog window with the classic VMP anti-crack message.
- **Anti-debug** — TLS-callback-free means no TLS-based anti-debug, but the standard VMP checks (`IsDebuggerPresent`, `NtQueryInformationProcess(ProcessDebugPort/ProcessDebugFlags)`, timing checks via `RDTSC`, hardware breakpoint checks via `NtGetContextThread`) are all present in the VM handlers.
- **Import obfuscation** — every imported function call goes through a VMP dispatcher that re-resolves the target via `LoadLibraryA` + `GetProcAddress` per-call, using hashed function names.
- **Context-check in DllMain** — verified experimentally. Loading the DLL by any path other than the vendor loader results in `DllMain` returning `FALSE`. The specific check mechanism is inside VMP p-code and is one of: caller identity via stack unwinding, `PEB.Ldr` walk for a specific module fingerprint, parent-process check, or a memory marker placed by the loader before the load. Static analysis cannot distinguish between these without VMP devirtualization.

## Behavior observed in a valid session

When loaded correctly (by the vendor's loader), the payload:

1. `DllMain(hInst, DLL_PROCESS_ATTACH, NULL)` runs, VMP unpacks in place
2. Payload allocates the 2 × 4 KB RWX renderer pages in DWM at fixed VAs `0x750000` and `0x9360000`
3. Populates a hook-target dispatch table at `0x6410000`
4. Wires itself into DWM's Direct2D / DirectComposition render path via one of {D2D vtable swap, dwmcore code hook, dwmcore vtable hook}
5. Returns `TRUE`
6. Its renderer runs every time DWM composites a frame that contains the game window — reads player data from a shared buffer, computes screen coordinates, emits Direct2D calls to draw ESP over the game
7. Menu toggle: `GetAsyncKeyState(VK_...)` polled — visible via the recovered import

## 7. Decoy stubs

Every loader invocation drops **new** 1 KB PE files to the source directory (typically the USB drive).

Observed samples in this analysis: `li5k2hokg.exe` · `uzx0odykv8p2.exe` · `suk4itsj.exe` · `,c'vrl].exe` · `xd'bngxf.exe` · `qa'oao.fn.exe` · `xsbj'o!.exe` · `v,qdrlsy.exe` · `rooht!lk.exe`

Naming pattern is unrestricted printable — includes commas, apostrophes, exclamation marks. Windows accepts these as filenames.

**Stub PE anatomy (verified)**

| | |
|---|---|
| File size | `1024` bytes (exactly) |
| Machine | `0x8664` (x64) |
| Sections | 1 (`.text`) |
| `SizeOfImage` | `0x2000` (8 KB in memory) |
| `.text` VSize | `0x3` — literally three bytes of executable code |
| Rest of file | `0xCC` padding (int3) |
| Attributes on disk | `Hidden + System` |
| Runtime persistence | stays resident as long as parent session lives |
| Loaded DLLs at runtime | 62 modules including `d3d11.dll`, `dxgi.dll`, `dwmapi.dll`, `apphelp.dll`, `MSVCP140`, `VCRUNTIME140_1`, `WINMM`, full CRT |

The 3 bytes of code do nothing meaningful. The stub exists solely so Windows PE loader **automatically loads its declared imports** — bringing d3d11/dxgi/dwmapi into a resident process for later use.

The stubs are **decoys / persistence tokens**. They hold no cheat code (every writable VAD checked — no non-standard executable payload). Their function is not confirmed but architecturally they act as session markers that must remain alive.

## 9. Anti-cheat detection matrix

![Zakynthos Detection](diagrams/zakynthos_detection.svg)

PUBG PC uses **two** anti-cheat systems: BattlEye (third-party) and Zakynthos (Krafton's own, kernel driver `navagio.sys`). It does **not** use NEAC (NetEase Anti-Cheat) — that's a separate system for NetEase-published games (Peace Elite, Rules of Survival, etc.).

| AC | Detects the cheat? | Evidence |
|---|---|---|
| **BattlEye** (`BEDaisy.sys` + `BEClient_x64.dll`) | **No** | BE does not scan `dwm.exe`. Cheat lives entirely in DWM. Hours of gameplay without ban. |
| **Zakynthos** (`navagio.sys` + user-mode scanner in TslGame) | **Yes, logged** — but did not ban | Zakynthos maintains a ~16 MB RWX diagnostic buffer inside `TslGame.exe`. It scans DWM by reading its dirbase (CR3) and checks vtable/code integrity against known hook patterns. Found verbatim detection strings: `D2d1 D2DDeviceContextBase Vtable Hook` · `Dwmcore CRenderTarget Vtable Hook` · `Dwmcore CRenderTarget Fake Vtable` · `Dwmcore RenderBlackContent Code Hook` + 10 more templates. Scans for `NeacInterface.dll`/`libzdtp64.dll` as **scan targets** (known AC DLLs to inventory), not as own identity. Provenance confirmed by `Navagio::Search::PatternBlocks` string in `navagio.sys`. |

**Kernel-driver load** — `kdmapper` and `iqvw64e.sys` strings ARE present in the loader's `.rdata` (references to `iqvw64e.pdb`, `windriverpci_i.c`, `NalWindowsDriver...`, `MpFreeDriverInfoEx`, `[!] Failed to remove from RuntimeDriversArray`, `[-] Registry path to disable vulnerable driver list: HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\CI\Config`, `[-] Your vulnerable driver list is enabled and have blocked the driver loading, you must disable vulnerable driver list to use kdmapper with intel driver`). **However**, no manually-mapped kernel driver appears in the kernel module table at runtime — either the code path is dead / fallback, or the driver is loaded transiently and unloaded. Function unconfirmed.
