## 方法论

- **静态**：`otool` 解析段节/导入符号；自写 ObjC 元数据解析器（`__objc_classlist` / 相对方法表 / chained fixups）；自写 numpy 交叉引用索引（ADRP+ADD/LDR 物化、BL/B 目标、寄存器生命周期感知扫描）；Capstone 5.0.7 反汇编；还原解密算法后离线批量解密整个字符串池。
- **动态**：Frida 只读 hook（`spawn → resume → 等 2~4 s → attach`，解析全部放 `setTimeout` 避免重入死锁），观测调用链 backtrace、探针命中、解密调用、规则引擎 VM 原语计数。
- **交叉验证**：IDA Pro 9.3 + idalib，对 508 MB 主二进制采用「雕刻子二进制」法（按目标函数取窗口包成最小 ELF64，`run_auto_analysis=False` 逐函数 Hex-Rays），独立复核手工逆向结论。

## 核心发现 TL;DR

1. **三款 App 共用一套安全组件**：运行期符号名表 15/15 逐字节同一（番茄↔红果偏移恒定 `0x41DF00`），规则引擎 VM 原语逐字节同构，差别只在规则配置规模（番茄/红果 15 条、抖音 66 条）。

2. **真实检测面比"代码里写了多少检测"窄得多**：`fopen` 五探针是死代码（静态零引用 + 内存零登记 + 运行时零调用）；`statfs` 93 路径在 roothide 上全 miss；`canOpenCydia` 因未声明 scheme 恒假；文件遍历链需支付页才跑而本机无此入口。本地唯一给出非零结论的只有 `/hmd_tmp_file` 越界写（→ `is_env_abnormal=1`）与一次目录名巧合命中。

3. **检测挂在 HMD（Heimdallr）上报链上**，每次构造上报 header 时触发（三条并列路径），结果用 `dispatch_once` 缓存；越狱标志进入 HMD 的**明文字典**（34 字段，含 `is_env_abnormal`）。

4. **SafeGuard 规则引擎在本构建中不可达**：六路引用全 0、不在静态构造表、运行期零调用，但模块初始化确实发生过（沙盒目录存在）。规则数据里含 roothide 特征串，却没有任何可达路径会解密它们。

5. **加密名单其实覆盖三代越狱**（Dopamine/roothide/Xina），但以 bundle-id 与 plist 名出现，不是路径与库名——这正是此前只做路径扫描看不到的原因。

# 拆解字节系 App 的越狱检测——一次 roothide 环境下的静态 + 动态联合逆向

> 本文是一次**合法安全研究**的记录。目标是把字节系 App 的越狱/注入检测与风控机制的"真实形态"搞清楚：它从哪些维度检测、检测逻辑如何实现、检测结果如何联动到上层。全程 Frida **只读**（只 `onEnter/onLeave` 读参数、读返回、backtrace、dump 内存，不修改任何返回值或字段），不包含任何绕过武器化内容。文中所有技术论断都以目标二进制中实际读出的指令、字符串、表结构与设备上的现场读数为依据；无法取得直接证据的判断，一律在文末如实标注为"不可验证"。
>
> 文中不提供任何 IPA、脱壳后的 Mach-O 或可直接运行的绕过代码。

---

## 0. 写在前面：为什么要联合逆向

纯静态分析能看到"代码里写了什么检测"，但看不到"哪条真的在跑"；纯动态能看到"跑了什么"，但看不到被混淆、被延迟触发、或当前环境没走到的分支。字节系 App 恰好把两者的盲区都占满了：

- 单个主二进制 500 MB 级别、ObjC 类数以万计；
- 关键符号在**运行期**才用 `dlsym` 解析，只看导入表会系统性低估检测面；
- 字符串两套变体加密，方法 IMP 走三跳分支岛，子系统入口全部运行期分发。

所以本文采用静态（Capstone + 自写 ObjC/交叉引用索引 + 离线批量解密）与动态（Frida 只读观测）互为印证的方式，最后再用 IDA Pro 9.3 的 Hex-Rays 对关键函数做第三方交叉验证。

### 分析对象与环境

| 项 | 值 |
|---|---|
| 番茄小说 | 7.4.1（`com.dragon.read` / 主二进制 `Reading`） |
| 红果短剧 | 7.4.1（`com.phoenix.video` / 主二进制 `Eggplant`） |
| 抖音 | 40.8.0（`com.ss.iphone.ugc.Aweme` / 主二进制 `AwemeCore`） |
| 设备 | iPhone 11 Pro Max（`iPhone12,5`），iOS 26.0，roothide（relaxin） |
| Frida | host 17.7.3 ↔ device 17.23.3 |

一个动态侧必须交代的坑：host 与 device 版本错位导致 `Module.getExportByName` / `Process.findExportByName` 已被移除，必须改用 `Module.getGlobalExportByName`；attach 还有严格时序——`spawn → resume → 等 2~4 s → attach`，早于 ~0.9 s attach 进程约 1 s 被杀，而在 hook 回调里直接调 ObjC 会重入死锁拖垮整机（实测掉过一次线）。这些约束决定了"启动头两秒窗口"天然测不到，后文会再提。

分析期间自然产生了一个对照组：会话中途设备崩溃恢复，jbroot 哈希从 `.jbroot-4C4DC0C67115CBA8` 变成 `.jbroot-8FF0E778ECD87DA9`，注入层结构一致，正好用来验证结论的稳定性。

## 1. 第一个发现：三款 App 共用同一套安全组件

同一把 XOR key 下，相同明文对应的密文完全相同，因此可以直接拿**密文**做跨 App 指纹。这把钥匙后面会详细讲，先看结论。

### 1.1 运行期符号名表：番茄 ≡ 红果，逐字节同一

把加密池里的一组密文解出来，是这样 15 条：

```
dladdr  stat  lstat  fopen  __opendir2  getifaddrs
CCCryptorCreateWithMode  CCCryptorUpdate
CFNetworkCopySystemProxySettings  CFBundleIdentifier
Filter  .plist  libdyld.dylib  libcommonCrypto.dylib  CFNetwork
```

番茄这 15 条落在 `0x112F3C29A` 起的一段，红果落在 `0x11335A19A` 起的一段，**偏移恒定 `0x41DF00`，15/15 一一对应，连"哪条用加密变体 v1、哪条用 v2"都完全相同**。

这里有个容易被原始分析带偏的点：这**不是**越狱路径黑名单，而是 **`dlsym` / CFNetwork 的运行期符号名表**。App 在运行期用 `dladdr`/`dlsym` 去解析 `stat / lstat / fopen / __opendir2 / getifaddrs` 这些 libc 符号——这正是"只读导入表会低估检测面"的直接证据：这些函数在导入表里根本不出现。

抖音是同一框架的**不同配置子集**：`CCCryptorCreateWithMode`、`CFNetworkCopySystemProxySettings`、`CFBundleIdentifier`、`libcommonCrypto.dylib` 在；部分密文缺失；池内额外多出 `com.bytedance.safeguard.data`——第一次出现"safeguard"这个自曝家门的字符串。

### 1.2 规则引擎：同一台 VM，只是配置规模不同

三款都带一台"字段求值虚拟机"，原语逐字节同构，差别只在喂进去的规则数：

| App | 规则条目 | 键名范围 | 注册函数 | VM 读 / 写原语 |
|---|---|---|---|---|
| 番茄 | 15 | `G0` + `CF0..CFD` | `0x10185ADF8` | `0x1019A08E4` / `0x1019A08F0`（`ctx+0x6070+idx*8`） |
| 红果 | 15 | `G0` + `CF0..CFD` | `0x1017DBDD0` | 同构 |
| 抖音 | 66 | `G0..G7` + `CF0..CF39` | `0x77AB3B4` | `0x78BDAB8` / `0x78BDAC4`（同构） |

读写原语都是 `ctx + 0x6070 + idx*8` 这种裸的槽位存取，三款逐字节一致。到这里"字节内部公共安全组件"已经不是推测，而是逐字节级的事实——**但要强调：横向比对在本研究里只是辅助印证手段，主线是把机制本身讲清楚。** 下面开始拆机制。

---

## 2. 检测链的真实形态：它挂在 HMD 上报链上

原始分析最大的空白是"检测到底在什么时候、被谁调起"。动态 backtrace（Frida 权威符号化，非推测）把这条链钉死了：

```
+[SSLaunchMonitor markFirstClassLoad]
 ├─ +[HMDTTMonitorHelper reportHeaderParamsWithInjectedInfo:]   （性能上报）
 ├─ -[HMDExceptionModuleReporter _reportExceptionData]          （异常上报）
 └─ +[HMDConfigHelper requestHeaderFromProvider:]               （远程配置拉取）
      └─ -[HMDUploadHelper headerInfo]        0x10A09EDBC
           └─ -[HMDInfo isEnvAbnormal]        0x10A09F728
                └─ dispatch_once
                     └─ 0x10A09F79C   statfs × 93 路径 + /hmd_tmp_file 越界写
```

HMD 是字节的 Heimdallr 监控框架。关键认知有两点：

1. **触发时机不是"启动检测一次"，而是每次构造 HMD 上报 header**——性能、异常、远程配置三条并列路径都会走到，沙盒探测结果用 `dispatch_once` 缓存一次。
2. **真正的检测体 `0x10A09F79C` 干两件事**：对 93 条路径跑 `statfs`，以及往 `/hmd_tmp_file` 做一次沙盒越界写。

越狱标志最终进了哪里？进了 HMD 上报 header 的**明文字典**（34 个字段），其中有一个字段叫 `is_env_abnormal`。这一点很重要——它否定了"越狱标志走 protobuf、字段名不可见"的旧假设：至少 HMD 这条通道是明文可读的。

---

## 3. 那些"看起来在检测"、其实没在跑的代码

逆向最容易犯的错，是把二进制里存在的检测代码直接当成"正在生效的检测"。这次最有价值的几个结论恰恰相反。

### 3.1 `fopen` 五探针 = 死代码（三重独立证据）

有一族 `fopen` × 5 路径的探针（`0x10250F8C4`，同族还有个开关不同的 `0x10264A018`），形态非常像经典越狱文件检测。但三条独立证据一致判它死亡：

| 证据 | 方法 | 结果 |
|---|---|---|
| 静态引用 | `ADRP+ADD/LDR`、chained 指针槽、相对指针、`__init_offsets`、base 相对表 全扫 | 全 0 |
| 运行期登记 | 模块非可执行段 23,674,880 B 全扫函数指针 | 0 命中 |
| 运行期调用 | 45 s 会话计数 | 0 次 |

静态零引用、内存零登记、运行时零调用——这不是"没触发"，是根本没有可达入口。真正跑在链上的是上一节那个 `statfs` 版本。

### 3.2 `statfs` 的 93 条路径，在 roothide 上全部 miss

`statfs` 这条是真的在跑（挂在 HMD 链上），但它查的是什么、查中没有，是两回事。先做一件原始分析没做到的事：**把三款里每一处 `statfs` 族调用全部静态定性**。

`statfs` 普遍走 `分支岛 → 二级片段 → stub` 三跳，只扫 `BL` 到 stub 会漏掉大部分调用点。按三跳展开后，番茄与红果各 **12** 处 `statfs` + 3 处 `statvfs` + 2 处 `fstatfs`（又一处数字完全相同的同组件证据）。逐处看它们读没读 `f_flags`（偏移 0x40）、`f_type`（偏移 0x3c）：

- `f_flags` 读取次数 = **0 / 17**。

这意味着**全部 17 处没有任何一处做 `f_flags & MNT_RDONLY` 的"根分区被重挂载为可读写"判定**。原始分析里"statfs 可能用于根分区 remount 检测"的猜测，由此从"动态单点否证"升级为"全调用点静态穷举否证"。`statfs` 族的真实用途只有三类：路径存在性探测（93 项表，用 `tbnz`/`cmn w0,#1` 把返回码布尔化）、磁盘空间查询、以及唯一一处 `f_type` 文件系统类型判定（`0x101866E70`）。

动态侧补刀：93 路径（去重 50 条）在本机实测 **434 次探测 / 0 命中**。这些是 Cydia 时代的 `/private/var/...` 老路径，在 roothide 的 rootless 布局下自然一条都对不上。

### 3.3 SafeGuard 规则引擎：一台没通电的状态机

前面那台 VM（`CF0..CFD`）看着像"逐项越狱检查清单"，实际逆出来是一套**通用字段求值 VM**：`field[6]` 是结果位，`field[8..12]` 是输入槽，每条规则读 N 个输入、调一个专属 helper、写 `field[6]`。helper 本身是通用运行时函数（lazy-init、`[x0+0x110]` 取对象、分支岛），不是"检查某个越狱特征"的领域谓词。

更关键的是可达性。对规则注册函数做穷尽排查：

| 来源 | 结果 |
|---|---|
| `BL/B`（三个可执行节） | 0 |
| `ADRP+ADD/LDR`（寄存器生命周期感知） | 0 |
| chained 指针槽 / int32 / int64 相对指针（全部节） | 0 |
| `__init_offsets` 静态构造表（2903 项） | 不在表内 |
| 运行期 VM 原语调用计数（番茄 / 抖音） | 0 / 0 |

**六路引用全 0，不在静态构造表，运行期零调用**——这台 VM 在当前构建里没有静态可达入口，运行期也从没被调起。旁证：它的沙盒目录 `.../Library/Heimdallr/CrashCapture/LoadLaunch/SafeGuard` 确实存在（模块初始化过），但规则求值没有发生。换句话说：引擎装好了、通电了，但没人踩油门。

## 4. roothide 下到底命中了什么

把所有探针在本机的真实表现列成一张表（两次 jbroot 哈希都测过）：

| # | 探针 | 实现位置 | 本机实测 | 判定 |
|---|---|---|---|---|
| 1 | `fopen` × 5 路径 | `0x10250F8C4` / `0x10264A018` | 零引用/零登记/零调用 | 死代码 |
| 2 | dyld 镜像名 5 子串 | `0x1083E1854` | 1118 次调用 / **1 次命中** | 靠目录名巧合命中 |
| 3 | `statfs` × 93 路径 | `0x10A09F79C` | 434 次探测 / 0 命中 | 全 miss |
| 4 | `/hmd_tmp_file` 越界写 | `0x10A09F79C` 内 | fd = -1 → `is_env_abnormal=1` | 触发（极性见下） |
| 5 | 逐镜像 `isEnvAbnormal` | `HMDCrashBinaryImage` | 读 1117 次，全 0 | 未标记任何注入库 |
| 6 | 规则引擎 `G0/CF0..CFD` | `0x10185ADF8` | 0 次调用 | 未参与判定 |
| 7 | `canOpenCydia` | `0x1074B70B8` | 未触发；且 `cydia` 未在 `LSApplicationQueriesSchemes` 声明 → iOS 15+ 恒假 | 逻辑上无效 |
| 8 | `canGetAllAppName` | `0x1074B7138` | 未触发 | 未测 |

### 4.1 最有意思的一条：唯一的"命中"是目录名撞名

探针 2 遍历已加载镜像名，拿去比对 5 条子串。roothide 全套注入库的名字**一条都不匹配**：

```
/usr/lib/systemhook-8FF0E778ECD87DA9.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/roothideinit.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/roothidepatch.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/libroothide.dylib
.../.jbroot-8FF0E778ECD87DA9/usr/lib/ellekit/libinjector.dylib
```

唯一命中的是：

```
.../.jbroot-8FF0E778ECD87DA9/usr/lib/TweakInject/FakeTweak.dylib
```

命中原因是路径里含 **`TweakInject`**（名单第 3 条），属于**目录名撞名**，不是库名命中。所以"旧名单对 rootless/roothide 没跟进"这个说法要精确修正为：**旧名单在 roothide 上由一次目录名巧合命中，5 个核心组件里 4 个被漏检。**

### 4.2 越界写的极性：普通设备可能也报 1

探针 4 是本地唯一真正给出非零结论的检测。静态看：`0x10A09F800` 处 `open_dprotected_np("/hmd_tmp_file", O_CREAT|O_RDWR)`，随后 `tbnz w0,#0x1f` 判符号位——**失败置 1、成功置 0**。动态看：本机 fd = -1（失败）→ 缓存 1 → `-[HMDInfo isEnvAbnormal]` 返回 1 → header 里 `is_env_abnormal = "1"`。

但这里有个诚实必须交代的疑点：按这条指令，"写失败 → 异常"意味着**普通未越狱设备在同一沙盒位置写失败时同样会报 1**。所以 `is_env_abnormal` 这个字段的真实语义，必然要结合服务端判定，本地只能还原到"写失败→1"这一步。本文不对后端含义做推断。

## 5. 解密体系：把整个加密字符串池逆出来

前面所有"解出某某字符串"都依赖同一把钥匙。完整逆出来是这样。

### 5.1 算法（key = `0xDEADBEEF`）

```
变体 1（0x109F8B83C）：
  整词: plain_word[i] = ror32(cipher_word[i] ^ 0xDEADBEEF, 23)      ; 4 字节小端
  尾部: plain_byte[j] = cipher_byte[j] ^ ((0xDEADBEEF >> (8*(j%4))) & 0xFF)

变体 2（0x109F778F4）：
  整词: plain_word[i] = cipher_word[i] ^ cipher_word[i-1] ^ 0xDEADBEEF
  尾部: 同变体 1
```

关键点在尾部：不满 4 字节的尾巴不走整词路径，而是逐字节异或 key 的低位字节。漏掉这一段，就会出现"最后 1~3 字节乱码"——这是早期分析踩过的坑，也是判断算法是否真正逆对的试金石。

实现上还有个陷阱：两个真身各挂一个分支岛（`0x107C16440` / `0x107C16448`），**hook 必须挂真身**，挂在岛上 `onLeave` 读到的是还没写入的缓冲。静态上 15 个调用点全部集中在 `0x1019616xx–0x1019624xx` 一个函数簇里。

### 5.2 全池批解：`__const` 7.89 MB → 11,812 条明文

两变体 × 两种对齐批量解密、去重后得到 **11,812 条不同明文**（路径 189、bundle-id 16、纯标识符 1,026、其他 10,581）。越狱/注入相关命中 19 条，其中 6 条是原始 50 条路径名单里完全没有的：

```
com.opa334.Dopamine            com.opa334.Dopamine.roothide
com.roothide.manager           com.roothide.manager.plist
com.xina.jailbreak.plist       com.xina.blacklist.plist
```

这改写了"名单只覆盖 Cydia 时代"的旧印象：**名单其实覆盖了 Dopamine（rootless）/ roothide / Xina 三代，但用的是 bundle-id 与 plist 名，不是路径与库名。** 这正是此前只做路径扫描完全看不到它们的原因。原 50 条路径里有 29 条能在加密池对上，仍然缺席的是 `ellekit`、`libhooker`、`/var/jb`、`substitute`、`trollstore`。

### 5.3 roothide 密文块是惰性的

池里确实存在 `com.roothide.manager`、`com.opa334.Dopamine.roothide`、`Documents/bootstrap.tar`、`/var/mobile/Library/HTTPStorages` 这些 roothide 特征串，且可解。但三条独立证据表明当前环境没有任何路径会去解它们：静态五种编码 × 三个可执行节 + 数据段指针引用全 0；778 MB 可写区间扫三条明文 0 命中；hook 两个解密真身 22 s，13 次调用全部落在符号名表 `0x112F3Cxxx`，无一进入密文块所在的 `0x112F15Cxx`。

密文在、能解、但在 roothide + 正常使用 + 无崩溃上报的条件下不可达。

## 6. 控制流平坦化：点状，而非整库

很多人默认大厂 App 是整库 OLLVM。实测不是。判据：`br xN` 前 7 条指令内同时出现 `adr` + `ldrsw/ldrb` + `add`，站点间距 ≤2KB 聚为一函数。

| 二进制 | dispatch 站点 | 聚类 ≈ 函数 | 覆盖代码 | 占 `__text` |
|---|---|---|---|---|
| 番茄 Reading | 10,589 | ≈4,925 | ≈2,582 KB | **0.89%** |
| 抖音 AwemeCore | 25,155 | ≈11,280 | ≈5,341 KB | **0.81%** |

**只有 0.8–0.9% 的代码被平坦化，点状分布在安全/风控相关模块**——这也是为什么大部分代码能直接读。

这里补一个抖音侧的分析缺陷修正，影响上面的计数口径：原始的函数起点识别只认三类序言（`sub sp` / `stp` 预索引 / `pacibsp`），必然漏掉无栈帧的叶子函数（典型如 `0x1E6EF964` 那种 `adrp/ldrsw/ldr/ret` 的 getter）。以 ObjC IMP 为真值实测，CJPay 窗口覆盖率只有 **16.9%**；叠加"终结指令（`ret`/`b`/`br`/`udf`）之后线性扫描起点"的补全后拉到 **97.2%**。因此此前对抖音任何"函数级"的统计都系统性低估了叶子函数占比，校正后抖音侧函数边界与番茄同样可信。

## 7. 用 IDA Hex-Rays 做第三方交叉验证

前面的结论来自自写工具链（Capstone + numpy 交叉引用索引）。为避免"自己验自己"，最后用 IDA Pro 9.3 的 Hex-Rays 独立复核。

直接 `idat -A` 导入 508 MB 的 `Reading` 在 16 GB 机器上不可行（卡在 ObjC 解析 >750 s，`.id0` 2.1 GB；`idalib` 无分析加载也 >600 s 未返回）。改走**雕刻子二进制**：按目标函数取 ±1~4 KB 窗口包成最小 ELF64（`PT_LOAD.p_vaddr` 保持原始虚拟地址），用 `idalib.open_database(run_auto_analysis=False)` + `add_func` + `ida_hexrays.decompile`，每函数约 1 秒。跨切片调用显示为 `MEMORY[addr]()`、尾调用显示为 `JUMPOUT(addr)`，地址与原二进制一致。

11 个关键函数全部与手工结论逐条对上，摘几条：

| 目标 | Hex-Rays 反编译要点 | 与手工结论 |
|---|---|---|
| `dec_v1` `0x109F8B83C` | `HIDWORD(v6)=c^0xDEADBEEF; out=v6>>23`；尾部 `out=c^(0xDEADBEEF>>v7)` | 一致（整词 ROR23 + 尾部逐字节） |
| `sandbox_statfs93` `0x10A09F79C` | `while(v0!=344)`→43 项，`while(v0!=400)`→50 项；`open(...,514)`；`if (fd & 0x80000000) →1 else {close;unlink;→0}` | 一致（43+50 / `/hmd_tmp_file` / `O_RDWR\|O_CREAT=0x202` / fd 符号位） |
| `vm_get/vm_set` | `*(qword*)(a1 + 8*a2 + 24688)` | `24688 = 0x6070`，一致 |
| `pred_inject_substr` `0x1083E1854` | `if (v2==40)` 循环比对 | `40/8 = 5` 项，一致 |
| `sysctl_caller` | `mib[2]=1; mib[3]=pid`；返回后浮点换算，**全程无 `0x800` 测试** | 一致（无 P_TRACED 判定） |

这些数都能自洽验算：`344/8=43`、`400/8=50`、`40/8=5`、`514=0x202=O_RDWR|O_CREAT`、`24688=0x6070`，`0xDEADBEEF` 低字节 `EF BE AD DE`，且 `(((x<<32)|x)>>23)` 的低 32 位恰好等于 `ror32(x,23)`。手工逆向与 Hex-Rays 无一处需要推翻的差异。

## 8. 对一些常见假设的修正

这次推翻/收紧了若干看似"显然"的结论，列出来比结论本身更有价值：

1. **`fopen` 五探针不是主检测，是死代码**（静态零引用 + 内存零登记 + 运行时零调用）。
2. **`statfs` 不做 remount 判定**：全 17 处调用点 `f_flags` 读取 0 次，猜测被全调用点穷举否证。
3. **"反调试走 sysctl 查 P_TRACED"不成立**：mib 常量静态验证确为 `{1,14}`、`size=648`（`kinfo_proc`），形态像经典探针；但全 `__text` 无 `AND #0x800`，4 个 `_sysctl` 调用点附近无 bit11 测试，返回后是对结构头做浮点换算——sysctl 只用于取进程信息，没有实现 P_TRACED 判定。
4. **加密池不是越狱路径表，是 dlsym/CFNetwork 符号名表**（15 条）。
5. **名单覆盖三代越狱**（Dopamine/roothide/Xina），但以 bundle-id 和 plist 名出现，不是路径。
6. **越狱标志 HMD 通道是明文字典**（34 字段，含 `is_env_abnormal`），不是不可见的 protobuf。
7. **平坦化仅 0.8–0.9%**，点状分布于安全模块，非整库 OLLVM。
8. **规则引擎在本构建不可达**：六路引用全 0、运行期零调用，但模块初始化确实发生过。

## 9. 没能验证 / 无法验证的

诚实地列出边界：

- **启动 0–2 s 窗口内规则引擎是否跑过一次**：更早 attach 会打死进程，这个窗口测不到。
- **崩溃上报路径是否会解密 roothide 密文串**：唯一验证方式是人为制造崩溃，那会改变目标行为，属于自设红线，不做。
- **`is_env_abnormal` 的后端语义**：需服务端对照，本地只能还原到"写失败→1"。
- **SafeGuard 调用方是否在 Swift 侧**：Swift 字面量走 `__swift5_reflstr` 相对偏移表，ARM64 引用扫描覆盖不到。
- **CJPay `appendParamTo:` 的真实 key**：番茄/抖音充值均为 App Store 内购，无第三方支付入口，这条链从未执行，客观拿不到。

## 10. 结论与思考

把机制收束成几句话：

1. **三款 App 共用一套安全组件**：符号名表 15/15 逐字节同一（偏移恒定 `0x41DF00`），规则引擎 VM 原语逐字节同构，差别只在规则配置规模（番茄/红果 15 条、抖音 66 条）。

2. **真实检测面比"代码里写了多少检测"窄得多**：`fopen` 五探针是死代码；`statfs` 93 路径在 roothide 上全 miss；`canOpenCydia` 因未声明 scheme 恒假；文件遍历链需要支付页才跑而本机无此入口。本地唯一真正给出非零结论的，只有 `/hmd_tmp_file` 越界写（→ `is_env_abnormal=1`）和那次目录名巧合命中。

3. **最该当成结论的，不是"某个探针是否命中"，而是这套防静态分析的设计是系统性的**：运行期符号名解析、方法 IMP 三跳分支岛、字符串两套变体加密、子系统入口全部运行期分发——四者叠加，使"只读导入表 + 只看调用图"的分析必然遗漏检测面。单看任何一层都会得出偏乐观的结论。

4. **对抗的真正边界在服务端**：本地最强的一条（越界写）也只产生一个语义存疑的上报字段，识别与否最终由服务端结合设备指纹决定。纯静态/本地动态能还原到"采集什么、怎么上报"，但服务端如何裁决属于不可见区。

对做越狱检测的人，反过来读也成立：把检测逻辑藏进运行期解析和点状平坦化、把判定搬到服务端，确实显著抬高了纯静态分析的成本——但一旦允许只读动态观测，"哪条真在跑"仍然会暴露无遗。攻防的价值，恰恰在于把"看起来在检测"和"真的在检测"区分开。

## S1 —— 澄清并修正：加密池其实是「运行期符号名表」，不是路径黑名单

### 解密算法（已完全逆出，含尾部）

变体 1（0x109F8B83C）：
```
plain_word[i] = ror32(cipher_word[i] ^ 0xDEADBEEF, 23)      ; 按 4 字节小端整词
plain_byte[j] = cipher_byte[j] ^ ((0xDEADBEEF >> (8*(j%4))) & 0xFF)  ; 尾部 1~3 字节
```
变体 2（0x109F778F4）：`plain_word[i] = cipher_word[i] ^ cipher_word[i-1] ^ 0xDEADBEEF`

## S3 —— 重要修正：我此前对「roothide 字符串消费者」的判断是错的

**旧结论（第 2 轮）**：`0x112F15C00–0x112F16000` 有 7 处代码引用（0x10185AF08 等），构成"密文指针 + 校验函数"配对表。

**实测否定**：那批"引用"是我的引用索引的**假阳性**。原因：`XrefIndex` 用「adrp 后 N 条指令内 add/ldr 同寄存器」的窗口匹配，**不感知寄存器被后续 adrp 覆盖**。`0x10185AF04: adrp x8,#0x10185A000` 之后 `0x10185AF08: add x8,x8,#0xc70` 应指向 `0x10185AC70`（checker），却被同时配到上一条 `adrp x8,#0x112F15000` 上，于是凭空得到 `0x112F15C70`。

用**寄存器生命周期感知**的线性扫描重做后：

| 检查 | 结果 |
|---|---|
| `adrp+add/ldr` 物化到 `0x112F15C00..0x112F16000`（全 __text，寄存器被覆盖即止） | **0** |
| 数据段中指向该区间的 chained 指针槽 | **0** |
| 相对指针（field+int32/int64） | **0**（此前已测） |

而该区间**确实是密文**（原始字节为高熵数据，`0x112F15EEC` 起还有 `00 00` 前缀），我按变体 1 解出 `com.roothide.manager` / `com.opa334.Dopamine.roothide` / `Documents/bootstrap.tar` / `/var/mobile/Library/HTTPStorages` 是**真实存在的加密串**。

**结论**：这些 roothide 特征串**存在，且没有任何静态可解析的消费者**——三种编码方式、三个可执行节、数据段指针全为 0。与 `fopen` 五探针的"死代码"签名完全一致，指向同一种机制：**运行期计算 / 表驱动分发的访问方式**（例如 `adrp` 只取页基址 + 运行期索引寄存器，静态无法解析）。
**这条必须等设备恢复后用动态确认**（在解密例程返回处 dump，或直接扫内存中的明文字符串）。

与旧哈希（4C4DC0C6…）完全一致：**1117~1118 次遍历、1 次命中、命中的永远是 `TweakInject` 目录名**。这条结论现在有两次独立会话、两个不同 jbroot 哈希的复现。

## R2 —— 逐镜像 `isEnvAbnormal`：假设被实测否定

我的假设（上一轮）：`HMDCrashBinaryImage.isEnvAbnormal` 可能是真正"按单个 dylib 标记可疑"的机制。

安全实现（hook 内只记指针/整数，ObjC 解析全部延迟到 `setTimeout`，不再重入）：

```
sets = 1          # -[HMDCrashBinaryImage setIsEnvAbnormal:]  只被调用 1 次
gets = 1117       # -[HMDCrashBinaryImage isEnvAbnormal]      被调用 1117 次（≈ 每个已加载镜像一次）
abnGets = 0       # 返回非 0 的次数 = 0
IMGMARK_FLAGGED: count = 0
```

**结论**：HMD 崩溃模块**确实会逐镜像读取**这个标志（1117 次 = 镜像数），但在本机 roothide 上**没有任何一个镜像被标为异常**——`systemhook` / `ellekit` / `TweakInject` / `roothideinit` 全部为 0。

→ **假设不成立**。这个字段不是有效的注入识别点（至少在正常运行时；不排除崩溃上报时才重新计算）。

## R3 —— roothide 明文在运行期内存中**不存在**

对 `rw-` 全量可写区间（扫描 778 MB）搜三条明文字节串：

| needle | 命中 |
|---|---|
| `com.roothide.manager` | **0** |
| `com.opa334.Dopamine.roothide` | **0** |
| `Documents/bootstrap.tar` | **0** |

结合 S3 的"静态零引用"，现在的证据链是：

- 密文确实存在（高熵字节，按 `ror(c^0xDEADBEEF,23)` 可解出上述明文）；
- 静态没有任何代码/指针引用它（三种编码 × 三个可执行节 × 数据段全 0）；
- 运行期内存里也**从未出现**这些明文（idle 会话 30 s + 778 MB 扫描）。

**最可能解释**：这组字符串属于**按需解密、且当前路径未触发的规则数据**（例如只在特定风控/规则求值时解开，或由服务端下发的配置命中后才用）。标注为 **未证实**，缺：规则求值入口或对应触发条件。

**与 R2 的呼应**：既然 `isEnvAbnormal` 全部为 0、明文也没出现，说明这套"roothide 识别规则"在本次会话里**根本没被执行**——不是"检测到了但被绕过"，而是"没跑到"。

## R4 —— 安全性回归

本轮所有脚本遵守新纪律：**hook 回调里不出现任何 ObjC 调用**，对象解析统一放在 `setTimeout`。设备全程稳定，无卡死、无掉线。

# 规则引擎与跨 App 比对（静态 + 定位）

## C1 —— 规则引擎的取值原语（已还原）

两个 helper 极短，语义明确：

```asm
; x0 = ctx, w1 = field index
0x1019a08e4: add x8, x0, w1, uxtw #3      ; x8 = ctx + idx*8
0x1019a08ec: ldr x0, [x8, #0x6070]        ; 读 ctx->fields[idx]
0x1019a08ec: ret

0x1019a08f0: add x8, x0, w1, uxtw #3
0x1019a08f8: str x2, [x8, #0x6070]        ; 写 ctx->fields[idx]
0x1019a08fc: ret
```

即：存在一个 **字段数组** `ctx + 0x6070 + idx*8`。`CF0…CFD` 这些"规则"本质上是**对字段数组做读/写/比较的小步骤**：

- `CF0 (0x10185A9B0)`：调 `0x107C1516C`（分支岛 → `0x10A542664`）取一个值，写进 **field[6]**
- `CF1 (0x10185A9DC)`：读 field[8]、field[9] 后比较
- `CF2 (0x10185AA14)`：同样读 field[8]、field[9]，再组合
- `CF3 (0x10185AA60)`：读 field[8]，调 `0x107C15178`（→ `0x10A006C7C`），用 field[6] 作参数

—— 这是**规则/表达式求值器**的步骤函数，不是"检查项"本身。`G0` / `F0` 更像控制流标记（goto / function）。

## C2 —— 这套东西属于 HMD 的 SafeGuard 子模块（关键连线）

跨 App 字符串检索发现一条路径：

```
Library/Heimdallr/CrashCapture/LoadLaunch/SafeGuard
```

而抖音的加密池里解出：`com.bytedance.safeguard.data`。

把它与前面的发现串起来：

| 发现 | 归属 |
|---|---|
| `HMDCrashBinaryImage`（逐镜像记录、含 `isEnvAbnormal`） | Heimdallr 崩溃模块 |
| `binaryImagesLogStrWithMustIncludeImagesNames:includePossibleJailbreakImage:` | 同上 |
| 规则表 `G0/CF0…CFD` + 字段数组 VM | `CrashCapture/LoadLaunch/SafeGuard` |
| `com.roothide.manager` 等加密串 | 同一子系统（规则数据） |

这解释了 R3 的"明文从未出现"：**这些串是崩溃/上报路径（crash capture）按需解密的**，正常刷 App 不会走到。

## C3 —— 跨 App 比对：番茄 ≡ 红果，抖音同源但不完全一致

同一把 key（`0xDEADBEEF`），所以**相同明文的密文逐字节相同**，可以直接用密文做跨 App 指纹：

| `fopen` 密文 | 0x112F3C2D0 | 0x11335A1D0 | **0 处** |
| `CCCryptorCreateWithMode` 密文 | 0x112F3C330 | 0x11335A230 | 0x29D91D90 |

| `libdyld.dylib` 密文 | 0x112F3C3B9 | 0x11335A2B9 | 0x29D91E89 |
| `CF0…CF3` 规则名表 | 0x112F158F7 | 0x1133337F7 | 0x29D8E0F0 |

- **番茄与红果：四处密文全部逐字节一致** → 同一份组件、同一版本、同一 key。
- **抖音：规则名表在、部分符号密文在，但 `fopen` 与 `CFBundleIdentifier` 两处密文缺失** → 抖音用的是同一套框架的**不同配置子集**（或那两项改了实现）。

  ```
  其中 `com.bytedance.safeguard.data` 只出现在抖音，番茄/红果该位置没有。

## C4 —— 系统性问题：这套子系统的所有入口都是运行期分发的

对三个"入口"分别做了完整引用检查（`__text` + `__stubs` + `__objc_stubs`，四种编码）：

| 入口 | BL/B 调用者 | adrp 物化 | 数据槽 | 相对指针 |
|---|---|---|---|---|
| `fopen` 五探针 `0x10250F8C4` / `0x10264A018` | 0 | 0 | 0 | 0 |
| 规则表构建 `0x10185ADF8` | **0** | **0** | — | — |
| roothide 密文区 `0x112F15C00+` | — | 0 | 0 | 0 |

三者签名完全一致。结论（已证实的"缺席"）：**该子系统的入口不由静态引用可达**，必然通过运行期计算/表驱动分发。这也解释了原报告为何会觉得"检测点零散、调用链断裂"——不是断，是静态不可达。

## C5 —— 下一步（动态，只读）

**探针思路**：既然规则引擎的读写原语是 `0x1019A08E4 / 0x1019A08F0`，就 hook 这两个**极小的字段读写函数**并计数。

- 若计数为 0 → 规则引擎在正常使用中不跑（可据此断定"roothide 规则未参与日常判定"）；
- 若计数 > 0 → 说明引擎在跑，进一步记录 `w1`（字段索引）分布，就能反推 `CF0…CFD` 到底碰哪些字段，从而还原规则语义。

这个探针**不需要触碰任何返回值**，且 hook 体里只有整数自增，安全。

## C6 —— 实测：规则引擎在正常会话中**完全没有运行**

按 C5 的探针思路，hook 字段读写原语 `0x1019A08E4`（读）/ `0x1019A08F0`（写），番茄 spawn → settle 4s → attach → 观测 17 s：

```
VM_STAT:  gets = 0   sets = 0   uniqGet = 0   uniqSet = 0
```

**17 秒内、一次都没调用。**

### 这条负结果的效力与边界

- **已证实**：attach 之后的正常使用窗口内，`CF0…CFD` 这套规则引擎**不参与任何判定**。
- **未覆盖**：启动最早期（t < 4 s）。因为 attach 必须等到 ≈3–4 s 才稳定（更早会把进程打死，已实测），所以"启动瞬间是否跑过一次"没有排除。
- 结合 R2（`isEnvAbnormal` 被读 1117 次但全为 0）与 R3（roothide 明文从未出现），三条独立观测指向同一结论：**这套 roothide/SafeGuard 规则在当前环境（roothide + 正常使用 + 无崩溃上报）**里不生效**。

### 对整体判断的收敛

至此，"字节系这套检测能否识别 roothide"在本机上的答案已经很具体：

| 环节 | 有没有跑 | 结论 |

| 逐镜像 `isEnvAbnormal` | 读了 1117 次，全 0 | 未标记 |

| `canGetAllAppName` / CJPay 链 | 无第三方支付入口 | 未测 |

## D1 —— `CF0…CFD` 的字段级语义（静态，全部 15 个步骤函数解完）

按"读哪些字段 / 写哪些字段 / 调哪个 helper"逐条解码：

| 规则 | 读字段 | helper | 写字段 |
|---|---|---|---|
| `G0` | — | isl[-4] | — |
| `CF0` | — | isl[+0] | **field[6]** |
| `CF1` | 8, 9 | isl[+4] | — |
| `CF2` | 8, 9 | isl[+8] | **field[6]** |
| `CF3` | 8 | isl[+12] | **field[6]** |
| `CF4` | 8, 9, 10 | isl[+16] | — |
| `CF5` | 8, 9, 10 | isl[+20] | **field[6]** |
| `CF6` | 8, 9, 10 | isl[+24] | — |
| `CF7` | 8 | isl[+28] | **field[6]** |
| `CF8` | 8, 9, 10, 11, 12 | — | — |
| `CF9` | 8, 9 | isl[+36] | **field[6]** |
| `CFA` | 8, 9 | isl[+40] | — |

| `CFC` | 8, 9 | — | — |
| `CFD` | 8, 9, 10, 11, 12 | — | — |

**结构清晰**：`field[6]` 是**累加器/结果位**，`field[8..12]` 是**输入槽**（元数 1~5），每个规则调一个专属 helper（分支岛 `0x107C1516C + 4k`）。

**但 helper 本身是通用运行时函数**，不是领域谓词：
- `isl[+0] → 0x10A542664`：读一个 lazy-init 字节，再调 import `0x111A95904`
- `isl[+4] → 0x10A10F728`：从 `[x0+0x110]` 取对象、构造栈上结构
- `isl[+8] → 0x10A0D0FC8`：分支岛 → `0x10A0D0F5C`

即：这套东西是**通用字段求值 VM**（元数 1~5 的规则步），而不是"逐项越狱检测清单"。上一轮把 `CF0…CFD` 当"检查项"的描述需要按此修正。

## D2 —— 运行期解密实测：13 次调用，没有任何一次碰 roothide 密文区

全部 cipher 落在 0x115078xxx（= 静态 0x112F3Cxxx，滑移后）
inRoothide = false × 13
```

13 条正好是静态 15 条里的子集（`Filter` / `.plist` 本窗口未调用）。

→ **roothide 密文区（`0x112F15C00+`）在两个解密例程的运行期调用里也从不出现**。至此 ③ 的三条独立证据齐了：
1. 静态零引用（三种编码 × 三个可执行节 × 数据段指针）；
2. 运行期 778 MB 可写区间内明文从未出现；
3. 运行期解密调用全部落在符号名表，无一进入该区间。

**结论**：该密文块在"roothide + 正常使用 + 无崩溃上报"条件下**完全惰性**。标注为已证实的"未触发"，而非"未实现"。

## G1 —— 目标 B 静态验算：**mib 对上，但 P_TRACED 判定不存在（修正我此前的结论）**

### 静态证据 1：mib 常量

```
0x106C873D0: adrp x8, #0x112D0B000
0x106C873D4: ldr  d0, [x8, #0xa38]        ; 8 字节常量
0x106C873D8: stur d0, [x29, #-0x28]
0x106C873DC: mov  w8, #1
0x106C873E0: stp  w8, w0, [x29, #-0x20]   ; mib[2]=1, mib[3]=pid
0x106C873E8: sub  x0, x29, #0x28
0x106C873EC: bl   #0x109e73fc0            ; x2=sp+0x10(buf), x3=sp+8(&size)
0x106C873F0: bl   #0x109e3b0d8            ; w1=4, x4=0, x5=0 → b 岛 → _sysctl
```

读 `0x112D0B000+0xA38` 的 8 字节 = `01 00 00 00 0e 00 00 00` → **{1, 14}** = `CTL_KERN, KERN_PROC`。
另一处 `0x109EE5D10: mov w8,#0x288` = **648** = `sizeof(kinfo_proc)`。
`0x109E3B0D8` 尾跳的分支岛指向 `0x111A96660` = `_sysctl`（`otool -Iv` 符号表确认）。

**静态结论**：mib = `[1, 14, 1, pid]`、`namelen=4`、`buf=kinfo_proc(648B)` —— 与动态读数完全一致。

### 静态证据 2：**没有 0x800 掩码测试**

| 扫描 | 结果 |
|---|---|
| `AND w?, w?, #0x800`（按位掩码编码精确匹配，全 `__text`） | **0 处** |
| `TBZ/TBNZ bit11`（等价写法） | 306 处（其他数据用），**距 4 个 `_sysctl` 调用点 ±32KB 内的：0** |

番茄共有 4 个 `_sysctl` 直接调用点：`0x109F54490`、`0x10A0B681C`、`0x10A2679B0`、`0x10B0C8F8C` —— **每一个附近都没有 bit11 测试**。

### 这一处的真实用途

sysctl 返回后：

```
0x106C873F4: fmov  d0, xzr
0x106C873F8: cbnz  w0, #0x106c8740c      ; sysctl 失败 → d0=0
0x106C873FC: bl    #0x109ee5cec          ; ldr d0,[sp,#0x10]; scvtf d0,d0
0x106C87404: ldr   d2, [x8, #0x440]
0x106C87408: bl    #0x109e3e7ac          ; fdiv/fmadd
```

取的是 `kinfo_proc` 头部 8 字节做**浮点换算**，不是读 `p_flag`。

**→ 修正**：我此前写"反调试：P_TRACED 形态已证实"**不成立**。准确表述是：**mib 形态与经典 P_TRACED 探针相同，但该 App 没有实现 `0x800` 判定**；sysctl 在此用于取进程信息（启动时间一类）。动态读到的 `p_flag=0x04004004`（0x800 未置位）这个值是真的，但**没有人读它**。

## 六、解密体系（完整逆出）

### 6.1 算法

```
变体 1（0x109F8B83C）：
  整词: plain_word[i] = ror32(cipher_word[i] ^ 0xDEADBEEF, 23)     ; 4 字节小端
  尾部: plain_byte[j] = cipher_byte[j] ^ ((0xDEADBEEF >> (8*(j%4))) & 0xFF)   ; 1~3 字节

变体 2（0x109F778F4）：
  整词: plain_word[i] = cipher_word[i] ^ cipher_word[i-1] ^ 0xDEADBEEF
  尾部: 同变体 1
```

**关键点**：尾部不走整词路径，而是逐字节异或 key 的低位字节。漏掉这一段就会出现"最后 1~3 字节乱码"（本项目早期现象）。


### 6.2 调用布局

- 两个真身各对应一个分支岛（`0x107C16440` / `0x107C16448`）。**hook 必须挂真身**，挂岛上 `onLeave` 读到的是尚未写入的缓冲。
- 静态共 15 个调用点，全部集中在 `0x1019616xx–0x1019624xx` 一个函数簇内。

---

### 6.3 全池批解结果（`__const` 7.89 MB）

两变体 × 两种对齐（0 / +2 位移）批量解密、去重后：**11,812 条不同明文**（路径 189、bundle-id 16、纯标识符 1,026、其他 10,581）。

com.xina.jailbreak.plist       com.xina.blacklist.plist

结论：**点状布置在安全/风控相关模块，不是整库混淆**——所以大部分代码仍可直接读。



### 6.5 Hex-Rays 交叉验证（IDA Pro 9.3 + 雕刻子二进制）

`Reading` 单文件 508 MB、ObjC 类 78,911 个，`idat -A` 全量导入在 16 GB 机器上不可行（卡在 ObjC 解析 >750 s，`.id0` 2.1 GB）。改用**雕刻子二进制**：按目标 ±1~4 KB 取窗口包成最小 ELF64（`p_vaddr` 保持原虚拟地址），`idalib.open_database(run_auto_analysis=False)` + `add_func` + `ida_hexrays.decompile`，每函数约 1 秒。产物：`analysis/fanqie/hexrays_f5.md`（1,242 行 / 11 个函数）。

| 目标 | 反编译要点 | 与手工结论 |
|---|---|---|
| `dec_v1` | `HIDWORD(v6)=cipher^0xDEADBEEF; out=v6>>23;` 尾部 `out_byte=c^(0xDEADBEEF>>v7)` | 一致（整词 ROR23 + 尾部逐字节） |
| `sandbox_statfs93` | `while(v0!=344)`→43 项；`while(v0!=400)`→50 项；`open(0x1136AD0D6, 514)`；`if (fd & 0x80000000) → 1 else {close;unlink;→0}` | 一致（43+50 / `/hmd_tmp_file` / 0x202 / fd 符号位） |
| `vm_get` | `*(qword*)(a1 + 8*a2 + 24688)` | 24688 = 0x6070，一致 |
| `pred_inject_substr` | `if (v2==40)` 循环比对 5 项 | 一致 |
| `sysctl_caller` | `mib={const(1,14), 1, pid}`，之后 `v5=0; if(!ret){浮点}` | 一致，且**无 0x800 测试** |

→ 手工逆出的算法与 Hex-Rays 输出逐条对得上，无需推翻的差异。局限：切片外调用显示为 `MEMORY[addr]()`，只适合验证已定位函数。

## 八、未验证 / 不可验证项（如实列出）

| 项 | 原因 |
|---|---|
| 启动 0–2 s 窗口内规则引擎是否跑过一次 | 更早 attach 会打死进程（多次实测），无法覆盖 |

| `jailBreak`/`appendParamTo:` 的真实 key | 番茄/抖音充值均为 App Store 内购，**无第三方支付入口**，CJPay 链从未执行 |

| `is_env_abnormal` 的后端语义 | 需服务端对照；本文只陈述"写失败→1"的实测与指令 |

## 九、研究结论

1. **三款 App 共用一套组件**：符号名表 15/15 逐字节同一（偏移恒定 `0x41DF00`），规则引擎 VM 原语逐字节同构，差别只在**规则配置规模**（番茄/红果 15 条，抖音 66 条）。

2. **真实检测面比原报告描述窄得多**：`fopen` 五探针是死代码；`statfs` 93 路径在本机全 miss；`canOpenCydia` 因未声明 scheme 而恒假；`fileExistsAtPath` 链需要支付页才跑（而本机无该入口）。**唯一真正跑起来并给出非零结论的只有 `/hmd_tmp_file` 越界写（→ `is_env_abnormal=1`）与"目录名巧合命中"。**

3. **规则引擎（SafeGuard）在本构建中不可达**：六路引用全 0、不在静态构造表、运行期零调用，但模块初始化确实发生过（沙盒目录存在）。它的规则数据里含 roothide 特征串，却没有任何可达路径会解密它们。

4. **防静态分析的设计是系统性的**：运行期符号名解析（dlsym 名表加密）、方法 IMP 走三跳分支岛、字符串两套变体加密、子系统入口全部运行期分发——三者叠加，使"只读导入表 + 只看调用图"的分析必然遗漏检测面。这一点比"某个探针是否命中"更值得作为结论。

5. **对抗的边界在服务端**：本地最强的一条（越界写）只产生一个上报字段，且语义存疑；识别与否最终由服务端结合设备指纹决定。

## 第二部分：静态分析实操流程（IDA / Ghidra）

### 阶段 0 — 解包与侦察
1. `unzip xxx.ipa`，进入 `Payload/xxx.app/`
2. 读 `Info.plist`：重点看 `LSApplicationQueriesSchemes`（往往直接暴露要探测的 scheme，如 cydia/sileo）、`CFBundleShortVersionString`（记录版本）
3. `otool -L 主二进制`：看链接了哪些库，是否有可疑的安全/风控相关 framework
4. `otool -l 主二进制 | grep -A4 LC_ENCRYPTION_INFO`：看 `cryptid`
   - `cryptid = 0` → 未加密，可直接分析
   - `cryptid = 1` → FairPlay 加密，需先获得脱壳后的 Mach-O 再做静态分析
5. 字节系 App 多为超大体积、含大量自研组件，注意识别 App 内嵌的 `.framework`（在 `xxx.app/Frameworks/` 下），**安全/风控逻辑很可能封装在独立 framework 内**，优先定位这些组件。

### 阶段 1 — 加载与预处理
- IDA：加载主二进制及各 Frameworks，等待自动分析完成；启用 Objective-C 解析，确保 selector/class 还原
- Ghidra：新建 project，导入所有 Mach-O，运行 auto-analysis（勾选 Objective-C / Swift 相关分析器）
- 对 Swift 代码：注意 mangled 符号（`$s` 开头），用 `swift-demangle` 还原；IDA 新版本与 Ghidra 均有 Swift demangle 支持

### 阶段 2 — 定位检测逻辑（见第三部分 checklist）

### 阶段 3 — 还原判定链
对每个命中的检测点：
1. 从 API 调用处出发，向上回溯谁调用了它（xref to）
2. 向下跟踪返回值如何汇入最终的布尔判定
3. 还原汇编 → 伪代码，记录函数地址、所属 image、判定逻辑
4. 标注这是"本地直接判定"还是"结果写入某字段后参与后续网络请求"
5. 对联动到业务风控的检测点，继续向上追到业务入口（福利、广告、商城等），还原"检测 → 业务降级"的完整调用链

### 阶段 4 — 辅助验证（非主线）
当某个 App 的某处逻辑因混淆、加壳或延迟触发而看不清时，到另一个 App 中查找对应实现来补全印证。判定两处是否为同一逻辑的参考依据：

| 参考维度 | 说明 |
|---|---|
| mangled 符号名 | 完全相同的 C++/Swift mangled 符号 → 强参考 |
| 字符串常量表 | 相同的越狱路径黑名单、顺序一致 → 强参考 |
| 函数结构 | 基本块数量/布局/调用顺序高度一致 → 中强参考 |
| framework 名 | 内嵌同名 framework → 强参考 |
| 常量/magic | 相同的加密 key、相同的指纹字段名 → 中强参考 |

此步骤仅用于补全证据、提高单点结论可信度，不单独产出"横向对比"结论。

## 附录：静态分析注意事项

- **大体积二进制**：抖音主二进制极大，IDA 初次分析耗时长，建议先只分析定位到的 framework 和关键函数区段
- **混淆**：字节系安全组件可能有字符串加密、控制流平坦化（OLLVM 风格）。若字符串搜不到明文，重点转向：常量解密函数的 xref、`+[... load]` 初始化时机、以及对导入符号调用点的直接排查。此时另一 App 中混淆较轻的同类实现可作为补全参考。
- **延迟触发**：部分检测不在启动时执行，而在进入特定业务（如商城、提现）时才触发，需从业务入口函数反向定位，而非只看 `application:didFinishLaunching`
- **服务端边界**：纯静态无法看到服务端下发逻辑，凡涉及"采集后上报再由服务端判定"的部分，只能还原到采集与上报点，服务端决策须明确标注为静态不可见
