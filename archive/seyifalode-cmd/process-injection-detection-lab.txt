Oluwaseyi Michael Falode | Cybersecurity & Cloud Security Engineer | Toronto, ON

> **Status:** the write-up, Sysmon configuration and SPL/KQL detections are complete. The Windows VM run and screenshots are still pending — see the [deliverable checklist](#status--deliverable-checklist).

A hands-on lab using standard Windows tooling (Sysinternals + Sysmon) to observe
what process injection looks like from a defender's seat, and to write a
detection for it. The goal isn't to build anything malicious — it's to
understand the telemetry injection leaves behind, since that telemetry is
exactly what EDR and game anti-cheat both rely on to catch it.

## Why This Exists

External game cheats — and a large share of commodity malware — work by
reaching into another process's memory: reading it for a wallhack, writing to
it for an aimbot, or injecting code so their logic runs inside the target.
From the operating system's point of view those are all the same handful of
primitives: open a handle to a process, allocate memory in it, write to it,
and start a thread. This lab is about learning to spot exactly that sequence,
and about being honest with myself about where that visibility runs out.

**What this lab deliberately does not do:** it doesn't write, ship, or run
cheat code or a working injector. Everything here observes legitimate Windows
behavior (Process Explorer, a debugger, Sysmon's own event stream) and the
traces injection would leave in that same telemetry. A detection write-up is
more useful — and more honest — than a how-to-cheat, and it's the skill an
anti-cheat or EDR team actually hires for.

---

## Lab Setup

1. **VM.** Windows 10 or 11 in VirtualBox, VMware, or Hyper-V. Snapshot it
   clean before touching anything, so the environment can be rolled back.
2. **Sysinternals Suite** — [learn.microsoft.com/sysinternals](https://learn.microsoft.com/sysinternals).
   Used here: Process Explorer (`procexp`), Process Monitor (`procmon`), VMMap.
3. **Sysmon** — also Sysinternals, and the important one. It writes rich
   process/thread events to the Windows event log, which is the closest free
   equivalent to what an EDR agent sees.

Install from an admin PowerShell prompt:

```powershell
# from the folder where you unzipped Sysmon
.\Sysmon64.exe -accepteula -i sysmonconfig.xml
```

`sysmonconfig.xml` in this repo is scoped narrowly on purpose — it only turns
on the event types this lab cares about (Process Create, Image Load,
CreateRemoteThread, ProcessAccess), so the Operational log stays readable
while learning what each field means. It is not a general-purpose Sysmon
config; for production use, layer in something like the SwiftOnSecurity or
Olaf Hartong configs.

To update a running install with a new config: `.\Sysmon64.exe -c sysmonconfig.xml`

## Part 1 — Know What "Normal" Looks Like

You can't spot abnormal until you've stared at normal. Open Process Explorer
as admin.

1. Find a well-behaved process — `notepad.exe` is perfect. Launch it, locate
   it in Process Explorer.
2. Right-click → Properties. Walk through:
   - **Threads** — how many, and what their start addresses point to (all
     inside known modules like `ntdll.dll`, `kernel32.dll`).
   - **Handles** (`View → Lower Pane View → Handles`) — Notepad on its own
     doesn't hold an open handle to other user processes.
   - **Image** — verify the signature (Notepad is Microsoft-signed).
3. Screenshot this as your baseline — `01-notepad-baseline.png`.

**The takeaway:** a normal process's threads start inside its own loaded
modules, and it generally doesn't hold `PROCESS_VM_WRITE` /
`PROCESS_CREATE_THREAD` handles to unrelated processes. Injection breaks both
of those assumptions.

---

## Part 2 — The Anatomy of Classic Injection (On Paper)

The classic `CreateRemoteThread` injection chain, and the ATT&CK sub-technique
each step maps to under **T1055 — Process Injection**:

| Step | Windows API | What it does | MITRE ATT&CK |
|---|---|---|---|
| 1 | `OpenProcess` | Obtain a handle to the target with write/execute rights | T1055 (parent technique — this is the enabling primitive for all sub-techniques below) |
| 2 | `VirtualAllocEx` | Allocate memory inside the target process | T1055.001 — Dynamic-link Library Injection *(when the allocation will hold a DLL path)*, or T1055.002 — Portable Executable Injection *(when it holds shellcode/a PE image)* |
| 3 | `WriteProcessMemory` | Write the payload (or a DLL path) into that memory | Same sub-technique as step 2 |
| 4a | `CreateRemoteThread` | Start a new thread in the target running the payload | T1055.001 / T1055.002 |
| 4b | `QueueUserAPC` (as an alternative to 4a) | Queue the payload to run next time a target thread enters an alertable wait | T1055.004 — Asynchronous Procedure Call |
| 4c | `SetThreadContext` + `ResumeThread` (as an alternative to 4a) | Hijack an existing, already-running thread's execution rather than create a new one | T1055.003 — Thread Execution Hijacking |

**The defender's insight:** steps 1–4 are individually legal Windows API
calls — plenty of legitimate software calls `OpenProcess` or
`WriteProcessMemory`. What's rare is the *combination*: one process opening a
cross-process handle with write+execute rights and then starting or
redirecting a thread in another process. That combination, not any single
call, is the detection.

---

## Part 3 — Watch the Telemetry with Sysmon

Now generate benign cross-process activity and see how Sysmon records it, so
the real events are recognizable later.

A safe, built-in way to create legitimate cross-process access is a debugger.
Attaching a debugger opens a handle to another process with strong rights —
the same class of handle injection needs — with no malware involved.

1. Install Sysmon with `sysmonconfig.xml` from this repo (see Lab Setup above).
2. Open Event Viewer → `Applications and Services Logs → Microsoft → Windows
   → Sysmon → Operational`.
3. Trigger benign cross-process access: attach WinDbg or the Visual Studio
   debugger to a process you started, or use Process Explorer's Suspend /
   inspect actions on a process you own. Watch for **Event ID 10
   (ProcessAccess)**.
4. Screenshot an Event ID 10 record — `02-sysmon-event10.png`. In your notes,
   call out three fields specifically:
   - **SourceImage** — who reached in
   - **TargetImage** — who got reached into
   - **GrantedAccess** — the rights mask requested; this is the field that
     matters most

**The takeaway:** `GrantedAccess` is the signal. A mask that includes
`PROCESS_VM_WRITE (0x20)` + `PROCESS_CREATE_THREAD (0x02)` on a target the
source has no legitimate business writing to is the high-value flag.

---

## Part 4 — The Detection

Full writeup with the plain-English rule, the allowlist, and the reasoning
behind both is in [`detections/rule-notes.md`](detections/rule-notes.md).
Queries: [`detections/query.spl`](detections/query.spl) (Splunk) and
[`detections/query.kql`](detections/query.kql) (Sentinel/Defender for
Endpoint).

Short version: alert on Sysmon Event ID 10 where `GrantedAccess` includes both
`VM_WRITE` and `CREATE_THREAD`, excluding known-good source/target pairs
(debuggers, AV/EDR engines, backup agents). Optionally correlate with an
Event ID 8 (`CreateRemoteThread`) from the same source→target pair within a
short window for a much stronger signal.

**Honest limit, stated up front:** an attacker who requests only the minimal
rights needed — or who uses APC injection / thread hijacking instead of
`CreateRemoteThread` — can produce a `GrantedAccess` mask that never trips this
rule, and neither T1055.003 nor T1055.004 ever fire Event ID 8 at all. This
catches noisy, off-the-shelf injection. It is not a general solution, and the
full limitations section in `rule-notes.md` says so explicitly rather than
overselling the coverage.

---

## Part 5 — Tying This to Anti-Cheat

External game cheats read and write game process memory using the exact same
`OpenProcess` + `WriteProcessMemory` primitives observed in this lab — a
wallhack is a read, an aimbot or full code-injection cheat is a write, and
both start with the same `OpenProcess` call this detection watches for.

Anti-cheat systems monitor for exactly these handle opens against the game
process, which is why the `GrantedAccess` mask matters as much in a game
client as it does in an EDR: a mask that includes `VM_WRITE` from a process
that isn't the game's own overlay, launcher, or a small set of known-good
tools is the same red flag either way.

**Kernel-mode anti-cheat exists precisely because this kind of user-mode
detection can be evaded.** Everything in this lab watches events surfaced
through a user-mode-visible log (Sysmon's own driver reports up through a
channel that, at sufficient privilege, can be tampered with or blinded before
it ever writes an event). A kernel driver gets ahead of that by intercepting
the same `NtOpenProcess` / `NtWriteVirtualMemory` calls at a level the
attacker can't unhook without their own kernel access — trading a large
attack surface and real privacy/trust concerns for visibility that's much
harder to blind. That trade-off, not "kernel mode is inherently better," is
the actual argument for it.

`detections/query.kql`:

```kql
// KQL — Cross-process injection handle detection
// Works against Microsoft Sentinel / Defender for Endpoint's DeviceEvents
// (Sysmon-equivalent ProcessAccess events surface as ActionType == "OpenProcessApiCall")
// or against a raw Sysmon Event ID 10 table if you're forwarding via
// Sysmon-for-Linux/Winlogbeat into a custom table — adjust table/column
// names to match your ingestion pipeline.

let SuspiciousAccessMasks = dynamic(["0x1F0FFF", "0x1FFFFF", "0x1438", "0x143A"]);
let Allowlist = dynamic(["vsjitdebugger.exe", "devenv.exe", "windbg.exe",
                          "x64dbg.exe", "x32dbg.exe", "procexp.exe", "procexp64.exe"]);
DeviceEvents
| where ActionType == "OpenProcessApiCall"
| extend GrantedAccessHex = tostring(AdditionalFields.GrantedAccess)
| where GrantedAccessHex has_any (SuspiciousAccessMasks)
| where InitiatingProcessFileName !in~ (Allowlist)
| summarize Count = count(),
            FirstSeen = min(Timestamp),
            LastSeen = max(Timestamp)
          by InitiatingProcessFileName, FileName, InitiatingProcessId, ProcessId
| order by Count desc

// Correlated variant: same source/target pair also spawned a remote thread
// (CreateRemoteThread-equivalent, ActionType == "CreateRemoteThreadApiCall")
// within a short window — a stronger, lower-noise signal than either event alone.
let ProcessAccessEvents = DeviceEvents
    | where ActionType == "OpenProcessApiCall"
    | extend GrantedAccessHex = tostring(AdditionalFields.GrantedAccess)
    | where GrantedAccessHex has_any (SuspiciousAccessMasks)
    | project Timestamp, InitiatingProcessFileName, FileName, InitiatingProcessId, ProcessId;
let RemoteThreadEvents = DeviceEvents
    | where ActionType == "CreateRemoteThreadApiCall"
    | project ThreadTime = Timestamp, InitiatingProcessFileName, FileName, InitiatingProcessId, ProcessId;
ProcessAccessEvents
| join kind=inner RemoteThreadEvents on InitiatingProcessFileName, FileName, InitiatingProcessId, ProcessId
| where (ThreadTime - Timestamp) between (0min .. 10s)
| where InitiatingProcessFileName !in~ (Allowlist)
| project Timestamp, InitiatingProcessFileName, FileName, InitiatingProcessId, ProcessId, ThreadTime

```

`detections/query.spl`:

```spl
``` Splunk SPL — Cross-process injection handle detection
`` Assumes Sysmon logs are onboarded into index=sysmon (e.g. via the Splunk
`` Add-on for Sysmon or a UF forwarding the Sysmon Operational channel).

index=sysmon EventCode=10
| rex field=GrantedAccess "(?<AccessHex>0x[0-9A-Fa-f]+)"
| where match(AccessHex, "^0x(1F0FFF|1FFFFF|1438|143A)$")
| eval SourceImage=lower(SourceImage), TargetImage=lower(TargetImage)
| lookup allowlist_source_images.csv SourceImage OUTPUT is_allowed
| where isnull(is_allowed)
| stats count min(_time) as first_seen max(_time) as last_seen
        values(GrantedAccess) as granted_access_values
        by SourceImage, TargetImage, SourceProcessId, TargetProcessId
| convert ctime(first_seen) ctime(last_seen)
| sort - count

``` Optional: raise severity when the same Source->Target pair also produced
``` an Event ID 8 (CreateRemoteThread) within 10 seconds - this correlation is
``` a much stronger signal than ProcessAccess alone.

index=sysmon (EventCode=10 OR EventCode=8)
| eval AccessHex=case(EventCode=10, GrantedAccess, EventCode=8, "n/a")
| where EventCode=8 OR match(AccessHex, "^0x(1F0FFF|1FFFFF|1438|143A)$")
| eval pair=SourceImage.":".TargetImage
| transaction pair maxspan=10s
| where eventcount>1
| table _time, SourceImage, TargetImage, SourceProcessId, TargetProcessId, eventcount
| sort - _time

```

`detections/rule-notes.md`:

```md
# Detection Rule — Cross-Process Injection Handles

## Plain-English rule

> Alert when a Sysmon Event ID 10 (ProcessAccess) shows a **SourceImage** opening
> a handle to an unrelated **TargetImage**, where **GrantedAccess** includes both
> `PROCESS_VM_WRITE` (0x0020) and `PROCESS_CREATE_THREAD` (0x0002) — the two
> rights that turn a handle from "can inspect" into "can inject and execute."
> Suppress the alert when the SourceImage/TargetImage pair is on the allowlist
> below. Optionally raise severity if the same SourceImage → TargetImage pair is
> immediately followed by an Event ID 8 (CreateRemoteThread) within a short
> window (a few seconds) — that combination is much harder to explain away as
> benign.

## Why these two rights specifically

`OpenProcess` can legitimately be called with almost any combination of rights —
`PROCESS_QUERY_INFORMATION` alone covers most monitoring tools. What's rare is a
handle that combines:

- `PROCESS_VM_OPERATION` (0x0008) + `PROCESS_VM_WRITE` (0x0020) — "I intend to
  change this process's memory," and
- `PROCESS_CREATE_THREAD` (0x0002) — "I intend to make it run something."

Debuggers request similar masks (often `PROCESS_ALL_ACCESS`), which is exactly
why they show up in this data and exactly why they need an allowlist entry
instead of a code change to the rule.

## Allowlist (known-good pairs)

| SourceImage | Why it's noisy | Notes |
|---|---|---|
| `vsjitdebugger.exe`, `devenv.exe`, `windbg.exe`, `x64dbg.exe`, `x32dbg.exe` | Debuggers legitimately need `PROCESS_ALL_ACCESS` on their target | Scope the allow to a specific SourceImage, never a blanket "debuggers" wildcard — an attacker can rename a payload to `windbg.exe` |
| AV/EDR engine processes (e.g. `MsMpEng.exe`, vendor-specific) | Security products inject scanning hooks / inline hooks into every process | Get the exact binary path + hash from your vendor's docs, don't allowlist by name alone |
| Backup/imaging agents (e.g. VSS writers, `vssvc.exe` interactions) | Some backup agents inspect process memory for open-file consistency | Verify against your organization's approved software list |
| `procexp.exe`, `procexp64.exe` (Process Explorer) | "Suspend," "Kill," and handle inspection all open elevated handles | Expected in this lab — this is what you'll see in Part 3 |

Allowlist by **full image path + code-signing thumbprint**, not just filename.
Filename-only allowlisting is trivially defeated by an attacker naming their
injector `windbg.exe` and dropping it next to the real one.

## Splunk (SPL)

See [`query.spl`](query.spl).

## Elastic/Sentinel (KQL)

See [`query.kql`](query.kql).

## Honest limitations

- **Minimal-rights injection evades this.** An attacker doesn't need
  `PROCESS_ALL_ACCESS`. `OpenProcess` with exactly `PROCESS_VM_WRITE |
  PROCESS_VM_OPERATION` plus a separate call path for execution (e.g.
  `QueueUserAPC` on a handle opened with only `PROCESS_VM_WRITE |
  PROCESS_QUERY_LIMITED_INFORMATION`, or hijacking an existing thread with
  `SetThreadContext` instead of creating a new one) can stay under a
  narrowly-scoped GrantedAccess rule. This detection catches noisy, off-the-shelf
  injection techniques — not a tuned, minimal-footprint one.
- **No Event ID 8 doesn't mean no injection.** APC injection and thread
  hijacking never call `CreateRemoteThread`, so they never fire Event 8 at all.
  The ProcessAccess (Event 10) rule is the one doing real work here; Event 8 is
  a bonus signal when it does show up.
- **Reflective/manual-mapped DLL injection** avoids the loader entirely, so the
  ImageLoad (Event 7) rule in `sysmonconfig.xml` won't see anything — there's no
  `LoadLibrary` call to trace. That technique is really a job for memory
  scanning (VAD walking, `PAGE_EXECUTE_READWRITE` region hunting), which is
  outside what Sysmon's event stream can tell you.
- **Allowlists rot.** Every entry above needs periodic review — a debugger
  version bump, a new AV build, or an attacker impersonating an allowlisted
  binary name all break the assumption the allowlist is built on.
- **This is user-mode telemetry.** Sysmon itself runs as a driver but reports
  through a user-mode-visible event log; a sufficiently privileged attacker
  (or one with a kernel driver of their own) can tamper with or blind Sysmon
  before it logs anything. See the anti-cheat section in the main
  [README](../README.md) for why this exact limitation is why kernel-mode
  anti-cheat and EDR exist.

```

`sysmonconfig.xml`:

```xml
<Sysmon schemaversion="4.90">
  <!--
    Process Injection Detection Lab - Sysmon config
    Scope: deliberately narrow. This is not a general-purpose Sysmon config
    (see SwiftOnSecurity/olafhartong for those) - it only turns on the event
    types this lab cares about, so the Operational log stays readable while
    you learn what each field means.
  -->
  <EventFiltering>

    <!-- Event ID 1: ProcessCreate — baseline: know what launched Notepad/debugger/etc, with hashes -->
    <RuleGroup name="process-create" groupRelation="or">
      <ProcessCreate onmatch="include">
        <Image condition="end with">.exe</Image>
      </ProcessCreate>
    </RuleGroup>

    <!-- Event ID 8: CreateRemoteThread — the classic injection tell (step 4 of the chain) -->
    <RuleGroup name="remote-threads" groupRelation="or">
      <CreateRemoteThread onmatch="include">
        <!-- log all remote thread creation; tune later once you've baselined your VM -->
        <SourceImage condition="contains any">.exe</SourceImage>
      </CreateRemoteThread>
    </RuleGroup>

    <!-- Event ID 10: ProcessAccess — one process opening a handle to another (steps 1-3 of the chain) -->
    <RuleGroup name="process-access" groupRelation="or">
      <ProcessAccess onmatch="include">
        <!--
          GrantedAccess values worth alerting on:
            0x1F0FFF = PROCESS_ALL_ACCESS
            0x1FFFFF = PROCESS_ALL_ACCESS (newer OS builds report this mask)
            0x1438   = VM_OPERATION (0x8) + VM_WRITE (0x20) + VM_READ (0x10) + CREATE_THREAD (0x2) + QUERY_INFORMATION (0x400)
            0x143A   = same as above plus DUP_HANDLE (0x40)
          These are the masks a classic OpenProcess -> VirtualAllocEx -> WriteProcessMemory ->
          CreateRemoteThread chain needs. A narrower request (just VM_WRITE, no CREATE_THREAD)
          can mean thread hijacking or APC injection instead - see rule-notes.md for why this
          config alone won't catch that.
        -->
        <GrantedAccess condition="is">0x1F0FFF</GrantedAccess>
        <GrantedAccess condition="is">0x1FFFFF</GrantedAccess>
        <GrantedAccess condition="is">0x1438</GrantedAccess>
        <GrantedAccess condition="is">0x143A</GrantedAccess>
      </ProcessAccess>
    </RuleGroup>

    <!-- Event ID 7: ImageLoad — flags a process loading a DLL from an unusual path (classic DLL injection artifact) -->
    <RuleGroup name="image-load" groupRelation="or">
      <ImageLoad onmatch="exclude">
        <ImageLoaded condition="begin with">C:\Windows\System32\</ImageLoaded>
        <ImageLoaded condition="begin with">C:\Windows\SysWOW64\</ImageLoaded>
        <Signed condition="is">true</Signed>
      </ImageLoad>
    </RuleGroup>

  </EventFiltering>
</Sysmon>

```
